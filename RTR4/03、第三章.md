# 图形处理单元

## 章节内容

本章介绍 GPU 的发展、数据并行执行方式，以及 GPU 如何实现图形渲染管线。重点包括 Warp/Wavefront、延迟隐藏、可编程着色器、像素处理、合并阶段和计算着色器。

### 1. GPU 的基本特点

GPU 最初主要用于加速三角形的扫描转换、颜色插值、纹理访问、深度测试和像素覆盖判断。随着硬件发展，GPU 从固定功能管线逐渐变成包含大量可编程处理单元的并行处理器。

GPU 的优势不是单个处理核心一定比 CPU 强，而是能够同时处理大量相似且相互独立的数据，例如：

- 大量顶点；
- 大量片元；
- 大量粒子；
- 大量向量或矩阵运算。

GPU 重点优化吞吐量，也就是单位时间内能够完成多少任务；CPU 则通常更重视单个任务的低延迟和复杂控制逻辑。

### 2. 数据并行与延迟隐藏

访问寄存器通常很快，但访问纹理、显存或其他内存资源可能需要等待较长时间。如果处理器在等待时完全停滞，整体性能就会下降。

GPU 通常会在当前线程组等待内存时，切换到其他已经准备好的线程组：

```text
线程组 A 等待内存
        ↓
GPU 切换执行线程组 B
        ↓
线程组 B 等待内存
        ↓
GPU 继续执行其他线程组
```

这种方式不能降低单个线程的内存访问延迟，但可以隐藏部分延迟，提高整体吞吐量。

GPU 使用 SIMD 思想，让一条指令同时处理多份数据。现代 GPU 通常把多个线程打包成执行组：

- NVIDIA 称为 Warp；
- AMD 称为 Wavefront。

一个 Warp 中的线程通常共享指令流，但每个线程拥有自己的输入数据、寄存器和执行状态。

### 3. 占用率和分支发散

GPU 能够同时驻留多少个线程组，会受到以下资源限制：

- 寄存器数量；
- 共享内存使用量；
- 线程组大小；
- 处理器核心数量。

着色器使用的寄存器越多，能够同时驻留的 Warp 可能越少，GPU 隐藏内存延迟的能力也可能下降。活动 Warp 的数量通常与占用率有关，但占用率并不是越高越好，还要考虑 ALU、内存带宽、缓存和指令依赖是否已经成为瓶颈。

如果同一 Warp 中的线程遇到不同分支，GPU 通常会依次执行这些分支，并通过活跃掩码屏蔽不属于当前分支的线程：

```text
执行分支 A：A 线程有效，B 线程闲置
执行分支 B：B 线程有效，A 线程闲置
```

这叫做线程发散。循环次数不同也可能导致类似问题。

### 4. GPU 管线的逻辑模型

第二章描述的是功能性阶段，而 GPU 会使用不同硬件阶段实现它们。GPU 中的阶段大致可以分为：

- 完全可编程；
- 可配置但不可完全编程；
- 固定功能。

典型划分如下：

| 阶段 | 控制方式 |
| --- | --- |
| 顶点着色器 | 可编程 |
| 曲面细分 | 可选、可编程 |
| 几何着色器 | 可选、可编程 |
| 裁剪 | 固定功能 |
| 三角形设置 | 固定功能 |
| 三角形遍历 | 固定功能 |
| 屏幕映射 | 可配置 |
| 像素着色器 | 可编程 |
| 合并阶段 | 高度可配置 |
| 计算着色器 | 可编程、独立于传统管线 |

这里描述的是 GPU 的逻辑模型，不等于某一款 GPU 的实际物理结构。硬件厂商可以把阶段合并、拆分，或者使用统一的着色器处理核心执行不同类型的程序。

### 5. 统一的可编程着色器

现代 GPU 通常使用统一着色器架构。顶点着色器、像素着色器、几何着色器和计算着色器可以共享类似的处理核心，GPU 可以根据工作负载动态分配这些核心。

着色器通常使用类 C 语言编写，例如 HLSL 和 GLSL。着色器代码可能先被编译成中间表示，再由驱动程序转换为具体 GPU 的机器指令。

一次 Draw Call 会启动相应的渲染管线，并调用其中的着色器。可编程阶段的输入通常包括：

- Uniform：一次 Draw Call 中保持不变的输入，例如相机矩阵和光源颜色；
- Varying：来自顶点或光栅化插值的输入，例如 UV、颜色和法线。

### 6. 顶点着色器

顶点着色器通常负责：

- 计算顶点位置；
- 执行模型、观察和投影变换；
- 执行顶点动画或蒙皮；
- 计算法线、颜色和纹理坐标；
- 为后续阶段准备插值数据。

顶点着色器通常以顶点为基本处理单位，不负责直接判断整个三角形是否可见，也不直接生成屏幕像素。

### 7. 曲面细分

曲面细分可以根据相机距离等因素生成不同数量的三角形：

```text
近处曲面 → 更多三角形
远处曲面 → 更少三角形
```

它通常包含：

- Hull Shader；
- Tessellator；
- Domain Shader。

曲面细分可以在不预先保存大量细分顶点的情况下动态生成更密集的曲面，但移动 GPU 或部分硬件可能不支持该阶段。

### 8. 几何着色器

几何着色器以点、线或三角形等图元为输入，可以：

- 修改图元；
- 丢弃图元；
- 生成新的顶点和图元；
- 执行逐图元处理。

一个典型用途是把粒子点扩展为始终朝向相机的四边形。几何着色器的输出数量和图元类型存在限制，因此很多现代几何生成任务也会使用计算着色器或其他 GPU 驱动方案。

### 9. 流式输出

流式输出可以把 GPU 处理后的顶点或图元数据写入缓冲区，而不是直接送入后续渲染阶段。

这些数据可以：

- 被 CPU 读取；
- 被 GPU 后续阶段继续使用；
- 用于粒子模拟；
- 用于缓存顶点变换或蒙皮结果。

流式输出通常按图元产生数据，因此网格中原本共享的顶点可能被重复保存，也可能占用较多存储空间。

### 10. 像素着色器

光栅化阶段会为图元覆盖的像素生成片元，并将顶点数据插值后传给像素着色器。

像素着色器可以：

- 采样纹理；
- 计算光照和材质；
- 输出颜色和 Alpha；
- 修改片元深度；
- 丢弃片元。

像素着色器通常只能影响当前片元对应的位置，不能直接把结果写入任意相邻像素。需要处理相邻像素时，通常先输出到纹理，再在后续 Pass 中读取。

### 11. Quad、导数和纹理过滤

GPU 通常以 `2×2` 的片元组，也就是 Quad，执行像素着色，以便计算：

```text
DDX：水平方向变化
DDY：垂直方向变化
```

导数常用于：

- Mipmap 选择；
- 纹理过滤；
- 屏幕空间梯度计算；
- 法线或其他局部变化估计。

即使一个三角形只覆盖 Quad 中的部分像素，其他辅助像素也可能被执行，以便得到导数。因此在动态分支或不同步循环中使用导数会受到限制。

### 12. MRT、UAV 和数据竞争

像素着色器可以同时输出多个渲染目标，这叫做 MRT：

```text
RT0：颜色
RT1：法线
RT2：材质参数
RT3：对象 ID
```

延迟着色会先将可见表面的几何和材质信息写入多个渲染目标，再在后续 Pass 中统一计算光照。

UAV 或 SSBO 允许着色器对缓冲区进行更自由的读写。但多个线程同时读写同一地址时，可能产生数据竞争，需要使用原子操作和同步机制。原子操作可以保证数据正确，但可能造成线程等待。

某些 API 还提供 ROV 等顺序保证机制，使像素着色器能够实现更可控的自定义混合，但代价通常是降低并行性。

### 13. 合并阶段与 Early-Z

合并阶段负责：

- 深度测试和深度写入；
- 模板测试和模板写入；
- 颜色混合；
- 颜色、深度和模板缓冲更新。

如果片元已经被前面的片元遮挡，再执行昂贵的像素着色就可能是浪费。因此 GPU 可能在像素着色器之前进行深度、模板或裁剪测试，这类优化通常称为 Early-Z。

如果像素着色器修改深度或丢弃片元，GPU 通常无法安全地提前完成相关测试，Early-Z 可能受到限制。

### 14. 计算着色器

计算着色器不固定在传统图形管线中的某个位置，可以通过 Dispatch 独立执行通用 GPU 计算。

```text
Dispatch
    ↓
线程组
    ↓
大量计算线程
```

线程组中的线程可以共享少量共享内存，并通过线程 ID 访问不同数据。计算着色器适合处理：

- 后处理；
- 粒子系统；
- 网格处理和面部动画；
- GPU 剔除；
- 图像过滤；
- 阴影和景深；
- 流体、布料等其他并行模拟。

如果数据一直驻留在 GPU 上，就可以避免 GPU 与 CPU 之间的往返传输。

## 讨论与补充

### 1. GPU 通过线程切换隐藏内存访问延迟

GPU 访问纹理或显存时也可能需要等待。如果当前线程组正在等待，GPU 可以先切换去执行其他已经准备好的线程组，等数据返回后再继续执行原来的线程组。

```text
线程组 A 等待纹理数据
        ↓
GPU 切换执行线程组 B
        ↓
线程组 A 的数据返回后继续执行
```

这里的“切换”主要发生在不同线程组之间，不是说同一个线程可以随意中途切换去完成另一个完全无关的任务。

### 2. SIMD 与 SIMT

SIMD（Single Instruction, Multiple Data）强调数据级并行：一条向量指令同时处理多份数据。

```text
一条 ADD 指令：
a0 + b0、a1 + b1、a2 + b2、a3 + b3
```

SIMT（Single Instruction, Multiple Threads）更像是 GPU 提供的线程级编程模型。程序员可以编写许多看似独立的线程，GPU 再把它们分组，让它们执行相同的 Shader 代码，但处理不同的数据。

```text
SIMD：一条指令处理多个数据
SIMT：多个线程执行相同指令流，处理不同数据
```

现代 GPU 通常使用类似 SIMD 的硬件方式实现 SIMT，但二者不是完全相同的概念。

### 3. Warp / Wavefront 与相同指令

GPU 会把线程分组执行：

- NVIDIA 通常称为 Warp；
- AMD 通常称为 Wavefront；
- 不同硬件的线程组大小可能不同。

在同一执行时刻，一个线程组中的活跃线程通常执行同一条机器指令，而不是只执行“同类指令”。每个线程使用的输入数据可以不同。

```text
线程 0：用数据 0 执行 MUL
线程 1：用数据 1 执行 MUL
线程 2：用数据 2 执行 MUL
```

这里的并行来自：

```text
相同的指令 + 不同的数据
```

### 4. 分支发散与线程闲置

假设一个 Warp 中的线程执行：

```hlsl
if (value > 0)
{
    // 路径 A
}
else
{
    // 路径 B
}
```

如果一部分线程走 A，另一部分线程走 B，GPU 通常会使用活跃掩码分阶段执行：

```text
执行 A：走 A 的线程有效，走 B 的线程被屏蔽
执行 B：走 B 的线程有效，走 A 的线程被屏蔽
```

因此，分支发散的本质是：

> 同一个 Warp 共享指令流。当不同线程需要执行不同路径时，GPU 只能依次执行这些路径，暂时屏蔽不属于当前路径的线程。

这里的线程不是永远不能做其他工作。GPU 仍然可以切换到其他 Warp；只是当前 Warp 中没有走当前路径的 Lane，不能自动去处理另一个完全无关的任务。

如果整个 Warp 都走 A 或都走 B，就不会产生明显的分支发散。

### 5. 能否提前把 A、B 分成两批执行？

可以，但需要在执行 A、B 之前先完成分类和重新组织：

```text
原始数据
    ↓
判断哪些数据属于 A，哪些属于 B
    ↓
A 数据列表 ──→ 执行 A
B 数据列表 ──→ 执行 B
```

如果 CPU 事先知道分类结果，可以由 CPU 分别提交两个 Dispatch 或 Draw。

如果分类条件只能由 GPU 判断，则通常需要：

```text
Pass 1：GPU 判断并生成 A/B 列表
Pass 2：分别处理 A 列表和 B 列表
```

但分类、写入列表、原子操作、同步和重新调度本身也有成本。因此要比较：

```text
分支发散的代价
vs
分类、重排、同步和再次调度的代价
```

如果 A、B 只是很短的计算，直接让一个 Warp 依次执行两个分支可能更快；如果两个分支都很复杂，提前分类再分批执行可能更值得。

### 6. `float4` 不一定等于 SIMD 优化

```hlsl
float4 result = a * b + c;
```

它在语义上表示四个分量分别进行运算：

```text
result.x = a.x * b.x + c.x
result.y = a.y * b.y + c.y
result.z = a.z * b.z + c.z
result.w = a.w * b.w + c.w
```

`float4` 可能带来向量化计算，也可能主要改善数据布局和内存对齐，但不保证一定减少指令数量。现代 GPU 可能将它拆成多个标量运算。

还要区分两种并行：

```text
float4 的四个分量：一个线程内部的数据并行
Warp 中的多个线程：多个线程之间的 SIMT 并行
```

把几个参数打包成 `float4`，常见优势还包括：

- 更容易满足 16 字节对齐；
- 让 CBuffer 或 StructuredBuffer 的布局更规整；
- 方便一次读取一组相关参数。

但如果只使用其中一个分量，其他分量完全不用，打包后不一定更快。

### 7. 实例化、CBuffer 与 SIMD/SIMT 的关系

实例化本身不是 SIMD。实例化主要解决的是：

```text
一次 Draw 绘制多个相同 Mesh 的实例
```

GPU 随后会并行处理这些实例的顶点：

```text
线程 0：处理实例 0
线程 1：处理实例 1
线程 2：处理实例 2
```

这些线程执行相同的 Shader，但读取不同的实例数据，因此实例化很适合发挥 SIMT 并行能力。

CBuffer 也不是 SIMD。CBuffer 主要用于保存多个 Shader 调用共享的只读参数，例如：

```hlsl
float4x4 _ViewProjection;
float3 _CameraPosition;
```

所有线程可以读取同一个相机参数，但每个线程仍然要用自己的顶点执行矩阵乘法。

```text
CBuffer：所有线程共用的参数
Instance Buffer：不同实例各自的数据
SIMT：多个线程执行相同指令流
```

所以实例化和 CBuffer 的作用是组织数据、减少提交或重复绑定；真正的 SIMD/SIMT 并行发生在 GPU 执行这些 Shader 的时候。
