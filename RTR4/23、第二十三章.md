# 图形硬件

## 章节内容

本章从硬件角度解释三角形如何变成片元，以及 GPU 如何用层次化光栅化、线程组、缓存和片上存储提高吞吐。理解这些机制有助于解释 2×2 Quad、ddx/ddy、Hi-Z、寄存器占用、Early-Z、ROP、显存和 PCIe 等概念。

### 1. 三角形覆盖与边缘函数

三角形可以用三条边对应的线性函数表示。对一条边写成 E(x,y)=a*x+b*y+c，代入像素中心后，符号表示点位于边的哪一侧；三条边的符号满足同一方向条件时，像素就在三角形内部。因为线性函数在相邻像素之间只发生固定增量，所以硬件可以用加法递推，而不必为每个像素重新计算完整方程。

三角形覆盖通常先在 Tile 或粗粒度块上判断，再细分到更小区域，最后生成片元。这样可以快速跳过完全在三角形外部的块，也能对完全覆盖的块采用更高效路径。

### 2. 2×2 Quad 与导数

像素着色器通常以 2×2 的 Quad 作为导数计算的基本邻域。即使某些 Quad 中部分像素最终被裁剪，硬件也可能为它们执行辅助计算，以便得到稳定的 ddx 和 ddy。纹理隐式 Mipmap 选择、法线贴图过滤和程序化抗锯齿都会依赖这些导数。

2×2 不是说所有工作的线程组都只有四个线程，也不是 3×3 卷积。3×3 更适合通用图像滤波，而 Quad 是局部一阶导数和覆盖处理的最小常用邻域。

### 3. Tile、Hi-Z 与保守光栅化

Tile 级别的光栅化会先判断三角形与块的关系，再递归或迭代细分。Hi-Z 则是从深度缓冲建立层次金字塔，用一个粗粒度深度值代表区域，快速判断某个物体或块是否可能被遮挡。二者都利用层次化思想，但 Tile 光栅化关注三角形覆盖，Hi-Z 关注深度可见性。

保守光栅化会把任何与三角形接触的像素或体素标记，避免普通中心采样漏掉细小几何，适合碰撞、遮挡、体素化和可见性构建，但会产生一定误报。

### 4. GPU 存储层次

寄存器是线程私有、速度最快但容量有限的存储。Shader 使用的临时变量越多，每个线程占用的寄存器越多，同一计算单元可同时驻留的 Warp/Wave 越少。寄存器不足时，一些数据可能溢出到 Local Memory；Local Memory 在逻辑上属于线程私有，但物理上通常位于较慢的显存层次，因此会产生额外 Load/Store。

Shared/Group Memory 是一个线程组共享的片上存储，需要显式同步，适合 Tile 数据复用、局部归约和线程协作。它不是 Local Memory 的下一层自动溢出区域：寄存器溢出通常不会自动进入 Shared Memory，Shared Memory 也需要在 shader 中显式声明和管理。

更多驻留 Warp 可以隐藏纹理和内存延迟，但不是越多越好。如果 ALU、寄存器、Shared Memory、缓存或带宽已经成为瓶颈，继续增加 Warp 只会竞争资源。

### 5. 系统内存、显存、PCIe 与 UMA

显存不仅存最终画面，还保存顶点、索引、纹理、Buffer、Shader 资源、深度、阴影、G-Buffer 和中间 Render Target。独立 GPU 通常拥有独立显存，CPU 通过 PCIe 等总线提交命令和传输数据；频繁 CPU/GPU 回读会造成同步和带宽成本。

UMA 中 CPU 和 GPU 共享统一内存地址空间，避免独立显存之间的复制，但 CPU 和 GPU 会争用内存带宽和缓存。部分设备会从系统内存划出高带宽区域作为显存，但关键不是名称，而是物理内存层次、带宽、缓存和访问路径。

### 6. Early-Z、Late-Z 与深度预处理

ZTest 和 ZWrite 是渲染状态语义，但具体硬件何时执行测试会受 shader 和管线影响。Early-Z 在片元着色前进行深度测试，可以跳过被遮挡的片元；Late-Z 在片元着色后进行测试，适用于 shader 可能改变深度、discard 或产生其他影响的情况。

Alpha Clip 的典型做法是先执行 clip(alpha-threshold)，通过的片元才继续。若材质还要正确遮挡后方物体，通常开启深度测试和深度写入；被 clip 的片元不会写入深度，只有真正通过 shader 和深度测试的片元才会写入。为了减少昂贵透明或特效 shader 的片元开销，可以先用一个便宜的深度预处理 pass 写入 Alpha Clip 后的可见深度，后续 pass 再利用 Early-Z。

Shader 深度偏移可以修改片元深度或在光栅化阶段施加偏移，用于 Decal、阴影偏移和解决共面竞争；它不是简单移动整个模型，但如果 shader 显式写深度，就可能阻碍硬件使用 Early-Z。

### 7. 输出后端与交换缓冲

ROP 或类似的输出后端负责颜色和深度/模板测试后的写入、混合、格式转换和压缩等固定功能。具体硬件划分会不同，但深度、模板、RGBA Mask、Blend 等通常由光栅化后端和相关固定功能协同完成。

单缓冲会在显示和绘制之间产生撕裂，如今实时图形通常使用双缓冲或三缓冲。双缓冲延迟低但在 GPU 忙时可能阻塞；三缓冲可以让 CPU/GPU 继续工作，但可能增加排队帧数和输入延迟。现代系统还会使用邮箱模式、显示合成器和可变刷新率进行权衡。

## 讨论与补充

### 既有整理

### 本章核心

这一章主要解释 GPU 内部如何完成光栅化、并行执行、任务调度、缓存和内存访问。之前讨论的渲染管线是功能上的划分，而本章进一步说明这些功能在硬件上是如何高效实现的。

重点可以概括为：

```text
三角形
  ↓
边缘函数判断覆盖
  ↓
2×2 Quad 执行片元着色并计算导数
  ↓
Tile 级别粗筛和层次遍历
  ↓
深度测试、纹理采样和颜色写入
```

### 1. 用叉乘判断点是否在三角形内

设三角形顶点按照逆时针排列：

```text
A → B → C
```

对待测试点 `P`，分别计算它相对于三条有向边的位置：

```cpp
s0 = cross2(B - A, P - A);
s1 = cross2(C - B, P - B);
s2 = cross2(A - C, P - C);
```

二维向量叉乘为：

```cpp
cross2(u, v) = u.x * v.y - u.y * v.x;
```

对于逆时针三角形：

```text
s0 >= 0 且 s1 >= 0 且 s2 >= 0
```

就说明 `P` 位于三角形内部或边界上。如果某个结果小于 0，说明 `P` 位于对应有向边的外侧半平面，因此一定在三角形外部。

例如：

```text
A = (0, 0)
B = (4, 0)
C = (0, 3)
P = (1, 1)
```

计算得到：

```text
s0 = 4
s1 = 5
s2 = 3
```

三个结果都为正，因此点在三角形内。

需要注意，`s2 < 0` 的准确含义是：点位于有向边 `C → A` 对应的外侧半平面，不一定表示点落在“线段 AC 的延长线”上。若点在线段所在直线上，则 `s2 = 0`，还需要检查另外两条边。

如果三角形按照顺时针排列，三个符号会整体反过来。实际代码要统一顶点绕序，或检查三个结果是否具有相同符号。

### 2. 边缘函数

上面的叉乘可以展开成一个线性函数：

```text
E(x, y) = ax + by + c
```

它表示点 `(x, y)` 位于某条有向边哪一侧：

```text
E > 0：一侧
E = 0：在线上
E < 0：另一侧
```

以三角形 `A=(0,0)、B=(4,0)、C=(0,3)` 为例，三条边对应的函数可以写成：

```text
E_AB(x, y) =  4y
E_BC(x, y) = -3x - 4y + 12
E_CA(x, y) =  3x
```

点在三角形内部需要满足：

```text
E_AB >= 0
E_BC >= 0
E_CA >= 0
```

#### 为什么线性函数适合 GPU

对于：

```text
E(x, y) = ax + by + c
```

向右移动一个像素：

```text
E(x + 1, y) = E(x, y) + a
```

向下或向上移动一个像素：

```text
E(x, y + 1) = E(x, y) + b
```

例如：

```text
E_BC(x, y) = -3x - 4y + 12
```

如果当前像素的结果是 `5`，向右移动后就是：

```text
5 + (-3) = 2
```

再向右移动一次：

```text
2 + (-3) = -1
```

GPU 不需要为每个像素重新执行完整叉乘，只要保存当前结果，并按固定增量更新即可。

最终，GPU 对三条边生成覆盖判断：

```text
E0 >= 0
E1 >= 0
E2 >= 0
```

这三个布尔结果共同形成三角形的覆盖 Mask。

边界上的像素还要使用固定的决胜规则，例如 Top-Left Rule，避免两个共享边的三角形重复覆盖同一个像素。

### 3. 2×2 Quad 与 `ddx/ddy`

GPU 通常以 `2×2` 个片元为一组进行片元着色：

```text
[ a  b ]
[ c  d ]
```

对于某个片元属性 `v`，例如 UV，可以近似计算：

```text
ddx：
[ b - a ]
[ d - c ]

ddy：
[ c - a ]
[ d - b ]
```

这些差分表示属性在屏幕水平方向和竖直方向的变化速度。纹理采样器会利用它们估计纹理在屏幕上的覆盖范围，并选择合适的 Mipmap 层级：

```text
UV 变化快 → 使用更低分辨率的 Mipmap
UV 变化慢 → 使用更高分辨率的 Mipmap
```

#### 为什么是 2×2 而不是 3×3

普通 `ddx/ddy` 只需要一阶局部差分。`2×2` 已经包含两个水平方向差分和两个竖直方向差分，足够估计纹理梯度。

`3×3` 更适合计算中心差分，例如：

```text
ddx ≈ 右侧 - 左侧
```

但它会需要更多片元、更多寄存器和更大的执行范围，而且更容易跨越三角形边界。对于普通纹理 LOD 和导数计算，额外信息通常不值得这些成本。

如果三角形只覆盖 Quad 中的一个像素，其他位置也可能作为辅助线程执行，以便提供导数：

```text
[真实覆盖  辅助]
[辅助      辅助]
```

辅助线程通常不会写入最终颜色，但可能参与片元计算。这会造成 Quad Overshading：三角形覆盖的像素很少，但硬件仍然执行了整个 Quad 的部分工作。

### 4. Tile 级别的层次遍历

GPU 通常不会对整个屏幕逐像素扫描每个三角形，而是先把屏幕划分成较大的 Tile：

```text
屏幕
 ├─ Tile 0
 ├─ Tile 1
 ├─ Tile 2
 └─ ...
```

对每个 Tile，可以使用边缘函数进行粗略判断：

```text
Tile 完全在三角形外部
        ↓
直接跳过整个 Tile

Tile 可能与三角形相交
        ↓
继续细分成更小 Tile 或 Quad
        ↓
最后进行逐采样点判断
```

如果某个 Tile 的特定角点已经位于某条边的外侧，并且根据边缘函数可以确定整个 Tile 都在该边外部，就可以直接拒绝这个 Tile。移动到相邻 Tile 时，同样可以利用边缘函数的增量性质。

这种过程类似：

```text
大区域粗筛
    ↓
小区域细筛
    ↓
Quad
    ↓
单个采样点
```

它和 AABB 的粗筛、BVH 的层次遍历有相同的思想：先以较低成本排除大范围不可能区域。

### 5. Tile 遍历不是 Hi-Z

二者都有“粗到细、层次化拒绝”的思想，但判断的问题不同。

#### Tile 光栅化

判断：

> 当前三角形是否可能覆盖这个屏幕区域？

它主要使用：

- 屏幕空间包围盒；
- 边缘函数；
- Tile 与三角形的覆盖关系。

#### Hi-Z

判断：

> 当前物体是否已经被已有深度遮挡？

它从深度缓冲建立层次结构：

```text
原始深度图：8×8
       ↓ 2×2 合并
深度层级：4×4
       ↓ 2×2 合并
深度层级：2×2
       ↓
深度层级：1×1
```

查询一个物体时，可以先使用较粗的深度层级。如果已经能够确定物体完全位于已有遮挡之后，就直接丢弃；如果不能确定，再访问更细的层级。

因此，Hi-Z 更接近四叉树或图像金字塔，而不是严格意义上的一维二分查找。

```text
Tile 光栅化：三角形是否覆盖区域？
Hi-Z：物体是否被深度遮挡？
```

二者可以组合：

```text
三角形包围区域
  ↓
Tile 覆盖测试
  ↓
Hi-Z 粗略遮挡测试
  ↓
Quad 覆盖测试
  ↓
Early-Z
  ↓
片元着色
```

### 6. 保守光栅化

标准光栅化通常根据采样点是否位于三角形内部来决定是否访问像素。保守光栅化会改变这个覆盖规则：

- 外保守光栅化（Overestimate）：访问所有与三角形接触或重叠的像素，宁可多算；
- 内保守光栅化（Underestimate）：只访问完全位于三角形内部的像素，宁可少算。

它适合：

- 图像空间碰撞检测；
- 遮挡剔除；
- 阴影计算；
- 某些抗锯齿算法。

### 7. Register、Local Memory 与 Shared/Group Memory

这些存储不是“一级一级自动溢出”的统一层级，而是作用域和用途不同的存储区域：

```text
每个线程：
  Register
  Local Memory

每个线程组：
  Shared / Group Memory

全局：
  Global Memory / VRAM
```

#### Register

寄存器保存单个线程正在使用的局部变量和临时计算结果。它速度快，但每个 SM/CU 的寄存器文件总量有限。

Shader 每线程使用的寄存器越多，可以同时驻留的 Warp 越少。

#### Local Memory

Local Memory 在逻辑上属于单个线程，通常用于：

- 寄存器放不下的局部数组；
- 动态索引的临时数据；
- Register Spilling 产生的线程私有数据。

它不等于快速的“本地缓存”。在许多 GPU 上，它的实际后备存储位于全局显存或统一内存中，访问成本可能远高于寄存器。

如果寄存器不够，常见路径是：

```text
Register 不够
    ↓
部分线程私有变量溢出到 Local Memory
    ↓
增加额外 Load/Store
```

#### Shared/Group Memory

Shared Memory 是一个线程组共同使用的片上工作区，例如 HLSL 中的：

```hlsl
groupshared float tile[256];
```

它需要显式声明和协作访问，不是 Local Memory 满了之后的自动备用空间。

同样，Shared Memory 用量过大也不会自动转移到 Local Memory，通常会导致资源限制、编译/启动失败，或降低一个 SM/CU 能够同时驻留的线程组数量。

因此更准确的关系是：

```text
局部变量 → 优先分配 Register
Register 不足 → 可能溢出到 Local Memory

线程组共享数据 → 显式分配 Shared/Group Memory
```

某些特定厂商和编译器可能支持特殊的共享内存溢出优化，但不能把它当作通用硬件层级。

#### 与 CBuffer、Texture 的区别

`CBuffer`、Texture、StructuredBuffer 是资源或绑定对象，不是寄存器层级。Shader 读取这些资源时，数据可能经过常量缓存、纹理缓存等，再加载到寄存器参与计算。

```text
CBuffer：多个线程共享的只读输入
Register：每个线程自己的计算状态
```

### 8. 延迟与 Occupancy

GPU 中的延迟是从发起操作到结果可用之间的时间。例如：

- 读取显存中的数据；
- 等待纹理过滤结果；
- 等待缓存返回；
- 等待 GPU 结果回读到 CPU。

如果一个 Warp 发起纹理读取后只能原地等待，执行单元就会空闲。因此 GPU 会同时驻留多个 Warp：

```text
Warp A：等待纹理
Warp B：执行算术
Warp C：执行加载
Warp D：等待内存
```

调度器可以在 Warp A 等待期间切换到 Warp B 或 C，用其他 Warp 的工作隐藏内存延迟。

#### Occupancy

Occupancy 可以粗略表示为：

```text
Occupancy = 当前活跃 Warp 数量 / 硬件允许的最大 Warp 数量
```

寄存器、Shared Memory、纹理单元和其他资源都会限制可驻留的 Warp 数量。

```text
每线程寄存器少
    ↓
可驻留更多 Warp
    ↓
更容易隐藏纹理/内存延迟
```

但 Occupancy 不是越高越好：

- 过多 Warp 可能造成缓存竞争；
- 为了驻留更多 Warp，可能增加 Register Spilling；
- Shader 如果已经是 ALU 计算瓶颈，更多 Warp 不会增加 ALU 数量；
- 循环展开虽然可能提高指令级并行，却可能增加寄存器使用。

因此真正的目标是：

> 让活跃 Warp 数量足以隐藏主要延迟，同时避免寄存器溢出、缓存竞争和不必要的内存访问。

### 9. 系统内存、显存、PCIe 与 UMA

#### 显存不是只存最终画面

显存（VRAM，Video RAM）是 GPU 常用的专用内存。它可以保存：

- 纹理和 Mipmap；
- Vertex Buffer、Index Buffer；
- Constant/Structured Buffer；
- Color Buffer、Depth Buffer 和 G-Buffer；
- Shadow Map、后处理 Render Target；
- 光线追踪加速结构和 Compute Buffer。

因此，“视频内存”不是只保存最终要送到显示器的那一张图，而是 GPU 渲染和计算时经常访问的数据仓库。

#### 独立 GPU 与独立显存

独立显卡通常有自己的显存：

```text
CPU 内存 RAM
      ↓ PCIe
独立 GPU
      ↓
独立显存 VRAM
```

独立显存通常不是从系统 RAM 临时切出来的一块区域，而是 GPU 侧独立的物理内存。它可以通过更适合 GPU 的内存接口提供较高带宽。

因此，CPU 创建的资源可能需要上传：

```text
CPU 准备资源
    ↓ PCIe 上传
GPU 显存
    ↓
GPU 读取和渲染
```

反方向的 GPU 回读通常更加敏感，因为它可能要求等待 GPU 完成相关工作，并让数据通过 PCIe 返回 CPU。

#### PCIe

PCIe 是 CPU/主板平台与独立 GPU 之间的高速互连接口，不是显存，也不是 GPU 内部缓存。它主要承载：

- CPU 向 GPU 上传资源；
- GPU 向 CPU 回读结果；
- CPU 向 GPU 提交命令和同步信息。

PCIe 带宽通常低于独立显卡访问自身显存的带宽，所以实时渲染中会尽量让静态纹理、网格和 Render Target 留在 GPU 侧，减少频繁往返。

#### UMA

UMA（Unified Memory Architecture，统一内存架构）中，CPU 和 GPU 使用同一片物理内存：

```text
        共享内存
       /        \
     CPU        GPU
```

常见于手机、游戏主机、集成 GPU、Apple Silicon 和独立头显中的移动 SoC。

UMA 可以减少独立显卡式的“系统 RAM → VRAM”复制，但不代表 CPU 和 GPU 访问完全没有成本。它们仍可能竞争内存带宽，并且可能拥有各自的缓存，还需要处理缓存一致性和同步。

有些 UMA 系统会在设置中显示一部分“专用显存”，但这不一定等同于独立显卡上的物理 VRAM，可能只是为 GPU 预留的共享系统内存。

#### 两种架构的关键区别

| 项目 | 独立 GPU + VRAM | UMA |
|---|---|---|
| CPU/GPU 内存 | 通常分开 | 共享物理内存 |
| GPU 专用带宽 | 通常较高 | CPU/GPU 共享带宽 |
| CPU-GPU 资源共享 | 需要上传、映射或复制 | 通常更直接 |
| PCIe 往返影响 | 明显 | 通常没有独立显卡式往返 |
| 常见设备 | PC 独立显卡 | 手机、主机、集显、Apple Silicon |

所以最准确的记忆方式是：

```text
显存：GPU 常用的数据仓库
PCIe：CPU 与独立 GPU 之间的道路
UMA：CPU 与 GPU 共用一个物理内存仓库
```

### 10. Early-Z 与 Late-Z

需要区分“深度测试的逻辑规则”和“GPU 实际执行深度测试的时机”。

#### ZTest 和 ZWrite 是我们设置的语义

```text
ZTest：当前片元是否通过深度比较
ZWrite：通过后是否更新深度缓冲
```

例如：

```text
不透明物体：ZTest On，ZWrite On，Blend Off
透明物体：ZTest On，ZWrite Off，Blend On
```

开启 `ZTest` 只表示最终需要进行深度比较，不保证比较一定发生在片元着色器之前。

#### Early-Z

Early-Z 在 Fragment Shader 之前做深度测试：

```text
生成片元
  ↓
Early-Z
  ↓ 深度失败
直接丢弃，不执行 Fragment Shader
```

它的主要收益是避免对最终不会显示的片元执行纹理采样、光照和复杂计算。

普通不透明 Shader 最容易使用 Early-Z，因为它通常不使用 `clip/discard`，不写 `SV_Depth` 或 `gl_FragDepth`，也不产生会影响结果顺序的 UAV/Storage Buffer 副作用。

#### Late-Z

Late-Z 在 Fragment Shader 之后做深度测试：

```text
生成片元
  ↓
Fragment Shader
  ↓
Late-Z
  ↓ 深度失败
颜色和深度都不写入
```

如果 Shader 修改了最终深度，例如写入 `SV_Depth` 或 `gl_FragDepth`，GPU 必须先运行 Shader，才能知道应该用哪个深度值进行比较。常见用途包括视差遮挡、Ray Marching 和 Impostor。

#### 带 `clip` 的特效如何设置深度

如果特效是“要么显示、要么完全丢弃”的硬边镂空效果，例如树叶、栅栏、镂空贴花等，它应当按 Alpha Clip/Cutout 处理，而不是按普通透明处理：

```text
ZTest LEqual
ZWrite On
Blend Off
```

像素 Shader 中先执行：

```hlsl
float alpha = SAMPLE_TEXTURE2D(_MainTex, sampler_MainTex, uv).a;
clip(alpha - _Cutoff);
```

`clip` 失败时，片元会被完全丢弃；即使开启了 `ZWrite`，它也不会写入深度。只有通过 `clip` 的片元才会继续进行深度测试，并在通过后更新深度缓冲：

```text
生成片元
  ↓
clip()
  ├─ 失败：不写颜色、不写深度
  └─ 通过：执行 ZTest
              ↓
          通过后执行 ZWrite
```

因此，镂空物体的实体部分会遮挡后面的物体，而镂空部分不会遮挡后面的物体。它不需要像普通透明物体那样依赖严格的从后往前排序，因为保留下来的区域可以作为不透明表面参与深度测试。

需要注意，带 `clip` 的 Shader 仍可能限制完整的 Early-Z 优化。硬件可以先用 Early-Z 拒绝那些明显被前方物体遮挡的片元，但不能在确认 `clip` 结果之前就永久提交深度，否则被裁掉的区域会错误地遮挡后方物体。实际硬件可能使用“Early-Z 粗筛 + Fragment Shader 执行 clip + 最终深度确认”的混合路径，也可能退化为 Late-Z。

#### Alpha Clip 与普通透明的区别

```text
Alpha Clip：覆盖状态接近二值，通常 ZWrite On
Alpha Blend：覆盖程度是连续值，通常 ZWrite Off
```

如果是烟雾、火焰、柔边粒子等需要多个透明层叠加的特效，即使内部也使用了某种 `clip`，通常仍不应直接开启 `ZWrite`。否则前面的粒子可能写入深度并挡住后面的粒子，破坏叠加效果。这类材质一般使用：

```text
ZTest LEqual
ZWrite Off
Blend On
```

这样它仍然会被场景中的不透明物体遮挡，但不会把自己写入深度缓冲。

#### Alpha Clip 的深度预处理 Pass

如果像素 Shader 很复杂，或者 Alpha Clip 物体的 Overdraw 很高，可以增加深度预处理：

```text
DepthOnly Pass：
    执行相同的 Alpha 采样和 clip
    ZTest LEqual
    ZWrite On
    ColorMask 0

Color Pass：
    再次执行相同的 clip
    ZTest Equal 或 LEqual
    计算颜色、光照和其他昂贵效果
```

DepthOnly Pass 不是所有特效都需要。它本身仍然要执行顶点处理、Alpha 采样和 `clip`；如果正式像素 Shader 很简单，额外 Pass 反而可能变慢。更重要的是，两个 Pass 的几何、裁剪阈值、深度偏移和自定义深度计算必须一致，否则 Color Pass 可能无法通过 `ZTest Equal`。

#### 深度偏移不等于移动几何体

ShaderLab 中的：

```shaderlab
Offset Factor, Units
```

通常是在光栅化后的深度比较或写入时增加一个小偏移，而不是直接移动顶点。它常用于 Decal、弹孔、刀痕、共面覆盖层和阴影中的 Z-Fighting/Shadow Acne。

固定管线的 `Offset` 通常不会像像素 Shader 输出 `SV_Depth` 那样必然破坏 Early-Z，因为偏移规则可以较早确定；但偏移过大可能使物体错误地穿过遮挡物，或者造成阴影悬浮。

如果在 Fragment Shader 中输出 `SV_Depth` 或 `gl_FragDepth`，最终深度要等 Shader 执行后才知道，通常会限制 Early-Z，并可能让测试推迟到 Late-Z。若使用深度预处理，则预处理 Pass 也必须产生一致的自定义深度。

#### 为什么 `clip` 会影响 Early-Z

对于：

```hlsl
clip(alpha - cutoff);
```

GPU 必须保证：

```text
clip 失败 → 不写颜色，也不写深度
```

因此不能简单地采用“Early-Z 通过后立即永久写入深度，再执行 clip”的路径，否则透明纹素可能提前写入深度，错误遮挡后方物体。

实际硬件可能采用混合路径：

```text
Early-Z：提前排除已经被遮挡的片元
  ↓
Fragment Shader：执行 clip
  ↓
确认片元保留后，再提交最终深度写入
```

也可能使用更保守的 Late-Z。具体路径由编译器、驱动和 GPU 架构决定。

#### 为什么 Shader 副作用会阻碍 Early-Z

假设后方片元虽然最终会被深度测试丢弃，但 Shader 中有：

```hlsl
RWStructuredBuffer<uint> Counter;
InterlockedAdd(Counter[0], 1);
```

如果使用 Early-Z，片元可能在 Shader 前被丢弃，计数器不会增加；如果使用 Late-Z，Shader 会先执行，计数器会增加。两者结果不同，因此 GPU 不能随意提前测试。

#### Early/Late 是否完全由我们控制

普通情况下：

```text
ZTest/ZWrite：由应用设置
Early-Z/Late-Z：由编译器、驱动和硬件选择
```

部分 API 支持显式 Early Tests，例如 HLSL 的 `[earlydepthstencil]`，以及 GLSL/Vulkan 的 `layout(early_fragment_tests) in`。但强制 Early Tests 会改变深度、模板和 Shader 副作用的语义。对于带 `clip`、深度写入或副作用的 Shader，不能把它当成单纯的性能开关。

因此最准确的理解是：

> 我们控制深度测试和写入的规则，也能在特定 API 中要求 Early Tests；但普通渲染路径中，GPU 到底采用 Early-Z、Late-Z，还是 Early-Z 粗筛加 Late-Z 最终确认，通常不是跨硬件完全可控的。

### 11. 颜色缓冲、ROP 与交换缓冲

#### 颜色缓冲不一定只存颜色

颜色缓冲本质上是逐像素写入的 Render Target，可以保存最终颜色，也可以保存 Albedo、法线、材质 ID、运动向量、后处理结果等 G-Buffer 或算法数据。

```text
RGBA8：每通道 8 bit，常见的低成本格式
RGBA16F：每通道 16 位浮点，适合 HDR 和高精度中间结果
```

精度越高，颜色带状问题越少，但显存占用、带宽和缓存压力越大。

#### ROP/输出后端

ROP（Raster Operations）可以理解为光栅化后端的一组固定功能单元。片元着色器输出之后，GPU 需要决定这个结果能否以及如何写入 Render Target：

```text
片元着色器输出
  ↓
深度/模板测试
  ↓
Alpha Blending
  ↓
颜色写入 Mask
  ↓
写入颜色、深度和模板缓冲
```

现代 GPU 不一定严格使用“ROP”这个名称，而是由多个后端单元共同完成这些职责。`clip/discard` 则是在片元着色器中执行的，不是 ROP 主动计算 Alpha 后再决定丢弃。

#### 单缓冲、双缓冲和三缓冲

单缓冲让 GPU 和显示器同时访问同一张缓冲，容易出现撕裂，因此实时游戏和交互应用通常至少使用两个可显示缓冲。

双缓冲：

```text
Buffer A：正在显示
Buffer B：GPU 正在绘制
```

绘制完成后交换两张缓冲。它延迟较低、显存开销较小，仍然是常见方案。

三缓冲：

```text
Buffer A：正在显示
Buffer B：等待显示
Buffer C：GPU 正在绘制
```

当某一帧没有及时完成时，三缓冲可以减少 GPU 因等待显示同步而停顿，但代价是更多显存和可能更高的排队延迟。

现代 API 更常用 Swapchain 和 Present Mode 描述这套机制，而不只是简单地说“双缓冲”或“三缓冲”。Vulkan 的 FIFO、Mailbox、Immediate，以及 Windows 的 DXGI Flip Model，都会影响缓冲数量、呈现队列、是否等待垂直空白和是否可能撕裂。

因此：

```text
单缓冲：现代实时图形中较少作为常规方案
双缓冲：低延迟场景中仍常见
三缓冲/多缓冲：用于提高吞吐和减少卡顿
```

### 本章阶段性总结

```text
叉乘：判断点相对三角形边的位置
边缘函数：把叉乘改写成 E(x,y)=ax+by+c
增量计算：让 GPU 快速遍历相邻像素
2×2 Quad：计算 ddx/ddy，并执行片元着色
Tile 遍历：先粗筛屏幕区域，再细分到 Quad/像素
Hi-Z：使用深度层次结构判断遮挡
保守光栅化：扩大或收缩标准覆盖范围
Register：每线程的快速局部存储
Local Memory：每线程私有的溢出/大数组存储
Shared Memory：线程组显式共享的片上工作区
Occupancy：活跃 Warp 对可驻留最大 Warp 的比例
ZTest：最终是否进行深度比较
ZWrite：通过后是否更新深度缓冲
Early-Z：片元着色前的深度拒绝
Late-Z：片元着色后的深度确认
Alpha Clip：二值覆盖，失败的片元不写颜色和深度
Depth Prepass：先写深度，再执行昂贵的颜色 Pass
Offset：固定管线的深度偏移，不等于移动顶点
ROP：处理深度、模板、混合和颜色写入等输出后端操作
```

核心区别是：

> 边缘函数判断“像素是否被三角形覆盖”，Hi-Z 判断“物体是否已经被深度遮挡”；两者都采用了层次化拒绝，但不是同一种技术。

GPU 硬件优化还需要同时考虑：

```text
计算量
寄存器使用量
可驻留 Warp 数量
内存访问延迟
缓存命中率
显存带宽
VRAM：GPU 常用的专用内存
PCIe：CPU/平台与独立 GPU 的互连接口
UMA：CPU 与 GPU 共享物理内存的架构
```

这些指标之间存在取舍，不能只根据单一指标判断 Shader 是否更快。
