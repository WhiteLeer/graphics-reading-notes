# 管线优化

## 核心原则：先找瓶颈，再优化

渲染管线中可能成为瓶颈的阶段包括：

- 应用阶段：CPU 逻辑、剔除、排序、资源准备和 Draw Call/API 提交；
- 几何阶段：网格读取、顶点处理、顶点缓存和曲面细分；
- 光栅化阶段：三角形设置、遍历以及微小三角形带来的额外开销；
- 像素处理阶段：像素着色器、纹理采样和后处理；
- 合并阶段：深度测试、模板测试、混合以及 Render Target 写入。

优化一个阶段后，瓶颈可能会转移到另一个阶段，所以不能只优化一次就结束，而需要重新测量。

## 可能的性能问题

### CPU 与提交

- CPU 剔除、排序和 Draw Call 提交过多；
- Shader、材质、纹理和混合状态频繁切换；
- 资源创建、销毁或内存分配造成卡顿；
- CPU 准备数据时等待 GPU，或为了读取 GPU 结果而阻塞。

Draw Call 主要增加 CPU、驱动和状态管理成本，不等价于 GPU 只执行了一次绘制。实例化、批处理和 GPU Driven 主要减少 CPU 提交与准备工作。

### 几何与网格

- 网格数据读取和顶点带宽过大；
- 顶点格式包含不必要的数据；
- 顶点缓存命中率低；
- 三角形数量过多或存在大量微小三角形；
- 曲面细分因子过高；
- 缺少网格简化、LOD 或剔除。

网格优化、索引共享和缓存排序，可能减少顶点处理和内存访问，但不一定减少三角形总数。

### 着色器和资源访问

着色器性能不仅取决于指令数量，还受到以下因素影响：

- 顶点、像素和计算着色器的执行数量；
- 纹理采样数量和纹理缓存命中率；
- Constant Buffer、Structured Buffer 和其他参数读取；
- 分支分歧、循环和线程占用率；
- 寄存器压力；
- 指令缓存和数据缓存命中率。

Buffer 或参数读取不是独立的固定管线阶段，它们通常表现为着色器中的访存延迟和带宽压力，而 GPU 可能通过切换其他线程来隐藏部分延迟。

### 像素、过度绘制与透明

- 屏幕分辨率过高；
- 像素着色器计算复杂；
- 纹理采样昂贵；
- Overdraw 过多；
- 透明物体重复覆盖同一像素；
- 后处理需要多次全屏采样；
- 微小三角形产生大量部分覆盖的辅助像素。

透明绘制还会受到排序、深度写入受限以及混合操作的影响，因此可能同时成为像素处理和合并阶段的瓶颈。

### Render Target、G-Buffer 与带宽

这里的 RT 如果指 Render Target，大量 Render Target 或 G-Buffer 可能增加：

- 每像素存储量；
- Render Target 写入和读取次数；
- 显存带宽；
- 缓存压力；
- 后续光照 Pass 的读取成本。

降低缓冲区精度或格式可以减少带宽和存储，但可能带来颜色、深度、法线或光照精度损失。G-Buffer 本身不是必然的性能问题，它是用额外带宽换取延迟光照和光源处理灵活性的方案。

## GPU/CPU 同步

常见的停顿来源包括：

- CPU 读取 GPU 端结果；
- CPU 等待 GPU 完成上一帧；
- GPU 在不同 Pass 之间等待资源写入完成；
- Barrier、UAV 同步或资源状态切换；
- 缓冲区或纹理访问产生的依赖。

尤其要避免不必要的 GPU 到 CPU 回读，因为它可能迫使 GPU 刷新管线，使原本的 CPU/GPU 并行变成相互等待。

## 正确的优化流程

```text
测量整帧时间
    ↓
判断 CPU 还是 GPU 瓶颈
    ↓
隔离应用、几何、光栅化、像素和合并阶段
    ↓
只优化当前瓶颈
    ↓
重新测量，确认瓶颈是否转移
```

最终需要区分的是：计算瓶颈、带宽瓶颈、缓存瓶颈、同步瓶颈和提交瓶颈。不能仅凭 CPU/GPU 利用率或 Draw Call 数量判断性能问题。
