# 图形处理单元

## 核心理解

### 1. GPU 通过线程切换隐藏内存访问延迟

GPU 访问纹理或显存时也可能需要等待。如果当前线程组正在等待，GPU 可以先切换去执行其他已经准备好的线程组，等数据返回后再继续执行原来的线程组。

```text
线程组 A 等待纹理数据
        ↓
GPU 切换执行线程组 B
        ↓
线程组 A 的数据返回后继续执行
```

这里的“切换”主要发生在不同线程组之间，不是说同一个线程可以随意中途切换去完成另一个完全无关的任务。

### 2. SIMD 与 SIMT

SIMD（Single Instruction, Multiple Data）强调数据级并行：一条向量指令同时处理多份数据。

```text
一条 ADD 指令：
a0 + b0、a1 + b1、a2 + b2、a3 + b3
```

SIMT（Single Instruction, Multiple Threads）更像是 GPU 提供的线程级编程模型。程序员可以编写许多看似独立的线程，GPU 再把它们分组，让它们执行相同的 Shader 代码，但处理不同的数据。

```text
SIMD：一条指令处理多个数据
SIMT：多个线程执行相同指令流，处理不同数据
```

现代 GPU 通常使用类似 SIMD 的硬件方式实现 SIMT，但二者不是完全相同的概念。

### 3. Warp / Wavefront 与相同指令

GPU 会把线程分组执行：

- NVIDIA 通常称为 Warp；
- AMD 通常称为 Wavefront；
- 不同硬件的线程组大小可能不同。

在同一执行时刻，一个线程组中的活跃线程通常执行同一条机器指令，而不是只执行“同类指令”。每个线程使用的输入数据可以不同。

```text
线程 0：用数据 0 执行 MUL
线程 1：用数据 1 执行 MUL
线程 2：用数据 2 执行 MUL
```

这里的并行来自：

```text
相同的指令 + 不同的数据
```

### 4. 分支发散与线程闲置

假设一个 Warp 中的线程执行：

```hlsl
if (value > 0)
{
    // 路径 A
}
else
{
    // 路径 B
}
```

如果一部分线程走 A，另一部分线程走 B，GPU 通常会使用活跃掩码分阶段执行：

```text
执行 A：走 A 的线程有效，走 B 的线程被屏蔽
执行 B：走 B 的线程有效，走 A 的线程被屏蔽
```

因此，分支发散的本质是：

> 同一个 Warp 共享指令流。当不同线程需要执行不同路径时，GPU 只能依次执行这些路径，暂时屏蔽不属于当前路径的线程。

这里的线程不是永远不能做其他工作。GPU 仍然可以切换到其他 Warp；只是当前 Warp 中没有走当前路径的 Lane，不能自动去处理另一个完全无关的任务。

如果整个 Warp 都走 A 或都走 B，就不会产生明显的分支发散。

### 5. 能否提前把 A、B 分成两批执行？

可以，但需要在执行 A、B 之前先完成分类和重新组织：

```text
原始数据
    ↓
判断哪些数据属于 A，哪些属于 B
    ↓
A 数据列表 ──→ 执行 A
B 数据列表 ──→ 执行 B
```

如果 CPU 事先知道分类结果，可以由 CPU 分别提交两个 Dispatch 或 Draw。

如果分类条件只能由 GPU 判断，则通常需要：

```text
Pass 1：GPU 判断并生成 A/B 列表
Pass 2：分别处理 A 列表和 B 列表
```

但分类、写入列表、原子操作、同步和重新调度本身也有成本。因此要比较：

```text
分支发散的代价
vs
分类、重排、同步和再次调度的代价
```

如果 A、B 只是很短的计算，直接让一个 Warp 依次执行两个分支可能更快；如果两个分支都很复杂，提前分类再分批执行可能更值得。

### 6. `float4` 不一定等于 SIMD 优化

```hlsl
float4 result = a * b + c;
```

它在语义上表示四个分量分别进行运算：

```text
result.x = a.x * b.x + c.x
result.y = a.y * b.y + c.y
result.z = a.z * b.z + c.z
result.w = a.w * b.w + c.w
```

`float4` 可能带来向量化计算，也可能主要改善数据布局和内存对齐，但不保证一定减少指令数量。现代 GPU 可能将它拆成多个标量运算。

还要区分两种并行：

```text
float4 的四个分量：一个线程内部的数据并行
Warp 中的多个线程：多个线程之间的 SIMT 并行
```

把几个参数打包成 `float4`，常见优势还包括：

- 更容易满足 16 字节对齐；
- 让 CBuffer 或 StructuredBuffer 的布局更规整；
- 方便一次读取一组相关参数。

但如果只使用其中一个分量，其他分量完全不用，打包后不一定更快。

### 7. 实例化、CBuffer 与 SIMD/SIMT 的关系

实例化本身不是 SIMD。实例化主要解决的是：

```text
一次 Draw 绘制多个相同 Mesh 的实例
```

GPU 随后会并行处理这些实例的顶点：

```text
线程 0：处理实例 0
线程 1：处理实例 1
线程 2：处理实例 2
```

这些线程执行相同的 Shader，但读取不同的实例数据，因此实例化很适合发挥 SIMT 并行能力。

CBuffer 也不是 SIMD。CBuffer 主要用于保存多个 Shader 调用共享的只读参数，例如：

```hlsl
float4x4 _ViewProjection;
float3 _CameraPosition;
```

所有线程可以读取同一个相机参数，但每个线程仍然要用自己的顶点执行矩阵乘法。

```text
CBuffer：所有线程共用的参数
Instance Buffer：不同实例各自的数据
SIMT：多个线程执行相同指令流
```

所以实例化和 CBuffer 的作用是组织数据、减少提交或重复绑定；真正的 SIMD/SIMT 并行发生在 GPU 执行这些 Shader 的时候。
