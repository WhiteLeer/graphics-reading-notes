# Shader Interface

## 章节内容

着色器接口实现抽象编程，允许运行时绑定实现而无需重新编译。

**作者**: Matt Pharr

### 核心概念

着色器接口实现抽象编程，允许运行时绑定实现而无需重新编译。

### 设计原则

- **模块化**：从可重用片段组合着色器
- **运行时灵活性**：运行时绑定实现无需重编译
- **零性能成本**：最终GPU代码仅在绑定解析后生成
- **类型安全**：编译时验证with运行时绑定

### 参数绑定机制

**运行时流程**：
1. 禁用自动编译：`cgSetAutoCompile(context, CG_COMPILE_MANUAL)`
2. 创建接口实现：`cgCreateParameter()`
3. 连接实现到参数：`cgConnectParameter()`
4. 编译最终程序：`cgCompileProgram()`

### 跨平台考虑

- 未定大小数组`[]`（运行时确定可变长度集合）
- 单个接口实例可跨同一上下文中的多个程序共享
- 支持层级组合（接口包含其他接口）
- 减少对预处理器指令和字符串代码生成的依赖


## 讨论与补充


### 1. 本章在解决什么问题

本章介绍 Cg 1.2 的 Shader Interface，目标是把光源、材质和纹理等功能抽象成可组合模块：

```text
接口描述功能
    -> 应用绑定具体实现
    -> 编译出最终 GPU Shader
```

例如一个材质 Shader 可以依赖抽象的 `Light` 接口，而不必为点光源、聚光灯、方向光和带阴影光源分别重写一份材质代码。

Cg Shader Interface 现在已经基本淘汰，真正值得保留的是模块化 Shader、材质节点树和“将抽象组合在编译期变成具体代码”的思想。

### 2. 为什么需要 Shader Interface

支持多种光源时，直接在 Shader 中写大量分支会越来越复杂：

```hlsl
if (lightType == POINT) { ... }
else if (lightType == SPOT) { ... }
else if (lightType == DIRECTIONAL) { ... }
```

也可以使用预处理宏，但会产生大量 Variant，并需要应用层手动拼接或管理代码。

Shader Interface 希望把差异隔离到独立实现中，让主材质只依赖统一接口。

### 3. 归一化例子

定义一个抽象接口：

```cg
interface Normalizer
{
    float3 nrm(float3 v);
};
```

主 Shader 只调用：

```cg
float3 L = normalizer.nrm(lightVector);
float3 N = normalizer.nrm(normal);
```

可以有两种实现：

```text
StdNormalizer
    -> 使用数学 normalize()

CubeNormalizer
    -> 通过预计算 Cube Map 查表
```

应用绑定具体实现后，Cg 再生成最终代码。

这不是传统 CPU 意义上的 GPU 虚函数调用。GPU 最终执行的仍然是已经确定的具体代码，主要代价发生在绑定、组合和编译阶段。

### 4. Light Interface

本章把不同光源抽象为：

```cg
interface Light
{
    float3 illuminate(float3 P, out float3 L);
};
```

接口接收着色点 `P`，输出入射方向 `L` 和光照强度。可以实现：

- PointLight；
- SpotLight；
- DirectionalLight；
- ShadowedSpotLight；
- ProjectiveLight；
- 不同衰减模型的光源。

材质 Shader 只遍历这些接口并累加结果，而不关心具体实现。

### 5. 不定长光源数组

Cg 还支持：

```cg
uniform Light lights[];
```

应用运行时设置数组长度并绑定每个光源实现。这样材质不需要写死光源数量。

现代对应的是：

- StructuredBuffer；
- ByteAddressBuffer；
- Uniform Buffer 数组；
- GPU Light List；
- Forward+、Tiled Lighting、Clustered Lighting 的光源索引列表。

不过现代管线通常先按空间或类型整理光源，再进行批量计算，不一定对异构光源直接做接口式遍历。

### 6. Material 和 Texture Interface

本章继续把纹理抽象为：

```cg
interface Texture
{
    float3 eval(float3 P, float3 N, float2 uv);
};
```

实现可以是：

```text
ImageTexture
    -> 采样 2D 贴图

ConstantTexture
    -> 返回固定颜色

ProceduralTexture
    -> 程序计算颜色

BlendTexture
    -> 混合其他 Texture
```

材质只调用：

```cg
Kd = diffuse.eval(P, N, uv);
```

不需要知道颜色来自普通贴图、常量还是程序纹理。接口还可以嵌套：

```text
BlendTexture
    ├─ ImageTexture
    ├─ ConstantTexture
    └─ ProceduralTexture
```

材质也可以封装其他材质，例如 `FogMaterial` 先调用基础材质，再叠加雾效。

### 7. 与现代 Shader Graph 的关系

本章思想和现代 Shader Graph、Maya Hypershade、3ds Max Material Editor 类似：

```text
Texture Node
    -> Multiply
    -> Lerp
    -> Fresnel
    -> BRDF
    -> Output
```

区别在于：

```text
Cg Interface：运行时连接接口实例，再编译
现代节点图：编辑节点图，生成 HLSL/GLSL 和 Shader Variant
```

现代 Unity 还会使用：

- `.hlsl` 函数库；
- `#include`；
- Shader Keyword；
- Shader Variant；
- Material 参数；
- StructuredBuffer。

### 8. 为什么现代光照不直接照搬这种方式

本章的示例让一个材质遍历一组异构光源。现代项目往往结合：

- Deferred Lighting；
- Forward+；
- Tiled Lighting；
- Clustered Lighting；
- GPU Light Culling；
- StructuredBuffer；
- 按光源类型或空间分组。

这样可以先构造光源列表，再让 Shader 批量处理，通常比每个像素动态处理大量异构接口更容易优化。

### 9. 工程上的结论

- Shader Interface 是 Shader 版的接口和抽象类思想。
- 它让光源、材质和纹理逻辑能够模块化组合。
- 它不会让 GPU 在每个像素中执行传统 CPU 意义上的虚函数调用。
- 主要成本在模块绑定、Shader 组合和编译阶段。
- Cg 机制已经过时，但材质节点树、Shader 模块化和编译期特化仍是现代引擎的基础思想。
