# GPU 作为通用并行处理器

## 章节内容

GPU通用计算工具包，将GPU作为通用并行处理器的早期探索。

**作者**: Ian Buck, Tim Purcell

### 核心概念

GPU通用计算工具包，将GPU作为通用并行处理器的早期探索。

### GPU通用计算的理由

**性能对比（2004年）**：
- GeForce FX 5900 Ultra：20亿次乘法/秒
- Pentium 4：~60亿次/秒
- GPU内存带宽：25.3 GB/sec
- CPU内存带宽：5.96 GB/sec

**性能增速**：
- GPU：每年增长24 Gigaflops
- CPU：每年增长0.65 Gigaflops

### 数据并行编程模型

**流处理架构**：
- 对数据流应用kernel函数并行处理
- 每个数据元素独立计算，无相互依赖
- "mandatory parallelism"约束决定可映射算法

**粒子系统示例**：
- 粒子位置存储为纹理
- 渲染四边形触发片段着色器
- 并行更新所有粒子

### GPU排序/搜索算法

**Bitonic Merge Sort（双调排序）**：
- O(log² n)复杂度的并行排序
- 每个渲染通道执行比较-交换阶段
- 100万元素需210个渲染通道

**Binary Search（二分搜索）**：
- 单通道片段程序实现
- 支持并行搜索多个grid cells
- 搜索100万元素<1毫秒

### 实现技巧

**Reduce操作**：
- 多通道缩小处理范围
- O(log n)复杂度规约（如求最大值）

**纹理坐标映射**：
- `convert1dto2d`函数
- 1D数组地址→2D纹理坐标

**Uniform Grid数据结构**：
- 通过排序+搜索构建空间加速结构
- 用于碰撞检测

### 性能与限制

**优势**：
- 减少CPU-GPU数据传输
- 数据保持在GPU显存中

**限制**：
- 片段着色器输出受限（单/多个四分量向量）
- 回读性能瓶颈（AGP 1x上传 vs 8x下载）
- 并非所有CPU算法适合GPU

> [!note] 历史意义
> 2004年的GPGPU先驱工作，为后来的CUDA/OpenCL奠定基础。


## 讨论与补充


### 本章主线

本章讨论如何把 GPU 从“专门绘制三角形的设备”扩展成通用并行计算设备。书中的实现建立在 2004 年的浮点纹理、Pbuffer 和片元 Shader 之上，具体 API 已经过时，但核心思想后来发展成了 Compute Shader、CUDA、DirectCompute、Vulkan Compute 和 Metal Compute。

GPU 计算的基本模型是：把数据组织成一条记录流，对每条记录执行同一个 Kernel，再得到新的数据流。

```text
输入数据流
    ↓
对每个元素执行相同的 Kernel
    ↓
输出数据流
```

### GPU 为什么适合这类问题

GPU 拥有大量并行执行单元，适合同时处理大量结构相似的数据。例如：

- 每个粒子都更新一次位置和速度；
- 每个网格单元都计算一次压力或温度；
- 每个像素都执行一次图像滤波；
- 每个元素都参与一次向量或矩阵运算。

这类问题的共同点是：单个元素的计算比较简单，元素数量很多，而且元素之间尽量独立。

### 书中的 GPU 粒子计算例子

粒子的速度、位置等状态可以存储在浮点纹理中。随后绘制一个覆盖整个目标纹理的四边形，让每个片元对应一个粒子状态：

```text
位置纹理、速度纹理
        ↓
全屏四边形 + 片元 Shader
        ↓
每个片元更新一个粒子
        ↓
新的位置纹理、速度纹理
```

这不是让片元 Shader 直接“画出粒子”，而是把光栅化过程借来执行一次并行计算。计算结束后，新的纹理还可以继续作为下一阶段的输入，或者被另一个渲染 Pass 用来绘制粒子。

### Ping-Pong Buffer

GPU 计算通常不能在同一次处理中既读取又安全地覆盖同一个输入资源，所以需要两份资源轮换：

```text
本帧：读取 Buffer A，写入 Buffer B
下帧：读取 Buffer B，写入 Buffer A
```

这就是 Ping-Pong 技术。现代实现中，纹理可以换成 StructuredBuffer、RWStructuredBuffer 或 ComputeBuffer，但“输入和输出分离，再交换”的思想仍然常见。

### 四种基本并行操作

#### Map

对每个元素独立执行同一个操作：

```text
output[i] = Kernel(input[i])
```

粒子更新、图像处理、逐元素向量运算都属于 Map。

#### Reduce

把大量元素逐步合并成较少的结果，例如求和、最大值、最小值和平均值。Reduce 通常需要多轮处理：第一轮把相邻元素合并，下一轮继续合并，直到得到最终结果。

#### Sort

并行排序可以用于粒子排序、透明物体排序、数据重排等。它通常由多个比较、交换或前缀和阶段组成，而不是一次 Shader 调用完成。

#### Search

把查找问题改写成并行比较，再通过 Reduce 或前缀和得到结果。例如判断某个值是否存在，或查找满足条件的元素位置。

### GPU 计算的限制

GPU 并不是 CPU 的简单替代品。算法需要满足一定条件：

1. 大量数据之间应尽量相互独立；
2. 任务最好能够拆成相同或相似的 Kernel；
3. 多阶段算法需要明确的阶段边界和资源交换；
4. 尽量避免 GPU 计算一步、CPU 读取一步的往返；
5. 如果算法存在大量分支、随机访问、同步或串行依赖，GPU 的优势会降低。

书中一个重要的工程结论是：如果计算结果还要继续参与 GPU 计算或渲染，就尽量让数据留在 GPU 上。GPU 到 CPU 的回读在当时尤其昂贵，现代硬件虽然有所改善，但同步和回读仍然可能造成流水线停顿。

### 与 GPU Driven 的区别

两者都使用 GPU 进行大量并行计算，但目标不同：

| 方向 | 主要任务 |
| --- | --- |
| GPU 通用计算 | 粒子、流体、图像、排序、模拟等数值计算 |
| GPU Driven | 剔除、LOD、生成绘制参数、间接绘制和渲染流程驱动 |

GPU Driven 可以使用本章的 Map、Reduce、Sort 等操作，但本章不等于 GPU Driven。更准确地说，GPU Driven 是通用 GPU 计算在渲染调度方向上的一种应用。

### 与现代 Compute Shader 的对应

书中的“全屏四边形 + 片元 Shader”在现代通常会改写成：

```text
输入：StructuredBuffer / Texture
        ↓
Compute Shader Dispatch
        ↓
输出：RWStructuredBuffer / RenderTexture
```

`Dispatch` 会启动许多线程组，线程根据自己的线程 ID 找到负责的数据元素。这样可以直接进行随机读写、使用共享内存、原子操作和显式同步，比旧式 GPGPU 更适合复杂算法。

### 我的理解

本章的关键不是“用两张纹理做计算”这一具体技巧，而是认识到：

> 只要问题能够拆成大量相似、可并行的数据元素，就可以尝试把它改写成 GPU Kernel。

因此，GPU 计算的实际流程通常不是一次 Shader 解决全部问题，而是：

```text
准备数据
  → 多个并行 Kernel
  → Buffer/纹理交换
  → 必要的同步或归约
  → 继续计算或用于绘制
```

这也解释了为什么 GPU 粒子、GPU 流体、GPU 剔除和后处理经常采用多个 Pass 或多个 Dispatch：每个阶段都尽量保持简单、规则，并把中间结果继续留在 GPU 上。

### 时代局限

本章写于 GPU 通用计算仍处于早期的阶段。Pbuffer、浮点纹理和片元 Shader 是当时绕过传统图形管线限制的办法，现在不应照搬代码和 API。应该保留的是数据并行、Map/Reduce、Ping-Pong、GPU 内部连续处理以及减少 CPU-GPU 往返这些思想。
