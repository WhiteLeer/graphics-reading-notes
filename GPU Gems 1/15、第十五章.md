# 逐像素光照中的可见性管理

## 章节内容

使用可见性管理技术优化多光源逐像素光照的性能，避免对不可见或不受影响的像素进行昂贵的光照计算。

**作者**: John O'Rorke

### 核心概念

使用可见性管理技术优化多光源逐像素光照的性能，避免对不可见或不受影响的像素进行昂贵的光照计算。

### 我的理解

**多光源问题**：

```
场景：100个动态光源
传统Forward Rendering：
- 每个像素计算100次光照
- 大量像素不受特定光源影响
- 浪费计算资源

示例：
像素P在角落：
- 距离光源L50: 100米（超出衰减范围）
- 仍然计算光照 → 结果为0 → 浪费！

性能：
100个光源 × 1920×1080像素 = 2亿次光照计算/帧
60 FPS → 120亿次/秒（不可行！）
```

### 解决方案：光体积（Light Volumes）

**核心思路**：仅对光源影响范围内的像素进行光照计算。

**1. 光源包围体定义**：

```cpp
// 计算光源影响半径
float ComputeLightRadius(PointLight light) {
    // 基于衰减公式反推半径
    // Attenuation = 1 / (constant + linear*d + quadratic*d²)
    // 当Attenuation < threshold (如0.01)时截断

    float threshold = 0.01;  // 1%亮度
    float maxIntensity = max(light.color.r, light.color.g, light.color.b);

    // 求解二次方程
    float radius = (-light.linear + sqrt(light.linear * light.linear
                    - 4 * light.quadratic * (light.constant - maxIntensity / threshold)))
                   / (2 * light.quadratic);

    return radius;
}

// 创建光源包围球
Sphere lightVolume;
lightVolume.center = light.position;
lightVolume.radius = ComputeLightRadius(light);
```

**2. 使用模板缓冲（Stencil Buffer）标记**：

```cpp
// Multi-pass光照渲染
void RenderLights(Scene scene, Camera camera) {
    // Pass 1: 渲染场景几何（仅环境光）
    glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT | GL_STENCIL_BUFFER_BIT);
    RenderSceneAmbient(scene);

    // Pass 2+: 为每个光源添加光照
    glEnable(GL_BLEND);
    glBlendFunc(GL_ONE, GL_ONE);  // 累加光照
    glDepthMask(GL_FALSE);        // 不写入深度

    for (Light light : scene.lights) {
        // ⭐ 关键：渲染光源包围球
        // 仅影响球内的像素

        // 2a. 使用模板缓冲标记受影响像素
        glEnable(GL_STENCIL_TEST);
        glStencilFunc(GL_ALWAYS, 1, 0xFF);
        glStencilOp(GL_KEEP, GL_KEEP, GL_REPLACE);
        glColorMask(GL_FALSE, GL_FALSE, GL_FALSE, GL_FALSE);

        RenderLightVolume(light);  // 渲染球体，标记模板

        // 2b. 仅在标记像素执行光照计算
        glStencilFunc(GL_EQUAL, 1, 0xFF);
        glStencilOp(GL_KEEP, GL_KEEP, GL_KEEP);
        glColorMask(GL_TRUE, GL_TRUE, GL_TRUE, GL_TRUE);

        RenderSceneWithLight(scene, light);  // 仅计算模板标记的像素

        glClear(GL_STENCIL_BUFFER_BIT);
    }
}
```

### Shader实现

```hlsl
// 顶点着色器：渲染光源包围球
float4x4 WorldViewProj;

float4 VS_LightVolume(float3 position : POSITION) : POSITION {
    // 将光源包围球顶点变换到屏幕空间
    return mul(float4(position, 1.0), WorldViewProj);
}

// 像素着色器：空（仅标记模板）
float4 PS_LightVolume() : COLOR {
    return float4(0, 0, 0, 0);  // 不写入颜色
}
```

```hlsl
// 像素着色器：逐像素光照（仅在模板标记区域执行）
sampler2D normalMap : register(s0);
sampler2D depthMap : register(s1);

float3 lightPos;
float3 lightColor;
float lightRadius;

float4 PS_PerPixelLight(float2 texCoord : TEXCOORD0, float3 viewRay : TEXCOORD1) : COLOR {
    // 1. 从G-Buffer重建世界位置
    float depth = tex2D(depthMap, texCoord).r;
    float3 worldPos = cameraPos + viewRay * depth;

    // 2. 计算光照方向和距离
    float3 L = lightPos - worldPos;
    float distance = length(L);
    L = normalize(L);

    // 3. 提前退出（在影响范围外）
    if (distance > lightRadius) {
        discard;  // 或return 0
    }

    // 4. 读取法线
    float3 N = tex2D(normalMap, texCoord).xyz * 2.0 - 1.0;
    N = normalize(N);

    // 5. 计算光照
    float NdotL = saturate(dot(N, L));
    float attenuation = 1.0 / (1.0 + 0.1 * distance + 0.01 * distance * distance);

    float3 lighting = lightColor * NdotL * attenuation;

    return float4(lighting, 1.0);
}
```

### 优化策略对比

**1. 无优化（Brute Force）**：
```
for each pixel:
    for each light:
        compute lighting  // 即使光照贡献为0

成本：O(Pixels × Lights)
```

**2. 光源包围体（Light Volumes）**：
```
for each light:
    mark affected pixels (stencil)
    for each marked pixel:
        compute lighting

成本：O(Lights × AffectedPixels)
AffectedPixels << TotalPixels
```

**3. 延迟着色（Deferred Shading）**：
```
Pass 1: Render G-Buffer (geometry only)
Pass 2:
    for each light:
        render light volume
        compute lighting for covered pixels

成本：O(Pixels + Lights × AffectedPixels)
```

### 与延迟着色的关系

**本章技术是Deferred Lighting的前身**：

```
2004年（本章）：
- Forward Rendering + Light Volumes
- 使用模板缓冲优化
- 每个光源仍需访问场景几何

2007年+（现代Deferred）：
- G-Buffer存储所有几何信息
- 光照Pass完全解耦
- 仅计算光照，无需几何数据
```

**核心相同点**：
- 将光照计算限制在影响范围内
- 使用包围体渲染
- 多Pass累加光照

### 深度优化：Scissor Rect

```cpp
// 进一步优化：计算光源包围球的屏幕空间矩形
Rect ComputeScissorRect(Sphere lightVolume, Camera camera) {
    // 投影光源包围球到屏幕空间
    Point2D projCenter = ProjectToScreen(lightVolume.center, camera);
    float projRadius = ComputeProjectedRadius(lightVolume, camera);

    // 计算屏幕空间矩形
    return Rect(
        projCenter.x - projRadius,
        projCenter.y - projRadius,
        projCenter.x + projRadius,
        projCenter.y + projRadius
    );
}

// 渲染时应用裁剪
glEnable(GL_SCISSOR_TEST);
glScissor(rect.x, rect.y, rect.width, rect.height);
RenderSceneWithLight(scene, light);
glDisable(GL_SCISSOR_TEST);
```

**效果**：
```
无Scissor：光源包围球覆盖100×100像素
使用Scissor：仅处理80×80实际影响的像素
→ 节省36%像素着色器调用
```

### 性能分析

**场景示例**：
```
分辨率：1920×1080 = 207万像素
光源数：50个点光源
平均影响：每个光源影响10%像素

无优化：
207万 × 50 = 1.035亿光照计算

Light Volumes优化：
207万 × 0.1 × 50 = 1035万光照计算
→ 减少90%计算量！
```

```
本章技术演变为：
```

## Part III - Materials 材质

## 讨论与补充


### 这章的问题

逐像素光照可以让材质和光照更精细，但光源数量增加后，渲染 Pass 和 Batch 数量也会增加。

例如一个场景有 14 个基础 Batch、3 个光源：

```text
环境/基础 Pass：14
每个光源的阴影 Pass：14
每个光源的光照 Pass：14

总计：14 + 3 × 14 × 2 = 98 个 Batch
```

GPU 处理单个三角形越来越快，但 CPU 提交 Batch、切换材质和准备渲染状态的速度不一定能按同样比例提升。因此这章的核心是：尽量不要提交不会影响最终画面的对象和 Pass。

### Batch 和 Draw Call

在 GPU Gems 的语境中，Batch 可以近似理解为一组渲染状态下提交的一组几何体，通常接近一次 Draw Call。

但在现代 Unity 中二者并不严格等价：

- 动态合批通常可以减少 Draw Call，但需要 CPU 转换顶点；
- 静态合批可能仍然提交多个 Draw Call，只是减少状态切换；
- GPU Instancing 用一次或少量 Draw Call 绘制同一 Mesh 的多个实例；
- SRP Batcher 通常不合并几何，也不保证减少 Draw Call，而是减少材质绑定和状态准备的 CPU 开销。

所以本章的 Batch 更应该理解为“CPU 需要独立准备和提交的渲染单元”，而不是简单的三角形数量。

### 四类可见性集合

#### 1. 摄像机可见集合 V

集合 V 表示主摄像机可能看到的对象，通常由以下方法得到：

- 视锥剔除；
- 遮挡剔除；
- 距离剔除；
- LOD；
- Layer/Culling Mask；
- 自定义逻辑。

环境 Pass 通常只绘制 V 中的对象。

#### 2. 光源可见集合 L

集合 L 表示当前光源能够看到或影响到的对象。

它不能直接复用摄像机可见集合，因为摄像机和光源的位置、方向、影响范围不同。

#### 3. 光照集合 I

真正需要执行当前光照 Pass 的对象应该同时满足：

```text
I = V ∩ L
```

如果一个物体不在摄像机画面中，即使光源照到它，也不需要为最终画面执行光照 Pass；如果摄像机看得到它，但光源完全影响不到它，也不需要执行当前光源的 Pass。

#### 4. 阴影投射集合 S

阴影集合不能简单使用 I：

```text
S ≠ V ∩ L
```

因为摄像机视野外的物体也可能把阴影投射到视野内。例如摄像机外的一棵树可能把阴影投射到摄像机能看到的地面。

因此 S 需要包括所有可能把阴影投射到当前可见区域的 Shadow Caster。

### 各层剔除的区别

```text
对象级：这个 Renderer 要不要提交？
三角形级：这个三角形是否需要光栅化？
片元级：这个片元是否被深度遮挡？
光源级：这个对象/区域可能受哪些光源影响？
阴影级：这个对象是否可能写入当前 Shadow Map？
```

背面剔除发生在三角形级，不等于片元光源剔除；Early-Z 主要丢弃被前方物体遮挡的片元，也不等于光源筛选。

### 多光源的几种实现

#### 传统 Forward

CPU 为每个对象分配一组可能影响它的光源：

```text
物体 A → Light 1、Light 3
物体 B → Light 2、Light 4、Light 5
```

Shader 只遍历对象对应的光源列表，而不是场景中全部光源。这种方案实现简单，但粒度较粗，同一物体内的所有片元通常共享同一组候选光源。

#### Deferred + 光源体积

延迟渲染先生成 G-Buffer，再绘制光源影响体积：

- 点光源使用球体；
- 聚光灯使用锥体；
- 只有光源体积覆盖的屏幕区域才执行对应光照。

这种方案避免了对整屏或所有物体执行每个光源的计算，但大量光源可能带来多个光源体积 Draw Call 和屏幕 Overdraw。

#### Tiled Lighting

把屏幕划分成二维 Tile，为每个 Tile 建立光源列表：

```text
Tile 0 → Light 1、Light 4
Tile 1 → Light 2
Tile 2 → Light 1、Light 2、Light 7
```

片元根据屏幕坐标找到所属 Tile，只遍历这个 Tile 的候选光源。

#### Clustered Lighting

在 Tile 的基础上进一步沿深度方向划分 Cluster，形成三维光源网格。它更适合处理屏幕同一位置上存在多个深度层、且光源分布范围复杂的场景。

Tiled/Clustered 并不是对每个片元重新遍历所有光源，而是提前建立空间到光源的映射，片元只访问自己的候选列表。

### Shadow Map 的生成和采样

Shadow Map 不是主摄像机深度图和光源深度图的直接比较结果。

#### 生成阶段

```text
筛选 Shadow Caster
        ↓
从光源视角绘制几何体
        ↓
执行深度测试
        ↓
保存光源视角下最近表面的深度
        ↓
得到 Shadow Map
```

方向光通常使用朝向场景的虚拟正交相机；聚光灯使用透视投影；点光源通常使用六个方向的 Cube Shadow Map。

对于同一个 Shadow Map Texel，深度测试会保留距离光源最近的表面。例如沿光源方向依次遇到深度为 5、8、20 的物体，Shadow Map 保存 5。后面的表面会在主渲染阶段被判断为处于阴影中。

因此 Shadow Map 不需要显式计算所有物体之间的两两遮挡关系，而是利用光源视角下的深度缓冲隐式保留第一层遮挡表面。

#### 主渲染阶段

主摄像机看到片元后，将它的世界坐标转换到光源空间：

```hlsl
lightPosition = LightViewProjection * float4(worldPosition, 1);
lightPosition /= lightPosition.w;

uv = lightPosition.xy;
receiverDepth = lightPosition.z;
shadowDepth = ShadowMap.Sample(uv);

inShadow = receiverDepth - bias > shadowDepth;
```

比较的是：

```text
当前片元的光源空间深度
vs
Shadow Map 中保存的最近深度
```

通常不需要主摄像机深度图。主摄像机深度只有在屏幕空间阴影、世界坐标重建等特殊方案中才可能参与。

### 哪些对象会进入 Shadow Pass

不是所有场景对象都默认参与当前 Shadow Map。通常需要满足：

1. Renderer 和 GameObject 处于启用状态；
2. Layer 被光源的 Culling Mask 包含；
3. Renderer 开启 Cast Shadows；
4. 材质拥有可用的 ShadowCaster Pass；
5. 对象位于当前光源、Cascade 或阴影剔除范围内；
6. 没有被 Shadow Distance、LOD 或其他规则排除。

Alpha Clip 材质还需要在 ShadowCaster Pass 中执行相同或相近的裁剪，否则颜色 Pass 中透明的区域可能错误地投射整块阴影。

对于方向光 CSM，每个 Cascade 都有自己的阴影视锥或包围范围。同一个物体可能需要被渲染到多个 Cascade 中。

主摄像机视锥外的对象仍可能进入 Shadow Pass，只要它有可能把阴影投射到主摄像机可见区域；但完全不可能影响当前 Shadow Map 的对象会被剔除。

### Unity 中的整体流程

```text
主摄像机 Culling
    ↓
主颜色/深度/光照 Pass

每个光源或 Cascade 的 Shadow Culling
    ↓
ShadowCaster Pass
    ↓
Shadow Map
    ↓
主渲染片元采样 Shadow Map
```

因此阴影剔除发生在 Shadow Map 绘制之前，而不是绘制完成之后。主摄像机剔除和 Shadow Map 剔除也是两套不同的剔除过程。

### 工程上的核心认识

本章最终可以归纳为：

```text
摄像机剔除：减少主渲染对象
光源剔除：减少不必要的光照计算
阴影剔除：减少 Shadow Map 中的投射物
Tile/Cluster：减少每个片元遍历的光源
Scissor/光源体积：减少无效屏幕区域
Early-Z：减少被遮挡片元的昂贵着色
```

它们不是同一个“剔除”，而是分别作用在对象、三角形、片元、光源和 Shadow Map 等不同层次。
