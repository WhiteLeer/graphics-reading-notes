# EXR\HDR

## 章节内容

工业光魔开发的高动态范围（HDR）图像格式。

**作者**: Florian Kainz, Rod Bogart, Drew Hess (ILM)

### 核心概念

工业光魔开发的高动态范围（HDR）图像格式。

### 核心特性

**数据精度**：
- 16位浮点"half"精度色彩值
- 支持多图像通道with不同数据类型
- 无损压缩选项（PIZ、ZIP、RLE）
- 完整C++ API with RGBA接口

### HDR数据存储

**动态范围**：
- 保存超出典型显示限制（0.0-1.0）的亮度信息
- Half精度：5.96×10⁻⁸ 到 65,504.0
- 约一万亿比一的动态范围

**处理优势**：
- 压暗过曝图像时保持自然效果
- 传统格式压暗产生灰色伪影

### 与传统格式区别

**JPEG/标准格式**：
- 裁剪亮值
- 丢失过曝数据

**OpenEXR**：
- 保留过曝数据
- 后期处理保持自然

### 工业应用

- 视觉特效合成和图像处理
- 3D渲染环境映射
- 景深和运动模糊效果
- 色彩校正工作流
- 实时GPU渲染with正确线性色彩空间

## 讨论与补充


### 1. OpenEXR 解决什么问题

OpenEXR 是 Industrial Light & Magic 开发的 HDR 图像文件格式。它的重点不是提供某个渲染效果，而是保存 GPU 或离线渲染产生的高动态范围、线性颜色和额外渲染通道。

需要区分几个概念：

```text
HDR       -> 数据具有较大动态范围
EXR       -> 一种文件存储格式
RGBA16F   -> GPU 中的浮点纹理或渲染目标格式
```

因此，并不是所有 HDR 都使用 EXR：

- 影视、离线渲染和中间合成中经常使用 EXR；
- HDR 全景图也可能使用 `.exr` 或 `.hdr`；
- HDR 视频会使用 HDR10、HLG、PQ 等视频编码；
- 游戏运行时通常把 EXR 资源转换为 GPU 纹理格式，而不是直接把 EXR 当作实时渲染目标。

### 2. 为什么 PNG/JPG 不适合作为 HDR 中间结果

普通 LDR 图像一般把颜色限制在：

```text
0.0 ~ 1.0
```

如果 HDR 亮度是：

```text
1.5、5.0、100.0
```

提前存入 LDR 文件时，可能全部被截断为 `1.0`。这样强度差异就永久丢失了。

例如：

```text
HDR 高光 20.0
    -> Clamp
    -> LDR 高光 1.0
```

之后再把图像变暗，HDR 仍能保留不同高光的层次，而 LDR 无法恢复原始信息。

这对以下效果尤其重要：

- Bloom；
- 景深；
- 运动模糊；
- 高光扩散；
- 曝光调整；
- Tone Mapping；
- HDR 环境光照。

例如高光在 Bloom 前被 Clamp，就会导致扩散后的光斑过暗，因为原本的亮度能量已经被截掉。

### 3. OpenEXR 中保存的数据

一个 OpenEXR 文件通常包含 Header 和像素通道：

```text
Header
  - 分辨率
  - 裁剪区域
  - 通道描述
  - 压缩方式
  - 像素比例
  - 额外元数据

Pixel Channels
  - R、G、B、A
  - Z 深度
  - Normal
  - Motion Vector
  - Material ID
  - 其他 AOV
```

OpenEXR 的重要特点是支持额外通道，而且不同通道可以使用不同数据类型。例如：

```text
R、G、B、A -> half
Z           -> float
MaterialID  -> 整数或其他适合的数据格式
```

所以它既可以存最终颜色，也可以存影视合成和调试所需的中间渲染数据。

### 4. `half` 半精度浮点

OpenEXR 常使用 16-bit 浮点 `half`，结构类似：

```text
1 bit  符号
5 bit  指数
10 bit 尾数
```

它比 8-bit 整数有更大的动态范围，比 32-bit `float` 占用更少。GPU 中常见的 `R16G16B16A16_FLOAT` 与它的思想接近。

它适合：

- HDR 颜色；
- 中间渲染结果；
- GPU 与文件之间的数据交换；
- 需要高于 8-bit 但不想使用完整 32-bit 的场景。

但 `half` 不是无限精度，在极大或极小数值范围内仍会出现精度不足。

### 5. 线性空间和 sRGB 空间

OpenEXR 通常保存线性颜色。在线性空间中，数值与相对光强成比例：

```text
0.5 -> 约 0.5 倍光强
1.0 -> 约 1 倍光强
2.0 -> 约 2 倍光强
```

因此光照、混合和图像处理一般在线性空间进行：

```text
sRGB 贴图
    -> 采样时解码为 Linear
    -> Shader 光照和颜色计算
    -> 线性 HDR 后处理
    -> Tone Mapping
    -> sRGB 编码
    -> 显示器
```

如果纹理被标记为 sRGB，GPU 采样时通常会自动完成：

```text
sRGB -> Linear
```

最终输出到 sRGB 目标或显示阶段时，再进行反向编码。具体自动转换方式取决于渲染 API 和目标格式，但概念上必须区分解码和编码。

Alpha 通常不做 sRGB 解码，因为它表示覆盖率、透明度或混合权重，而不是显示颜色：

```text
RGB -> sRGB 解码
A   -> 原样读取
```

### 6. 各种颜色计算应该在哪个空间

涉及光能的计算通常在线性空间进行：

- 漫反射和高光；
- 环境光；
- Alpha 混合；
- Bloom；
- 模糊；
- 抗锯齿；
- 曝光；
- Tone Mapping。

Tone Mapping 通常接收线性 HDR：

```text
Linear HDR -> Tone Mapping -> 0~1 范围的显示颜色
```

但 Tone Mapping 输出后通常还需要经过 sRGB 编码，因此 Tone Mapping 不是 Gamma 或 sRGB 校正。

### 7. LUT 的颜色空间问题

不能简单说所有 LUT 都在线性空间使用，要看 LUT 的用途和生成约定。

#### 7.1 数据 LUT

材质参数、Mask、Roughness、Metallic、Normal 等不是给人眼显示的颜色，通常按线性数据读取，不应误标记为 sRGB。

#### 7.2 颜色校正 LUT

Color Grading LUT 作用于画面颜色。它可能被设计为接收：

- 线性颜色；
- Tone Mapping 前的 HDR 颜色；
- Tone Mapping 后的 0~1 显示颜色；
- Log 或其他工作颜色空间。

因此必须让 LUT 的输入空间和生成时的约定一致。实时管线中常见流程是：

```text
HDR 线性颜色
 -> Exposure / Tone Mapping
 -> Color Grading LUT
 -> sRGB 编码
```

但不同引擎可能调整调色与 Tone Mapping 的顺序。

如果 LUT 是按照 `[0,1]` 显示颜色制作的，就不能直接把 HDR 中的 `5.0` 输入进去；需要先经过适当的曝光和动态范围压缩。

### 8. OpenEXR 的压缩

章节中介绍了几种无损压缩：

- `PIZ`：适合复杂照片，压缩率通常较好；
- `ZIP`：解压速度较快；
- `RLE`：适合大面积相同颜色的图像；
- 未压缩：文件较大，但读写速度可能最快。

它们属于无损压缩，不像 JPG 那样为了体积引入明显的有损伪影。

### 9. 工程上的理解

- OpenEXR 是 HDR 和多通道中间数据的存储格式，不是某种后处理效果。
- HDR 渲染目标通常使用浮点纹理，运行时不一定直接使用 EXR 文件。
- 颜色通常在采样时从 sRGB 解码到线性空间，在 Shader 和后处理中使用线性 HDR，最后才编码回 sRGB。
- Tone Mapping、Bloom、景深和运动模糊等依赖真实亮度范围的效果，应尽量在 HDR 阶段执行。
- LUT 的空间取决于其输入输出约定；不能把所有 LUT 都默认看成线性 LUT。
