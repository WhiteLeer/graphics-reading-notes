# 将渲染上下文组织成系统

## 章节内容

本章讨论把 Shader 集成到应用程序中，使用 effect/CgFX 一类的文件和接口组织 Shader、渲染状态、参数及多个 Pass。

### Shader 与应用集成

- 用 effect 文件组织顶点 Shader、像素 Shader、渲染状态和多个 Pass。
- 通过参数、接口和语义连接应用程序与 Shader。
- 让应用程序在不把所有 Shader 细节硬编码到 CPU 代码中的情况下使用不同效果。

## 讨论与补充


### 本章主线

本章讨论的重点不是某个具体 Shader API 的写法，而是：如何把 Shader、材质、场景数据、顶点格式、渲染状态和渲染上下文组织成一个稳定的数据驱动渲染系统。

书中以 CgFX 一类的 effect file 为例，把顶点 Shader、像素 Shader、渲染状态和多个 Pass 组合起来。这个具体文件格式已经过时，但它要解决的问题仍然存在：应用程序不能把所有 Shader 参数和渲染规则硬编码在 CPU 代码中，而应该通过明确的数据契约和反射/语义来连接应用与 GPU。

### 我的理解与修正

#### Feature、RenderPass 和 Shader Pass 不是同一层

- `Renderer Feature` 是向渲染器注册功能的扩展入口。
- `ScriptableRenderPass` 是 Feature 实际注入的一个渲染步骤，拥有 `RenderPassEvent`，例如 `BeforeRenderingOpaques`、`AfterRenderingOpaques`。
- ShaderLab 中的 `Pass` 是 Shader 内部的一组 GPU 状态和着色器程序。
- 一个 RenderPass 可以通过 `DrawRenderers` 选择并绘制很多物体；它不是“一个物体对应一个 RenderPass”。

因此，普通场景物体并不会各自自动生成一个 RenderPass。通常是内置的透明/不透明 Draw Pass 统一遍历当前相机可见物体，再在其中产生多个 Draw Call。

#### RenderPipelineAsset、管线实例、Renderer Data 和 RenderingData

- `RenderPipelineAsset` 是项目配置资源，同时负责创建运行时的 `RenderPipeline` 实例。
- 运行时管线实例负责每帧执行 `Render()`。
- `Renderer Data` 是渲染器的配置资源，通常保存 Renderer Feature 列表和相关资源。
- `RenderingData` 是某一帧、某个相机的运行时数据结构，保存相机、光源、可见对象和光照等信息。

可以把它们理解为：Asset/Data 负责“配置和生成规则”，Pipeline/RenderingData 负责“当前运行和当前帧的数据”。

#### RenderPassEvent、Queue、LightMode 的职责

这三个标签看起来都像“排序依据”，但实际上属于不同层级：

| 概念 | 所属层级 | 作用 |
| --- | --- | --- |
| `RenderPassEvent` | RenderPass | 决定这个渲染步骤大致插入管线的哪个阶段 |
| `Queue` | SubShader/Material | 表示物体属于不透明、透明等渲染队列 |
| `LightMode` | Shader Pass | 给 Pass 起一个供渲染器匹配的标签 |
| `RenderType` | SubShader/Material 分类标签 | 用于分类、过滤、替换渲染等，不等价于 Queue |

物体本身不会因为写了 `Queue=Opaque` 就得到一个名为“Opaque”的 RenderPassEvent。实际情况是：渲染器创建一个拥有 `BeforeRenderingOpaques` 的不透明 Draw Pass，并用 `RenderQueueRange.opaque` 过滤出 Queue 属于不透明范围的物体。

在标准 URP 中，典型映射是：

```text
不透明 Draw Pass       -> BeforeRenderingOpaques       + opaque queue range
透明 Draw Pass         -> BeforeRenderingTransparents + transparent queue range
深度预处理 Pass        -> BeforeRenderingPrePasses     + opaque queue range
```

所以 `Queue=Opaque` 的物体通常在内置不透明 Pass 中绘制，而不是自己携带一个 `BeforeRenderingOpaques`。

#### LightMode 是选择条件，不是排序层

`DrawRenderers` 会带有一个 `ShaderTagId` 列表，例如 `UniversalForward`、`SRPDefaultUnlit`。它会在符合当前过滤条件的物体中，查找匹配这些标签的 Shader Pass。

因此，下面两件事必须同时满足：

1. 物体的 SubShader/Material 通过 Queue、Layer 等过滤条件；
2. Shader 中的 Pass 的 `LightMode` 被当前 Draw Pass 的 `ShaderTagId` 列表选中。

只写 `Queue=Opaque`，并不能让自定义的 `LightMode=AAA` 自动执行。如果当前 Draw Pass 没有把 `AAA` 放入 ShaderTagId 列表，这个 Pass 就不会被选中。需要使用内置标签，或者编写自定义 Renderer Feature/RenderPass 来绘制这个标签。

没有显式 `LightMode` 的 Pass，在 URP 中通常按 `SRPDefaultUnlit` 处理；但自定义管线可能有自己的标签约定，不能把 URP 的默认行为直接套到所有 SRP 上。

#### 一个具体例子

假设场景中有 A、B、C、D：

- A、B 是不透明，C、D 是透明；
- A、C 没有显式 LightMode；
- B 使用 `LightMode=TEST_B`，D 使用 `LightMode=TEST_D`。

如果内置不透明/透明 Draw Pass 只搜索默认标签，那么 A、C 可能被绘制，B、D 不会因为自定义标签而自动出现。要绘制 B、D，必须让某个 Draw Pass 的 ShaderTagId 列表包含 `TEST_B`、`TEST_D`，并且它的 Queue 过滤范围还要覆盖相应物体。

这也说明了：

```text
RenderPassEvent 决定“什么时候执行这个 Draw Pass”
Queue            决定“哪些物体有资格进入这个 Draw Pass”
LightMode        决定“物体中的哪个 Shader Pass 被这个 Draw Pass 选中”
```

#### 同一 RenderPassEvent 下的顺序

多个 Feature 可以来自不同脚本。它们通常都只是声明一个大致阶段；同一 `RenderPassEvent` 下的确切顺序取决于渲染器收集并 Enqueue 这些 Pass 的顺序，常见情况下与 Renderer Data 中 Feature 的顺序和 `AddRenderPasses` 的执行顺序有关，但不应把同一事件当成严格的细粒度排序保证。

如果 Pass 之间存在资源读写依赖，现代 RenderGraph 还可能根据依赖关系进行合并或调整。需要稳定顺序时，应使用不同的事件、明确的资源依赖，或在同一个 Feature/Pass 中显式组织顺序。

### 书中的 effect file 与现代 Unity 的对应关系

| 本章概念 | 现代 Unity 中的近似对应 |
| --- | --- |
| Effect file | ShaderLab + HLSL/Shader Graph + Shader 资源 |
| Technique | Shader Pass/变体选择、材质与渲染上下文组合 |
| Pass | ShaderLab Pass，以及 Renderer 对它的 Draw 调度 |
| Render state | `Blend`、`ZTest`、`ZWrite`、`Cull` 等状态 |
| 全局变量/语义 | 全局参数、每物体数据、材质属性、CBUFFER、属性 ID |
| Annotation | Shader 属性元数据、Inspector 描述、编辑器扩展 |
| Context | LightMode/ShaderTagId、Renderer Feature、关键字和变体 |
| Shader variation | Shader Keywords、变体、HLSL 条件编译 |
| Fallback | SubShader fallback、变体回退、不同管线实现 |

也就是说，CgFX 文件格式虽然已经不是 Unity/UE 项目的主流，但“把渲染所需的一组资源、状态和 Pass 数据化”的思想仍然体现在 ShaderLab、材质、Shader 变体和 SRP 中。

### 从工程角度得到的结论

1. CPU 渲染器和 Shader 之间需要稳定的数据契约：场景数据、材质数据、顶点数据和渲染上下文要分别约定来源与语义。
2. Shader 参数最好通过属性名、语义、属性 ID 或反射信息连接，而不是在大量 CPU 代码中散落硬编码。
3. 应用程序应根据 Shader 实际需要准备顶点格式和数据，避免所有物体都携带不使用的顶点属性，减少带宽和缓存压力。
4. 一个材质可能对应多个变体或多个 Pass；最终是否绘制，不只取决于 Queue，还取决于当前 Renderer Pass 的过滤范围、ShaderTagId、材质状态和平台能力。
5. 本章的具体 API 已经过时，但它提醒我们：渲染管线本质上是“数据准备 + Pass 选择 + 状态绑定 + Draw 调度”，并不是把一个 Shader 文件直接交给 GPU 就结束了。

### 与当前 BXRP 项目的对应

当前项目不是标准 URP，而是自定义 BXRP，因此不能直接假设它存在 `Renderer Feature` 和 `RenderPassEvent`。项目自己的流程是由 `BXRenderPiepline.Render()`、`BXMainCameraRender` 和 `BXRenderFeatureStep` 组织的：

- `BeforeRender`、`BeforeOpaque`、`AfterOpaque`、`BeforeTransparent` 等是项目自定义的阶段；
- `BXMainCameraRender` 用不同的 `ShaderTagId` 列表分别绘制不透明、AlphaTest、透明和特殊 Pass；
- `Queue`/`RenderType` 主要负责过滤和分类，`BXForwardBase`、`BXForwardBaseAlphaTest` 等 `LightMode` 标签负责让特定 Shader Pass 被选中；
- 多个组件处于同一阶段时，实际顺序取决于 BXRP 收集组件并执行的顺序，不是由 LightMode 自动决定。

因此，阅读项目代码时应先确认它是 URP 还是自定义 SRP，再确认“阶段、过滤条件、ShaderTagId、Shader Pass”这四层分别由哪里控制。
