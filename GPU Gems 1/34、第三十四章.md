# 初始语义和实际语义不同

## 章节内容

本章讨论把硬件着色和实时预览集成进 Cinema 4D 等 DCC 应用，以及 DCC 数据、材质和渲染功能如何映射到 GPU 渲染流程。

### 章节主题

- 将硬件着色接入 Cinema 4D 等 DCC 应用。
- 处理 DCC 场景、材质和 GPU 渲染数据之间的转换。
- 通过插件和实时预览把硬件渲染纳入原有工作流。

## 讨论与补充


### 1. 本章的定位

本章讨论如何给一个原本主要依赖 CPU 和离线渲染的 DCC 软件增加 GPU 实时预览和硬件加速渲染。案例是 Cinema 4D 的 `C4Dfx` 插件。

它实现的效果包括：

- Phong 高光；
- Bump Mapping；
- 环境贴图；
- 阴影；
- 聚光灯边缘；
- GPU 实时预览；
- 简单的硬件离线序列渲染。

现代 Unity Scene View、Unreal Viewport、Blender Eevee 和 Houdini 的实时视图，本质上也属于同类需求。

### 2. DCC 数据不能直接交给 GPU

Cinema 4D 的材质和场景可能包含：

- 位图；
- 视频；
- 程序纹理；
- 凹凸图；
- 环境贴图；
- 特殊高光；
- 动画参数。

这些内容不一定能直接对应 GPU Shader，因此插件需要建立转换层：

```text
Cinema 4D 材质
    -> GPU Shader 参数和纹理

程序纹理
    -> 烘焙纹理

Bump 高度图
    -> Normal Map

球面环境图
    -> Cube Map

复杂高光函数
    -> 预计算 LUT
```

### 3. 几何数据转换

Cinema 4D 中可能使用参数曲面、样条、Metaball、四边形和三角形网格。GPU 则需要明确的顶点和索引：

```text
参数曲面 / Metaball
    -> Tessellation
    -> Vertex Buffer + Index Buffer
    -> GPU 绘制
```

同时要准备：

- Position；
- Normal；
- Tangent；
- Binormal；
- UV；
- 其他顶点属性。

法线可以由邻接面法线平均得到；切线和副切线则需要根据 UV 方向和邻域顶点进行估计。对于不规则、已经三角化的网格，UV 方向不一定天然存在，因此通常是近似计算。

### 4. 材质转换

插件把 DCC 材质近似转换为 GPU 材质：

```text
Diffuse Map
    -> GPU 2D Texture

Bump Map
    -> 根据高度差生成 Normal Map

Environment Map
    -> Cube Map

Specular Model
    -> 预计算 1D LUT
```

这不是逐项保证完全一致的翻译，而是通过纹理、LUT 和实时 Shader 重新构造相似外观。

### 5. 阴影和多光源

阴影使用传统阴影贴图：

```text
从光源视角渲染深度
    -> Shadow Map
    -> 主相机渲染时比较当前深度
    -> 判断是否在阴影中
```

多个光源可以使用多 Pass：

```text
Pass 1 -> 光源 A
Pass 2 -> 光源 B
Pass 3 -> 光源 C
```

但每个 Pass 会重复执行顶点、材质、纹理和片元计算。现代 Deferred、Forward+、Tiled、Clustered Lighting 和 Shadow Atlas 已经改善了这个问题。

### 6. 场景线程和资源管理

为了让用户继续编辑场景，插件可以让预览或离线渲染在独立线程运行。但渲染线程不能直接读取用户正在修改的对象，否则可能出现资源失效。

因此需要：

```text
用户场景
    -> Clone / Snapshot
    -> 渲染线程使用副本
```

同时要缓存 Shader、纹理和 Render Target，因为编译 Shader、生成纹理和上传 GPU 资源的启动成本可能很高。

### 7. 运行时的不同阶段

实际转换通常不是一次性完成的：

```text
DCC 文件
    -> 编辑器导入
    -> 引擎资产
    -> 构建/平台转换
    -> 运行时加载
    -> GPU 资源
```

静态模型的 Mesh、UV 和贴图可以长期不变，但相机、物体 Transform、骨骼矩阵、灯光列表、剔除结果和绘制命令仍可能每帧更新。

用户通常不需要手动实现这些步骤，因为 Unity、Unreal 等引擎已经在 Importer、Asset Pipeline、Build Pipeline、Shader Compiler 和 Resource Loader 中自动完成了它们。

### 8. 本章没有解决什么

本章只是通过 Cinema 4D 插件案例说明：

```text
DCC 中的场景数据
    !=
目标引擎中的运行时数据
    !=
GPU 最终读取和执行的数据
```

它没有提出一个适用于所有 DCC、所有引擎和所有材质系统的通用转换标准。具体实现仍然需要处理：

- 几何展开；
- 材质近似；
- 纹理烘焙；
- 坐标和颜色空间转换；
- 参数语义映射；
- 资源上传；
- 平台 Shader 编译。

### 9. 工程上的结论

- DCC 的 GPU 预览本质上是建立一套“离线材质到实时材质”的适配层。
- 这层适配不仅包含 Shader，还包括 Mesh、纹理、灯光、相机、动画、坐标系和资源生命周期。
- 几何数据迁移通常比较稳定，材质和 Shader 更容易出现语义差异。
- 程序纹理、复杂高光和离线效果常需要烘焙、LUT 或实时近似。
- 本章的 CgFX/OpenGL 实现已经过时，但 DCC 数据到引擎/GPU 数据之间存在转换层这一事实仍然成立。
- 本章应理解为一个历史性的 DCC GPU 预览集成案例，而不是完整的跨 DCC/引擎迁移方案。
