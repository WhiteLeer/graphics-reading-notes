# 图像处理框架

## 章节内容

集成GPU和CPU的图像处理框架，采用三层设计模式。

**作者**: Frank Jargstorff

### 核心概念

集成GPU和CPU的图像处理框架，采用三层设计模式。

### 核心架构

**三层设计**：
- **源操作符(SourceOperator)**：生成图像数据
- **滤波器(ImageFilter)**：继承源和汇，执行处理
- **汇操作符(SinkOperator)**：消费最终结果

**数据模型**：
- "拉取"数据模型
- 结果节点主动从输入获取数据

### GPU/CPU协作

**分工**：
- GPU：像素级操作
- CPU：流程控制

**技术细节**：
- 屏幕对齐四边形渲染至不可见缓冲区
- 16位浮点（half）精度平衡性能与精度
- WGL扩展实现渲染到纹理
- 数据无需在内存间移动

### 滤波链设计

**递归脏检查**：
- 追踪上游参数变化
- 图像使用引用计数管理
- Image代理Buffer对象

**Cg实现**：
- 单个滤波器通过片元着色器实现不同效果

### 性能考虑

**加速效果**：
- 十倍加速已被测量（合理的图像处理问题）

**要求**：
- 需饱和CPU和GPU工作负荷
- 硬件限制（纹理尺寸、显存）需通过分块等工程方案克服

## Part V - Performance and Practicalities 性能与实践

## 讨论与补充


### 1. 本章真正讨论的内容

这一章不是在介绍某一种图像效果，而是在讨论：

> 如何把多个 GPU 图像处理步骤组织成可复用、可连接、可缓存的处理流水线。

书中的实现使用 OpenGL、Cg、PBuffer 和旧式的 C++ 对象管理。具体 API 已经过时，但思想对应现代引擎中的后处理链、Render Pass 和 Render Graph。

一个 Bloom 链条可以写成：

```text
Camera Color RT
    -> Bright Pass
    -> Downsample
    -> Horizontal Blur
    -> Vertical Blur
    -> Combine
    -> Tone Mapping
    -> Back Buffer
```

### 2. Source、Filter、Sink

书中把图像处理网络抽象为三类节点。

#### Source

产生图像数据，例如：

- 从磁盘加载 EXR；
- 摄像机输出的场景颜色；
- 视频帧；
- 深度、法线或其他输入纹理。

#### Filter

接收输入图像并产生输出图像，例如：

- Blur；
- Tone Mapping；
- Color Correction；
- Edge Detection；
- Resize；
- Bloom Extract。

#### Sink

消费最终图像，例如：

- 显示到屏幕；
- 保存为 EXR；
- 输出到视频编码器。

结构可以表示为：

```text
Source -> Filter -> Filter -> Sink
```

复杂时就是一张图：

```text
                 -> Blur -> Bloom
Scene Source ----|
                 -> Tone Mapping -> Display
```

### 3. GPU 图像不是 CPU 像素数组

书中的 `Image` 更像 GPU 资源句柄，而不是存储在 CPU 内存中的逐像素数组：

```text
Image
  -> GPU Texture
  -> Render Target
  -> 尺寸与格式
```

一个 Filter 的基本执行过程是：

```text
1. 获取输入 Image
2. 创建或复用输出 Render Texture
3. 将输入 Image 绑定为纹理
4. 将输出设置为 Render Target
5. 绘制覆盖整个屏幕的 Quad
6. Fragment Shader 采样输入并计算
7. 得到输出 Image
```

也就是现代渲染中的全屏 Pass：

```text
Input Texture
      -> Full-screen Triangle / Quad
      -> Fragment Shader
      -> Output Render Texture
```

整个过程尽量保持在 GPU 显存中，而不是：

```text
GPU -> CPU 数组 -> CPU 处理 -> GPU
```

后者会造成同步、带宽和延迟问题。

### 4. 不要混淆 Shader Pass、Render Pass 和 Renderer Feature

这是理解现代 Unity/SRP 时最容易混淆的部分。

#### 4.1 Shader Pass

Shader 文件中的一个 `Pass` 描述一次绘制所使用的 Shader 和渲染状态：

```shaderlab
SubShader
{
    Pass { /* 一次绘制 */ }
    Pass { /* 另一次绘制 */ }
}
```

多个 Shader Pass 通常表示同一个物体可能被绘制多次，但不一定代表后处理链。

#### 4.2 Render Pass

Render Pass 是渲染流程中的一个步骤，例如：

```text
场景绘制
 -> Bloom 提取
 -> 横向模糊
 -> 纵向模糊
 -> 合并
 -> Tone Mapping
```

每一步可能执行一次全屏绘制，也可能使用 Compute Shader。

#### 4.3 Renderer Feature

在 Unity URP 中，`ScriptableRendererFeature` 是把自定义 Render Pass 接入 Renderer 的扩展入口：

```text
Renderer Feature
    -> 创建并注册 Render Pass
        -> Render Pass 使用 Material / Shader
```

例如：

```csharp
class MyFeature : ScriptableRendererFeature
{
    MyPass pass;

    public override void Create()
    {
        pass = new MyPass();
    }

    public override void AddRenderPasses(
        ScriptableRenderer renderer,
        ref RenderingData data)
    {
        renderer.EnqueuePass(pass);
    }
}
```

因此 Feature 不是替代 Render Pass，而是调度和接入层。一个 Feature 可以创建一个或多个 Render Pass。

### 5. 现代 Unity 中的对应关系

| GPU Gems 1 | 现代 Unity / SRP |
|---|---|
| `SourceOperator` | 场景颜色、深度、外部纹理 |
| `ImageFilter` | Render Pass / Compute Pass |
| `SinkOperator` | Back Buffer、文件或视频输出 |
| `Image / Buffer` | Render Texture、Texture、Transient Resource |
| Filter Graph | 后处理链 / Render Graph |
| PBuffer | Render Texture / Framebuffer |
| 全屏 Quad | Full-screen Triangle |
| Cg | HLSL / Shader Graph |
| 手动引用计数 | 引擎资源管理和临时 RT 池 |

现代后处理通常可以理解成：

```text
Camera Color Target
    -> Renderer Feature
        -> Scriptable Render Pass
            -> Blit / Full Screen Draw
                -> Material + Shader
```

Feature 是把功能加入渲染流程的方式；真正执行图像处理的仍然是 Render Pass 加 Shader。

### 6. Pull 模型和 Dirty 状态

书中采用 Pull 模型：最终节点需要图像时，向上游请求数据：

```text
Display 要图像
    -> 向 Tone Mapping 要图像
        -> 向 Bloom 要图像
            -> 向 Scene Source 要图像
```

如果某个节点的参数改变，就标记为 Dirty：

```text
Blur 半径改变
    -> Blur Dirty
    -> 下游依赖 Blur，也需要重新计算
```

没有变化时，可以复用之前的结果，避免不必要的计算。这与现代渲染图中的资源依赖、缓存失效和惰性求值思想相似。

### 7. Ping-Pong 纹理

一个 Pass 不能同时把同一张纹理作为输入和输出，否则会发生读写冲突：

```text
错误：Texture A 同时作为输入和当前 Render Target
```

所以多次迭代通常使用两张纹理：

```text
A -> B
B -> A
A -> B
```

Bloom、Gaussian Blur、流体模拟和其他迭代算法经常采用这种 Ping-Pong 结构。现代引擎通常用 Render Texture Pool 或 Render Graph 自动管理这些临时资源。

### 8. 高斯模糊例子

每个输出像素采样邻域像素，再乘以 Gaussian Kernel 权重并求和。

如果半径为 3，直接使用二维 Kernel 需要大约：

```text
7 × 7 = 49 个采样
```

如果 Kernel 可分离，则拆成：

```text
横向 7 次采样
    -> 纵向 7 次采样
```

这也是现代 Bloom 和后处理模糊常见的优化方式。

### 9. 工程上的理解

- 本章不是在教某个过时 API，而是在教如何组织 GPU 图像处理链。
- 后处理通常由多个全屏 Render Pass 组成。
- 每个 Pass 从输入纹理读取，写入另一张输出纹理。
- 中间结果应尽量留在 GPU 显存中，避免 GPU/CPU 回读。
- 多 Pass 之间需要管理临时 Render Texture，不能随意让同一资源同时读写。
- Shader Pass、Render Pass 和 Renderer Feature 是三个不同层次的概念。
- Renderer Feature 是调度和接入层，真正执行图像处理的是 Render Pass 加 Shader。
- Render Graph 可以看作更现代、更自动化的图像处理依赖图。
