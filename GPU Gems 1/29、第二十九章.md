# 遮挡剔除

## 章节内容

通过硬件遮挡查询提升渲染性能，跳过视锥外或被遮挡的几何体。

**作者**: Dean Sekulic (Croteam)

### 核心概念

通过硬件遮挡查询提升渲染性能，跳过视锥外或被遮挡的几何体。

### 核心概念

**两种主要方法**：
- **遮挡查询**：几何级别拒绝（GeForce3+）
- **Early-Z拒绝**：光栅化阶段每片段剔除

**关键区别**：
- 遮挡查询在几何级别拒绝多边形
- Early-Z在光栅化级别工作

### 硬件遮挡查询机制

**处理流程**：
1. 禁用颜色/深度缓冲写入
2. 开始查询并渲染对象的包围盒
3. 结束查询获取可见像素数
4. 如果数量 > 阈值，渲染完整对象

**关键洞察**：
GPU报告"经过所有管道测试后应该出现在屏幕上的像素数"。

### 实现策略

**关键问题 - 管道停顿**：
- 朴素方法导致CPU-GPU同步瓶颈

**解决方案 - 跨帧延迟查询**：
- 当前帧查询可见性，下一帧检查结果
- 上帧可见对象完全渲染（作为遮挡物）
- 先前不可见对象仅测试包围盒

**优势**：
- 消除GPU停顿
- 1帧延迟可接受

### 优化技术

**排序策略**：
- 分离不透明对象（前到后）和半透明对象（后到前）
- 不透明对象自动成为遮挡物
- 使后续剔除更有效

**包围盒细化**：
- **静态对象**：复杂几何使用多个子盒（金字塔示例）
- **动画模型**：存储每动画盒而非每帧盒

### 常见陷阱

**填充率限制**：
- 高分辨率+简单shader时
- 包围盒可能需要比对象更多像素处理

**近距离对象**：
- 观察者接近包围盒内部时跳过测试
- 背面剔除导致误报

**简单几何无效**：
- ~300三角形以下对象改善最小

**CPU开销**：
- 简单对象（200三角形）查询成本可能超过直接渲染

**性能阈值**：
- 对象超过1000三角形时显示"超过两倍"加速


## 讨论与补充


### 1. 视锥剔除和遮挡剔除

#### 视锥剔除

判断物体是否在相机视锥内：

```text
物体在屏幕外 -> 不提交绘制
```

通常使用包围球、AABB 或 OBB 与视锥平面做数学测试。

#### 遮挡剔除

物体在相机视锥内，但被更近的物体完全遮挡：

```text
相机 -> 大墙 -> 墙后的房间
```

房间在视锥内，但完全不可见，因此可以跳过完整绘制。

### 2. Early-Z 和 Occlusion Query

这两种技术都利用深度，但作用层级不同。

#### 2.1 Early-Z

Early-Z 是片元级剔除：

```text
模型已经提交
    -> 光栅化产生片元
    -> 深度测试提前丢弃被遮挡片元
```

它可以减少 Pixel Shader 和后端写入，但不能阻止：

- DrawCall；
- 顶点读取；
- Vertex Shader；
- 图元装配；
- 部分光栅化工作。

#### 2.2 Occlusion Query

Occlusion Query 尝试在几何级判断物体是否可见：

```text
先绘制简单包围盒
    -> 关闭颜色和深度写入
    -> 保留深度测试
    -> 统计通过深度测试的像素
    -> 如果为 0，跳过完整模型
```

因此可以理解为：

```text
Occlusion Query -> 减少物体级工作
Early-Z         -> 减少片元级工作
```

### 3. Occlusion Query 的流程

```text
DrawBoundingBox(object)

if visiblePixelCount > 0:
    DrawFullObject(object)
else:
    SkipObject()
```

包围盒只参与深度测试，不应改变当前颜色和深度缓冲，否则会影响后续渲染结果。

### 4. 为什么不能立刻读取 Query 结果

GPU 需要先执行之前提交的命令，才能知道包围盒有多少像素通过测试：

```text
CPU 提交 Query
    -> GPU 执行
    -> GPU 产生结果
    -> CPU 读取
```

如果 CPU 立刻读取，CPU 往往需要等待 GPU 完成之前的命令，破坏 CPU/GPU 并行，甚至可能比直接绘制完整模型更慢。

因此书中建议延迟一帧读取：

```text
Frame N：
    使用 Frame N-1 的可见性结果
    同时发起 Frame N 的 Query

Frame N+1：
    读取 Frame N 的 Query
```

代价是可见性结果有延迟，物体重新出现时可能晚一帧显示。

### 5. 可见物体和不可见物体的处理

一种常见策略是：

```text
上一帧可见
    -> 当前帧直接绘制完整物体
    -> 同时发起 Query

上一帧不可见
    -> 当前帧只绘制包围盒做 Query
    -> 如果露出，下一帧再绘制完整模型
```

这是利用“可见物体通常会继续可见”的时间连续性，避免所有物体都先等待 Query。

### 6. Occluder 和 Occludee

#### Occluder

遮挡别人的物体，例如墙、建筑、地形和山体。通常是不透明物体，因为它们会写入深度缓冲。

#### Occludee

被遮挡的物体，例如房间内部物体、敌人和小道具。

透明物体通常不能作为可靠 Occluder，因为它们一般不写深度，或可以透过它看到后方。

常见顺序是：

```text
不透明物体前到后
    -> 建立深度和遮挡关系
    -> 判断后方物体
    -> 透明物体后到前
```

### 7. 包围盒带来的误判

Query 测试的是包围盒，不是实际模型。如果包围盒很大，可能出现：

```text
包围盒可见
模型本体完全被遮挡
```

这会产生保守误判：模型仍然被绘制，但不会错误消失。

静态复杂物体可以使用更紧的 AABB、OBB、多个子包围盒或简化代理网格，但包围体过多会增加 Query 本身的成本。

动画物体的包围盒也需要权衡：

- 每帧精确计算：准确但 CPU 成本高；
- 所有动画共用一个盒子：便宜但过松；
- 每个动画保存一个包围盒：通常是较好的折中；
- 混合动画时取各动画包围盒的并集。

### 8. 什么时候不值得做遮挡查询

如果物体只有很少三角形，可能出现：

```text
绘制完整模型的成本
    < 绘制包围盒 + 发起 Query + 管理同步的成本
```

遮挡查询更适合：

- 三角形很多；
- Pixel Shader 很复杂；
- 屏幕占用较大；
- 被遮挡概率高；
- 场景有稳定的大型遮挡物。

高分辨率下，包围盒自身也会覆盖很多像素。如果原物体很便宜，测试包围盒反而可能更慢。

### 9. 现代方案

传统 Occlusion Query 仍适合少量大型对象、特殊交互对象和 Lens Flare，但现代引擎通常更多使用：

#### 烘焙遮挡剔除

离线分析静态场景，记录区域之间的可见关系：

```text
当前区域 -> 哪些区域可能可见
```

#### Hi-Z / Depth Pyramid

把深度图逐级降采样：

```text
原始深度
 -> 1/2
 -> 1/4
 -> 1/8
 -> ...
```

GPU 用物体包围盒的深度与不同层级的深度比较，批量判断物体是否可能被遮挡。

#### Software Rasterization / GPU Driven

使用低分辨率代理几何体、CPU 软件光栅化或 Compute Shader 生成可见性结果，再通过间接绘制提交可见物体。

相比逐个 CPU 读取 Query，现代方法更适合批量处理并减少同步。

### 10. Lens Flare 的应用

镜头光晕通常是后处理或屏幕叠加效果，但需要判断光源是否被遮挡。

可以在光源屏幕位置绘制一个小区域，只开启深度测试和 Query：

```text
通过深度测试的像素比例
    -> 光晕可见程度
```

例如：

```text
可见比例 1.0 -> 完全显示
可见比例 0.5 -> 半透明
可见比例 0.0 -> 隐藏
```

### 11. 工程上的理解

```text
视锥剔除：物体是否在相机视野内？

Early-Z：已经提交的模型中，哪些片元被深度挡住？

Occlusion Query：这个模型是否值得完整提交？

烘焙遮挡 / Hi-Z：用预处理数据或深度金字塔批量判断哪些物体可见？
```

本章的 Occlusion Query 思想仍然有效，但 CPU 读取查询结果会带来同步和延迟。现代 GPU Driven 渲染通常更倾向于 GPU 批量剔除、Hi-Z 深度金字塔和间接绘制。
