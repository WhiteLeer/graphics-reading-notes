# Attributed Vertex Clouds（属性顶点云）

## 章节内容

本章提出 Attributed Vertex Clouds（AVC），用于表示和渲染大量简单、可参数化的几何体。核心做法是保存描述对象的数据点和属性，再通过 Transfer Function 将其转换为几何配置，并在 GPU 渲染管线中程序化生成顶点和图元。

作者用方块世界、长方体、多边形、圆弧和运动轨迹说明 AVC。它适合几何规则、可以由紧凑参数表达、且实例数量很大的场景；并不是任意复杂网格的通用替代品。

**作者**：Willy Scheibel、Stefan Buschmann、Matthias Trapp、Jürgen Döllner

## 核心概念

传统网格表示保存顶点、索引及法线、纹理坐标等数据。AVC 则把一个输入顶点视作一个对象或数据项的描述。它可以直接包含几何参数，也可以是需要进一步解释的领域数据。

```text
属性数据（位置、尺寸、类型、颜色……）
    ↓ Transfer Function
几何配置（类型、形状参数、LOD、交互状态……）
    ↓ 几何生成
Attributed Vertices / Primitives
    ↓ 光栅化
最终图像
```

Transfer Function 可读取对象自身属性，也可结合相机位置、全局配置和交互状态，决定几何类型与参数。几何通常由 Geometry Shader 生成，也可结合 Tessellation Shader；具体阶段依实现和硬件而定。

### 三个组成部分

1. **Attributed Vertex Cloud**：GPU 上的数据点集合。每个点表示一个目标对象或领域数据项，并携带生成目标几何所需的信息；也可以用索引引用共享的辅助数据。
2. **Transfer Function**：把输入属性映射为几何配置，可用于类型选择、LOD、交互过滤、选择高亮及参数化。
3. **Geometry Generation**：按配置生成顶点和图元，交给后续管线光栅化。某些实现会把 Transfer Function 和几何生成合并。

## 章节案例

### 方块世界

一个 AVC 元素可保存方块的网格位置和类型。顶点着色器传递属性，几何着色器按固定规则输出方块的 Triangle Strip。硬件实例化方案则复用顶点缓冲中的方块模板，把每个实例的位置和类型作为实例属性。

这不是“先画一个方块，再复制图像”。两种方案都在批量绘制中处理每个对象；区别在于实例化从 Buffer 读取模板顶点，AVC 从输入属性和 Shader 生成规则构造几何。

### 长方体和圆弧

- 长方体可由中心、尺寸和颜色值描述，再由几何阶段生成各面。
- 圆弧可由中心、内外半径、高度范围和角度描述；细分阶段产生弧段，几何阶段生成弧面和端部。
- 多边形的顶点数可变，因此示例使用一个缓冲区存多边形公共属性，另一个存边界顶点和多边形引用；顶点拉取和几何着色器逐段生成 polygon wedge。

### 运动轨迹

轨迹数据点带位置、时间、速度、加速度等属性。Transfer Function 可依据相机距离和交互状态改变表现：远处未选中轨迹画成线，高亮轨迹画成管道，选中的采样点画成球体；速度映射颜色，加速度映射半径。改变控制参数即可切换表现，不必为每种状态重新上传一套展开网格。

## 与硬件实例化的区别

| | 硬件实例化 | AVC |
|---|---|---|
| 几何模板 | 存一份共享 Vertex/Index Buffer | 生成规则通常写在 Shader 中，也可读取辅助数据 |
| 每个对象 | 保存位置、旋转、缩放等实例属性 | 保存位置、类型、尺寸或领域数据等属性 |
| GPU 工作 | 对模板顶点重复应用实例变换 | 从属性计算配置并动态生成几何 |
| 更自然的用途 | 大量复用同一份现成网格 | 几何可由紧凑参数和规则生成，或需数据驱动地改变形式 |

二者都不需要先单独绘制基础物体。实例化不是把基础网格“存在 Buffer 做的”——基础网格模板确实在 Buffer 中，但 GPU 在同一批次里对每个实例重复处理模板。AVC 也不是完全不存几何相关信息：生成规则、参数、拓扑描述或辅助数据仍然需要存在某处。

## 性能评估与边界

作者在 2017 年前后的 OpenGL 实现中，以方块世界比较三角形列表、Triangle Strip、硬件实例化和 AVC。测试环境为 Ubuntu 14.04、GeForce GTX 980、1920×1200，方块网格规模从 16³ 到 100³。

对每个固定尺寸方块，表格给出的实例化数据约为 336 字节静态模板加 16 字节/实例；AVC 为 16 字节/实例。也就是说，AVC 在这个例子中省的是一份小型共享模板，不是每个实例的属性数据。作者报告其实现的 AVC 在方块测试中最高约有 2 倍 FPS，并且几何处理计时较低；这是特定实现和硬件的测量，不是普遍保证。

采用 AVC 的潜在收益包括更紧凑的数据表达、较少的几何输入数据、减少 CPU 构建或上传展开网格，以及基于属性做动态几何、LOD、裁剪和交互表现。代价则可能是额外 Shader 计算、几何阶段吞吐压力、辅助数据访问和更复杂的生成逻辑。最终三角形仍要经过光栅化；若像素/光栅化是瓶颈，少存模板不一定带来明显加速。

对一个标准方块，实例化模板本身很小，因此“少了 Buffer”不自动意味着净优化。要看 GPU 时间中省下的顶点读取、输入和阶段调度是否大于 AVC 的生成成本。Geometry Shader 的性能也因硬件而异，应该在目标设备上 profiling。

任意不规则、高精度网格不能仅靠 AVC 消除顶点与拓扑信息。若需要精确还原，仍需保存或压缩几何数据；这时 AVC 可能只是以辅助数据和 Shader 读取的方式表达网格。多个方块组成固定组合时可用参数分别生成各部分，但 AVC 不会自动焊接顶点、去掉内部面或优化拓扑。若组合类型多、结构任意或需消除内部面，预先合并/优化网格往往更直接。

### 工程判断

- 大量同一草模型仅按距离缩放：通常用 GPU Instancing，Shader 按实例位置与相机距离连续求缩放；C# 传全局参数，不要逐株更新 Transform。AVC 并非必需。
- 大量规则方块：AVC 是合理候选，但先与实例化基线比较。如果方块相邻形成体素结构，应优先评估面剔除、Greedy Meshing、Chunk 剔除等，因为内部不可见面可能比模板 Buffer 更浪费。
- 任意复杂模型：更常见的方向是网格压缩、Meshlet、实例化共享网格、GPU-driven culling/indirect draw 和 LOD；AVC 只在确有紧凑生成规则时有明显意义。

## 讨论与补充

### 对“AVC 是否就是减少 Buffer、换成每帧大量计算”的理解

大方向成立，但不应把所有差异都归结为 ALU 运算。实例化也会在每帧读取模板顶点并做变换；AVC 把模板表示和一部分顶点处理转移到生成阶段。AVC 的收益可能来自减少模板/输入数据、CPU 提交或上传、以及适配动态几何；成本可能来自几何生成、额外数据读取和几何阶段压力。

所以应比较完整成本：

```text
数据存储与读取 + CPU/GPU 提交 + Shader/几何生成 + 光栅化
```

而不是只比较 Buffer 大小或 Shader 指令数。生成后仍输出同样多的三角形时，光栅化工作不会自动减少。

### 10,000 个方块的具体对比

若是同尺寸方块、位置或类型不同：

```text
实例化：一份方块模板 + 10,000 份实例属性
AVC：    10,000 份属性 + Shader 中的方块生成规则
```

两者都不需要存 10,000 份完整方块网格。AVC 主要省共享模板；实例化则读取模板并对其顶点应用实例数据。模板小到几百字节时，光靠省模板通常不是重要收益，实际差异应由目标 GPU 上的测试决定。

### 简单组合模型

两个方块可由“组合体变换 + 两个子方块的偏移/尺寸”描述，然后分别生成；也可以把每个子方块作为一条 AVC 记录。但这需要明确组合数据格式和规则。若每个组合结构都任意变化，描述数据、分支和生成逻辑会增长。逐个生成子方块也会保留接触面或内部面，除非额外做拓扑处理。固定的组合模型通常可以直接合并为一个网格，再实例化。

## 本章结论

AVC 是面向“可由紧凑属性与规则生成的几何”的数据表示和渲染方案，不是普遍优于实例化的技术。它的核心取舍是：用生成规则和 GPU 工作替代一部分显式几何存储或输入；只有被替代的部分确实是瓶颈，且生成成本可接受时，才构成实际优化。

> [!tip] 记忆要点
> 实例化复用一份已存储的网格模板；AVC 用属性和生成规则描述对象并在 GPU 中构造几何。AVC 能否更快要实测，尤其不能把“节省模板 Buffer”直接等同于“整体性能提升”。
