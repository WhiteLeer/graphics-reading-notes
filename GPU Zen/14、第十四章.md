# Understanding, Measuring, and Analyzing VR Graphics Performance（理解、测量与分析 VR 图形性能）

## 章节内容

本章讨论如何测量和分析 VR 应用的图形性能。VR 性能不能只用平均 FPS 判断，还需要观察每一帧是否在刷新周期内完成，以及 CPU、GPU、VR 合成器和显示链路之间是否存在等待。

作者：James Hughes、Reza Nourai 和 Ed Hutchins

## 核心思路

### 帧时间预算

刷新率决定每帧可用的时间预算。例如 90 Hz 时每帧约只有 11.1 ms。只要某些帧超过预算，就可能出现掉帧、重复显示上一帧或触发重投影，即使平均 FPS 看起来仍然较高。

### CPU、GPU 与合成器

VR 渲染通常不是简单的“CPU 提交、GPU 绘制、显示”三步，而是包含应用线程、渲染线程、GPU、VR Runtime 和合成器的协作。分析时需要判断：

- CPU 是否来不及提交命令；
- GPU 是否在规定时间内完成渲染；
- 合成器是否等待应用纹理；
- 是否发生 CPU-GPU 同步或队列阻塞。

### Trace 分析

性能 Trace 可以将各线程、进程和 GPU 阶段放到同一条时间线上。重点不是只找最长的函数，而是确认关键帧是否按时完成，以及延迟是在哪个阶段积累的。

## VR 特有问题

- 双眼渲染会增加几何、光栅化和着色工作。
- 重投影可以在应用未及时完成新帧时维持显示更新，但它不是免费的性能优化，会带来画面变形或运动伪影。
- 延迟不仅来自 GPU 着色，还可能来自输入采样、渲染提交、合成和显示扫描。
- 平均帧率掩盖不了偶发长帧，因此需要关注帧时间分布和最坏情况。

## 分析流程

1. 明确目标刷新率和每帧时间预算。
2. 记录真实运行中的 CPU、GPU 和合成器 Trace。
3. 判断瓶颈属于 CPU、GPU、同步等待还是显示/合成链路。
4. 修改一个环节后重新采集 Trace，确认是否只是把瓶颈转移到了其他阶段。

## 本章结论

VR 性能优化的目标不是单纯提高平均 FPS，而是让每一帧稳定地在预算内完成，并控制从输入到显示的总延迟。只有结合帧时间、Trace、CPU/GPU 队列和重投影状态，才能判断 VR 是否真正流畅。
