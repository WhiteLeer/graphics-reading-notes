# Profiling and Optimizing WebGL Applications Using Google Chrome（使用 Google Chrome 分析与优化 WebGL 应用）

## 章节内容

本章介绍如何使用 Chrome 内置工具分析 WebGL 应用的性能。这里的 WebGL 指浏览器中的 GPU 渲染接口，既可以用于普通动态网页中的 3D 内容，也可以用于网页端游戏和在线模型查看器。

作者：Gareth Morgan

## 核心思路

WebGL 应用的性能不只由 GPU 着色器决定，还受到 JavaScript 主线程、浏览器 Renderer 进程、GPU 进程以及 CPU-GPU 数据传输的影响。因此分析时不能只看 FPS，而要观察完整的时间线，确认究竟是谁在等待谁。

## 主要工具与指标

### FPS 与帧时间

Chrome 的 FPS 计数器可以快速判断页面是否掉帧，但它只能说明结果，不能直接说明瓶颈位置。

### WebGL 渲染循环

网页端通常通过 `requestAnimationFrame` 驱动渲染。浏览器决定回调的实际执行时机，应用并不能完全控制最终帧率，因此需要区分 JavaScript 执行时间和浏览器调度造成的等待。

### Chrome Event Tracing

Tracing 时间线可以显示 JavaScript、Renderer、GPU Process 等不同进程的活动。通过事件的开始、结束和等待关系，可以定位 Draw Call 过多、GPU 忙、命令队列阻塞以及 CPU-GPU 同步等问题。

## 案例中的优化规律

一个案例中，过多 Draw Call 使 CPU 不断提交渲染命令，优化后 CPU 提交时间下降，但瓶颈可能转移到 GPU 命令队列或数据传输。因此每次优化后都必须重新 Profiling，不能只根据局部代码耗时判断整体变快。

另一个重要问题是 CPU 更新顶点数据后等待 GPU 完成传输。这类同步会让 JavaScript 线程停顿，即使单个 Draw Call 本身并不复杂，也可能造成明显卡顿。

## 普通网页与网页游戏

- 普通动态页面主要关注 JavaScript、布局、绘制和合成。
- WebGL 网页游戏还需要关注 Draw Call、纹理上传、Shader 执行、GPU 队列和 CPU-GPU 同步。
- Chrome Profiling 更擅长定位浏览器整体链路；GPU 专项工具才能进一步分析具体 Shader、纹理和渲染状态。

## 本章结论

WebGL 性能优化应遵循“先观察完整时间线，再定位瓶颈，修改后重新测量”的循环。减少 Draw Call 并不保证整体性能一定提升，因为瓶颈可能转移到 GPU 队列、资源上传或同步等待。
