# iPhone 3GS Graphics Development and Optimization Strategies（iPhone 3GS 图形开发与优化策略）

作者：Andrew Senior  
来源：GPU Pro 1，Part VI，Chapter 3，pp. 385–395。

> 本章基于 2009 年左右的 iPhone 3GS、OpenGL ES 2.0 和 PowerVR SGX。具体 API、工具和硬件限制已经过时，但它把移动 GPU 优化中的几个关键矛盾讲得很清楚：CPU/GPU 同步、提交开销、带宽、缓存、片元数量和资源格式。

## 1. 本章的定位

本章不是提出一种新的渲染算法，而是以 iPhone 3GS 为案例，总结一套移动端图形优化方法。书中的“快”主要来自以下几类减少：

- 减少 CPU 与 GPU 的同步等待；
- 减少 Draw Call 和状态切换；
- 减少传给 GPU 的顶点和纹理数据；
- 减少片元着色器中的计算；
- 提高纹理缓存和内存带宽利用率；
- 尽早剔除不会产生可见结果的对象。

## 2. 开发环境与性能验证

iPhone 3GS 是本系列设备中首次支持 OpenGL ES 2.0 的型号，同时拥有更快的 CPU 和更多内存。书中涉及：

- Apple iPhone SDK 与 Xcode；
- OpenGL ES 1.1/2.0；
- PowerVR SGX；
- PowerVR SDK 的 PVRTexTool、PVRShaman、PVRUniSCo Editor 和 PVRTools；
- Instruments 性能分析工具。

最重要的工程提醒是：模拟器可以用于检查画面、输入和逻辑，但不能用来判断真实 OpenGL ES 性能。性能必须在实际设备上测量，因为模拟器的 GPU、驱动、内存带宽和并行方式都不同。

## 3. 七条总原则

### 3.1 不要从 CPU 访问 framebuffer

CPU 读取 framebuffer 会迫使驱动刷新已经排队的渲染命令，并等待 GPU 完成工作，从而破坏 CPU、GPU 和驱动之间的并行性。

这条原则今天仍然有效：类似的同步点包括 CPU 读取 GPU 资源、阻塞式映射、立即读取查询结果和不必要的 GPU → CPU 回读。

### 3.2 使用 VBO 和索引几何体

将顶点和索引放入 GPU 友好的缓冲区，驱动可以采用更好的内存布局和传输路径。索引还能复用共享顶点，减少顶点数据量。

### 3.3 批处理，减少 Draw Call

动态几何体、粒子等不要逐个对象提交，而应先写入一个共享的顶点/索引数组，再用一次或少量 Draw Call 绘制。批处理的价值不仅是少调用 API，也包括减少状态切换和驱动工作。

### 3.4 在 CPU 侧做粗粒度剔除

应用程序比 GPU 更了解场景结构、对象语义和可见性。视锥体剔除、距离剔除、空间层级和已知遮挡关系都可以在提交前排除对象。

### 3.5 使用纹理压缩和 MipMap

压缩纹理减少显存、传输和带宽压力，提高纹理缓存利用率。MipMap 则同时改善远距离纹理的缓存访问和缩小采样质量。

### 3.6 尽量把计算从片元移到顶点

通常顶点数量远少于屏幕片元数量，因此可以把适合插值的计算放在顶点阶段，避免每个像素重复执行。

### 3.7 避免 fragment shader 中的 `discard`

在当时的 PowerVR 架构中，`discard` 会破坏部分隐藏面消除优势，需要更晚才能确定片元是否可见。能用混合、材质拆分或专用 Shader 表达的效果，不应无条件依赖 `discard`。

## 4. 顶点数据与提交方式

### VBO 组织

不建议每个小网格都创建一个独立 VBO。总是一起绘制的网格可以放在同一批缓冲区中，以减少绑定和提交成本。

### 交错数组与分离数组

交错布局相当于：

```text
position0 normal0 uv0, position1 normal1 uv1, ...
```

一次顺序读取就能取得一个顶点的全部属性，通常更利于缓存。

但并不是任何情况都必须交错：如果某个属性被多个网格共享，或者只有一个属性频繁更新，分离数组反而可以避免重复数据和不必要的传输。布局应根据访问模式决定。

### 粗粒度剔除

使用包围盒、包围球和空间数据结构做快速判断：如果对象完全在视锥体外，直接不提交。即使 GPU 自己有隐藏面消除，完全不提交仍然更便宜，尤其是顶点 Shader 很复杂时。

## 5. 渲染顺序与批处理

本章针对 PowerVR SGX 给出的基本分组是：

1. 不透明物体；
2. 使用 `discard` 的物体；
3. 使用混合的透明物体。

不透明物体可按渲染状态排序，减少 Shader、纹理和 uniform 切换。PowerVR 的隐藏面消除机制使得专门按深度前后排序不一定值得，可能还不如按状态排序划算。

透明物体依赖当前 framebuffer，因此通常需要从后往前绘制。动态粒子几何应先合并为一个索引三角形列表，再统一提交。

这里体现出一个重要取舍：排序不应只看“理论上的深度顺序”，而要看目标架构真正昂贵的部分是状态切换、overdraw、带宽还是排序本身。

## 6. 纹理优化

### 纹理尺寸

不要因为“大纹理看起来更清晰”就给所有对象使用 1024×1024。应根据对象在最近观察距离下覆盖的屏幕像素选择尺寸，目标大致是一个屏幕像素对应一个纹素。

### NPOT 纹理

当时的 PowerVR 对 NPOT 支持有限，通常不能使用 MipMap，寻址模式也需要 `CLAMP_TO_EDGE`。因此 NPOT 更适合屏幕大小的 render target，而不是需要缩小采样和重复寻址的普通模型纹理。

### PVRTC 压缩

PVRTC 可以使用 4bpp 或 2bpp，减少纹理占用和内存带宽，同时提高缓存效率。对于移动设备，压缩格式的收益往往不只是“省显存”，还包括上传更快、缓存命中更高和采样带宽更低。

### MipMap

MipMap 是预先过滤的多级缩小纹理。它能：

- 减少严重缩小时的闪烁和混叠；
- 让硬件选择更接近屏幕覆盖范围的纹理级别；
- 改善纹理缓存访问。

三线性过滤能减少级别切换接缝，但会增加额外采样成本；是否值得取决于 Shader 和纹理单元是否还有余量。

### 纹理图集

将多个小纹理放进一个 atlas 可以减少纹理绑定。但要注意过滤和 MipMap 会采样到相邻图块，需要边缘扩展或合理 padding；同时纹理图集会限制独立重复寻址。

## 7. Shader 优化

### `discard`

`discard` 会阻止当前片元写入，但代价是硬件可能必须先运行片元 Shader 才能确定可见性，从而损失早期隐藏面剔除收益。应优先考虑：

- 使用 alpha blending 表达透明区域；
- 将需要裁剪的对象单独分组；
- 只为确实需要的材质使用专用 discard Shader；
- 确保这类对象在不透明物体之后提交。

在 `discard` 外层再加条件分支，并不一定能消除其架构代价。

### 顶点属性

当时的 OpenGL ES 2.0 顶点属性最终都要进入浮点顶点 Shader。非 FLOAT 类型可能需要转换；属性最好按四字节边界对齐。过度追求紧凑打包可能换来额外的读取和转换成本，需要实测。

### 把计算移到顶点阶段

如果某个计算可以通过插值保持足够质量，应优先放到顶点 Shader。典型例子是将逐像素光照简化为逐顶点光照。

### 循环展开

只有在其他优化完成、并且确实由小循环造成瓶颈时，才考虑手动展开。展开可能帮助编译器，但也会增加 Shader 代码体积，不应当作为第一手段。

## 8. 今天仍然适用的部分

尽管 iPhone 3GS 和 PowerVR SGX 已经是历史平台，本章仍然可以抽象出一套通用判断：

```text
先避免同步
→ 再减少提交和状态变化
→ 再减少数据传输和带宽
→ 再减少片元工作
→ 最后才做局部 Shader 微优化
```

过时或需要重新验证的部分包括：

- 具体 PVRTC、NPOT 和 `discard` 限制；
- PowerVR 的特定隐藏面消除行为；
- 固定的纹理位深和属性类型建议；
- 当年的 Xcode、PVRTools 和 Instruments 工作流。

## 9. 总结

本章的核心不是“把所有计算都移到顶点 Shader”，而是从完整渲染链路减少不必要的工作：不触发 CPU/GPU 同步，提前剔除对象，合并提交，压缩纹理，利用缓存，并控制片元 Shader 成本。

对于今天的 Unity、Unreal 或自研引擎，应把这些原则转化为可测量的问题：每帧 Draw Call 多少、状态切换多少、GPU/CPU 是否互相等待、纹理带宽是否饱和、片元指令是否被 overdraw 放大，而不是机械照搬某个旧硬件结论。
