# Optimizing a 3D UI Engine for Mobile Devices（移动设备上的 3D UI 引擎优化）

作者：Hyunwoo Ki  
来源：GPU Pro 1，Part VI，Chapter 4，pp. 397–410。

## 1. 本章的定位

本章不讨论单个 Shader 的局部优化，而是讨论一个可跨平台的移动端 3D UI 引擎如何从整体架构上控制性能和内存。

目标包括：

- 减少 UI 渲染状态和 Shader 切换；
- 减少文字渲染的 Draw Call 与纹理切换；
- 将稳定的复杂控件缓存为纹理；
- 只更新发生变化的局部区域；
- 在内存不足时释放并恢复资源。

核心思想是：UI 不应每帧都从头遍历、生成和绘制所有内容，而应把稳定内容变成缓存，把变化限制在脏区域，把资源生命周期交给统一的资源管理器。

## 2. 渲染管线优化

移动 UI 通常由图片、文字、矩形和透明控件组成，复杂光照并不是主要成本。引擎可以采用少量固定组合：

- 简单纹理映射 Shader；
- 一个主颜色；
- 开启 Alpha Blend；
- 关闭 Depth Test 和 Depth Mask；
- 按从后到前的顺序绘制透明控件。

渲染器保存当前的 Render State、纹理和 Shader 信息。绘制新控件前，先把它的材质状态与缓存状态比较，只有真正发生变化时才调用 OpenGL API。

这避免了两类浪费：

1. 明明状态没有变化，却重复调用设置函数；
2. 为了查询当前状态而频繁调用昂贵的 `glGet*`。

引擎维护自己的状态副本，而不是每次向驱动询问。对于发布版本，也不应在每个 API 后都调用 `glGetError`，而是只在关键且低频的资源创建操作上检查错误。

## 3. Shader 与纹理策略

由于移动设备屏幕像素很多，片元 Shader 的成本会迅速放大。因此 UI Shader 应尽量简单，避免不必要的条件分支和 `discard`。

在很多 UI 场景中，透明区域可以直接依靠纹理 Alpha 和混合实现，不一定要使用 Alpha Test。这样可以避免额外的片元控制流和可见性判断。

纹理方面：

- 绝大多数没有缩放或旋转的控件可以使用最近点过滤；
- 需要缩放、旋转或 3D 模型时再启用 MipMap 和线性过滤；
- 16 位格式可以减少纹理上传和采样带宽；
- 压缩格式可以减少内存、上传时间和缓存压力；
- NPOT 纹理在支持的平台上可减少 padding，但需要考虑平台限制。

这里的原则不是“格式越高质量越好”，而是让纹理格式、过滤方式和控件实际显示方式匹配。

## 4. 顶点、剔除与裁剪

引擎使用索引顶点数组，避免重复存储共享顶点，并偏向交错顶点布局来提高内存访问效率。

UI 场景中的可见性优化包括：

- Visibility Culling：完全位于控件可见区域外的子控件不绘制；
- Occlusion Culling：已知被上层控件完全遮住的控件不绘制；
- Scissor Test：矩形裁剪区域之外的片元直接不进入后续处理。

如果只需要矩形裁剪，Scissor Test 通常比 Stencil Test 更划算，因为 Stencil 可能需要额外的渲染通道和模板缓冲访问。

对于全屏弹窗、键盘等确定会遮挡大量内容的控件，可以先绘制遮挡控件，再用屏幕空间包围盒判断下层控件是否完全被覆盖。

## 5. TrueType 字体渲染

文字渲染的基本形式是：每个字符对应一个四边形，四边形采样字体纹理中的 Glyph 位图，并使用 Alpha Blend 绘制。

引擎按以下层级管理字体数据：

```text
Font
  → FontFace
    → 字号集合
      → Glyph 集合
        → 字符位图与纹理坐标
```

只有真正使用过的字体、字号和字符才会创建 Glyph 数据，从而避免一次性保存完整字符集。

### 文本缓存

如果文本的内容、位置、对齐方式或字号没有变化，就可以复用预生成的文本顶点缓冲，不必每帧重新计算每个字符四边形的位置和纹理坐标。

### 按纹理分组

一段文字可能使用多个字体纹理。如果按字符原顺序绘制，就会频繁切换纹理。由于同一段文字中的字符通常没有复杂的相互遮挡关系，可以按字体纹理对字符顶点缓冲重新分组：

```text
文本字符
  → 按字体纹理分组
  → 每组生成一个顶点缓冲
  → 每组一次提交
```

这会减少 Draw Call 和纹理绑定次数，中文、韩文等字符集较大的语言收益尤其明显。

## 6. Widget Cache

复杂组合控件可能包含背景、图片、文字、按钮和多个子控件。每帧递归渲染它们会产生很多 Draw Call，因此可以将整个控件绘制到 Render Texture：

```text
复杂控件 → Render Texture → 后续当作一张图片绘制
```

只要外观没有变化，之后每帧只需绘制一张缓存纹理。

### 缓存失效

当子控件的位置、颜色、纹理、文字等发生变化时，设置 Dirty 标记。渲染时递归查找所有 Dirty 子控件，并合并其包围盒。

为了处理动画移动留下的旧区域，还要把上一帧的 Dirty 区域一起合并：

```text
DirtyRect = Union(CurrentDirtyRect, PreviousDirtyRect)
```

这样可以避免控件移动后留下“残影”或旧内容。

## 7. 局部更新

得到 Dirty Rect 后，将它变换到屏幕空间，并同时设置：

- 可见性裁剪区域；
- Scissor Box；
- Widget Cache 的 Render Target。

更新流程为：

1. 绑定 Widget Cache 纹理；
2. 设置 Dirty Rect 对应的裁剪区域；
3. 只重新渲染受影响的子控件；
4. 不清除缓存中未受影响的部分；
5. 恢复 Render Target；
6. 将缓存作为整体绘制。

例如键盘中只有一个按钮被按下时，不需要重绘整个键盘，只需要重绘背景和这个按钮覆盖的矩形区域。

### 适用边界

Widget Cache 不是始终有效：

- 控件长期稳定：非常适合缓存；
- 局部小范围变化：适合 Dirty Rect；
- 整个控件频繁变化：缓存会频繁重建，收益可能消失；
- 缓存尺寸很大：需要权衡额外 Render Texture 内存。

## 8. 资源管理

移动设备可能同时运行多个应用，内存和显存都有限。引擎为每个资源记录：

- 引用计数；
- 最近使用时间；
- 优先级；
- 资源类型；
- 当前状态；
- 内存占用。

本章划分了四种资源池类型：

### Default

除非应用显式释放，否则不会自动销毁。

### Managed

可以回收内存，之后能从原始文件或源数据完整恢复。例如从图片文件加载的纹理。

### Semi-managed

可以回收 GPU 内存，但只会重新分配空间，内容需要引擎重新生成。例如文本顶点缓冲和 Widget Cache。

### System

始终保留在系统内存中，用于特殊的 CPU/系统侧数据或混合 2D、3D 渲染的资源。

这四类资源的关键区别是：释放后能否自动恢复内容，而不是单纯的“是否占用内存”。

## 9. 资源回收流程

当需要创建新纹理但内存不足时，资源管理器可以：

1. 收集引用计数较低的 Managed 和 Semi-managed 资源；
2. 按优先级和最近使用时间排序；
3. 依次释放资源，直到获得足够空间；
4. 必要时强制释放更多可恢复资源；
5. 分配新资源；
6. 之后在资源重新使用时恢复内容。

在内存碎片或其他应用占用内存的情况下，即使理论上还有剩余容量，资源创建也可能失败。因此资源系统需要根据真实分配结果调整可用内存上限，而不是只相信静态预算。

文本缓冲和 Widget Cache 的恢复方式通常是重新计算顶点数据或重新渲染缓存，而不是从磁盘读取一份现成的 GPU 数据。

## 10. 与现代引擎的对应关系

本章的概念可以对应到现代引擎中的：

- UI Draw Call 合批；
- Sprite/字体图集；
- Retained UI 与脏矩形；
- Render Target Cache；
- Canvas 或 Slate 的缓存绘制；
- 纹理 Streaming 与 Eviction；
- GPU 资源生命周期和重新创建。

但具体实现不能照搬旧的 OpenGL ES 代码。现代引擎还要考虑异步上传、Render Graph、Bindless、GPU 虚拟内存、移动 TBDR 和多线程渲染。

## 11. 总结

本章可以浓缩为四个工程策略：

1. 用状态缓存和批处理减少渲染提交；
2. 用字体图集和文本缓存减少文字开销；
3. 用 Widget Cache 和 Dirty Rect 避免整棵 UI 树重绘；
4. 用分级资源池和可恢复资源应对有限内存。

最重要的判断是：缓存只有在“重建代价大于维护和占用代价”时才值得使用。UI 优化的核心不是盲目缓存，而是控制缓存失效的范围和频率。
