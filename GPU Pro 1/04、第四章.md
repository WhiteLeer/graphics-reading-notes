# Rule-Based Geometry Synthesis in Real-Time（实时规则驱动的几何合成）

## 章节内容

本章提出一个在 GPU 上实时生成程序化几何的框架。场景不直接以完整网格保存，而是用上下文无关规则或等价的 L-system 描述。GPU 根据规则逐层生成“几何对象描述符”，再把这些描述符按类型分组，最后通过 Instancing 绘制真正的网格。

作者：Milán Magdics、Gergely Klár。

## 核心思路

传统程序化建模常常在 CPU 上展开规则并生成完整几何，再上传到 GPU。本章把中间过程也放到 GPU：

```text
初始符号 / Axiom
        ↓
GPU 并行应用规则
        ↓
生成新的模块描述符
        ↓
剔除不可见模块、选择 LOD
        ↓
按网格和材质类型分组
        ↓
Instancing 绘制最终几何
```

这里的模块不是最终三角形，而是“某种对象、位置、方向、尺寸和参数”的描述。例如，一个建筑模块可以继续生成楼层、窗户和装饰物；一个植物模块可以继续生成枝干和叶片。

## PGI 与 L-system

框架建立在 Procedural Geometric Instancing（PGI）和 L-system 的思想上。

- PGI 把场景表示为带有生成过程的场景图节点；
- L-system 用符号和替换规则描述不断展开的结构；
- 每个符号可以带参数，例如长度、方向、尺寸或颜色；
- 规则把一个父模块替换成多个子模块。

传统 turtle graphics 需要按顺序维护全局绘制状态，后一个命令依赖前一个命令，因此不容易并行。本章将状态变化拆成与具体实例绑定的操作，使每个生成模块尽量独立，从而可以在 GPU 上并行处理。

## GPU 生成流程

每个模块用一个通用记录表示，包含符号 ID 和所有可能的参数。初始 Axiom 放入 Vertex Buffer，之后通过 Geometry Shader：

1. 检查模块是否可见；
2. 判断模块是否已经终止；
3. 根据符号类型和规则选择策略选取规则；
4. 创建并初始化后继模块；
5. 通过 Stream Output 写入下一轮 Buffer；
6. 交换输入和输出 Buffer，继续下一轮。

这样 CPU 不需要每轮读取 GPU 生成的模块，也不需要把完整中间几何拷回 CPU。

## 剔除与动态 LOD

剔除发生在规则展开之前。不可见模块直接不输出后继模块，因此不会继续生成更深层的内容。可用的剔除依据包括：

- 视锥体；
- 与摄像机的距离；
- 屏幕空间尺寸；
- 透明度或重要性；
- 与其他对象的包围体相交关系。

不同模块可以展开到不同深度。例如近处建筑生成更多窗户和装饰，远处建筑只保留主要结构。这样规则系统本身就可以承担动态 LOD，而不是先完整生成场景再在最后阶段丢弃细节。

## 为什么还需要排序

规则展开后，模块的顺序通常是混合的，但 Instancing 需要把使用同一网格和渲染技术的模块放在一起。因此 GPU 生成之后还要按 instancing type 分桶：

- 每个桶对应一种网格和渲染技术；
- 同一桶中的模块作为 instance buffer；
- 每种 instancing type 最终只需要相应的绘制调用。

排序是这个方案的重要成本。书中讨论了朴素的逐桶筛选和类似二叉树的分组方法，并指出如果 GPU 支持多个 Stream Output，排序过程可以进一步简化。

## 内存与表示的取舍

为了避免不同符号使用不同顶点类型带来的多次 Pass 和 Shader 分支，框架使用一个通用模块结构来容纳所有可能的数据。代价是：

- 每个模块可能存储一些当前符号并不需要的字段；
- 单个 Vertex 的大小变大；
- Geometry Shader 的输出大小和顶点大小限制更容易成为瓶颈。

因此，这个方案不是无代价地“把所有生成工作搬到 GPU”，而是在并行生成效率、Buffer 空间、Shader 输出限制和排序成本之间做取舍。

## 与实例化的关系

它并不是用程序化规则替代所有实例化，而是：

1. 先用规则生成大量实例描述；
2. 再把相同类型的实例分组；
3. 最后仍然通过 Instancing 绘制基础网格。

所以它和普通实例化的区别在于，实例的位置、尺寸、层级和数量不是 CPU 预先固定好的，而是由 GPU 根据规则动态展开。

## 交互和碰撞

本章还展示了如何利用相同的规则层级做大量对象与程序化场景的相交测试。

方法是为每个程序化模块附加包围体，并把主动对象的信息写入模块记录。GPU 在规则层级上逐层剔除不相交的模块，最终得到主动对象与叶节点之间的相交结果。结果可以读回 CPU，用于：

- 大量 AI 对象与程序化环境的碰撞；
- 粒子与程序化场景的交互；
- 物理模拟中的批量相交查询。

对于少量对象，CPU 处理可能更简单；GPU 方法主要适合对象数量足够多、相交测试可以并行的情况。

## 与普通程序化生成的区别

普通程序化生成通常是：

```text
CPU 解释规则 → CPU 生成网格 → 上传 GPU → 渲染
```

本章的方案更接近：

```text
CPU 提供规则和少量初始数据 → GPU 展开模块 → GPU 分桶和实例化 → 渲染
```

它的主要优势是减少 CPU-GPU 往返，并能在生成过程中进行视锥体剔除和距离 LOD。但它也要求规则适合并行展开，复杂的上下文依赖和全局连接关系不容易表达。

## 代价与限制

- 上下文相关规则和复杂对象依赖受到限制；
- Geometry Shader 输出量、Buffer 容量和动态分支可能成为瓶颈；
- 规则展开后的排序会产生额外 Pass；
- 需要为规则自动生成 Shader 和 CPU 端配套代码；
- 生成的模块不是最终网格，仍然需要合适的基础 Mesh、材质和实例化路径；
- 如果场景规模不大，CPU 生成可能更简单、更容易调试。

## 本章结论

本章不是简单地“用 Compute Shader 画出所有几何”，而是把程序化场景拆成三个层次：

1. 规则描述结构；
2. GPU 并行生成对象描述符；
3. 按类型分组后用 Instancing 绘制。

它适合城市、植物、递归结构和大量规则化对象，尤其适合需要动态 LOD、视锥体剔除和大量实例的场景。对高度不规则、强依赖全局拓扑的模型，它的表达能力和收益都会下降。
