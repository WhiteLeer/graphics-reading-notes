# Migration to OpenGL ES 2.0（迁移到 OpenGL ES 2.0）

## 章节内容

作者：Ken Catterall

本章介绍如何把 OpenGL ES 1.x 的固定功能渲染迁移到 OpenGL ES 2.0 的可编程管线。核心变化不是简单替换几个 API，而是把原来由图形 API 隐式完成的矩阵、光照、纹理组合和顶点处理，明确拆分到 Vertex Shader、Fragment Shader 以及应用程序自己的资源绑定代码中。

本章针对的是 2009 年左右的移动 GPU 和 OpenGL ES 2.0。虽然具体 API 和硬件限制已经过时，但从固定管线迁移到 Shader 管线的思维方式仍然适用于理解现代移动渲染。

## 固定功能管线与可编程管线

OpenGL ES 1.x 中，开发者通过 API 配置状态：

```text
设置矩阵
设置光源
设置材质
启用纹理
设置纹理组合方式
提交顶点
```

图形驱动会在内部完成顶点变换、光照、纹理环境组合和最终颜色计算。

OpenGL ES 2.0 则要求开发者提供 Shader：

```text
应用程序准备数据和 uniform
        ↓
Vertex Shader 处理顶点
        ↓
光栅化与插值
        ↓
Fragment Shader 计算颜色
```

因此迁移的本质是把隐式固定功能状态变成显式的数据和程序。

## 上下文和 EGL 配置

创建 OpenGL ES 2.0 上下文时，需要：

- 在 EGL 配置中指定 `EGL_OPENGL_ES2_BIT`；
- 在上下文属性中指定 `EGL_CONTEXT_CLIENT_VERSION = 2`；
- 创建并链接 Vertex Shader 和 Fragment Shader；
- 查询 uniform 和 attribute 的位置。

如果上下文仍按照 ES 1.x 创建，即使 Shader 代码正确，也可能无法得到预期的可编程管线行为。

## 矩阵迁移

### OpenGL ES 1.x

固定管线会维护 ModelView 和 Projection 矩阵栈：

```text
glMatrixMode(GL_MODELVIEW)
glLoadIdentity()
glRotatef(...)
glTranslatef(...)
```

### OpenGL ES 2.0

应用程序自己创建矩阵，并将最终矩阵传给 Vertex Shader：

```text
MVP = Projection × View × Model
```

Vertex Shader 中执行：

```glsl
gl_Position = myMVPMatrix * myVertex;
```

通常会在 CPU 端预先组合矩阵，避免每个顶点重复做矩阵乘法。

## 顶点数据迁移

固定管线的 Client State 数组需要改成 Shader attribute：

- 顶点位置 → `attribute vec4`；
- 法线 → `attribute vec3`；
- 纹理坐标 → `attribute vec2`；
- 切线、颜色等 → 额外 attribute。

应用程序通过 `glEnableVertexAttribArray` 和 `glVertexAttribPointer` 绑定这些数据。

迁移后，顶点布局不再由固定功能状态隐式解释，而是由 Shader 输入和应用程序的 attribute location 明确约定。

## 固定功能光照迁移

在 ES 1.x 中，光照通过：

```text
启用 GL_LIGHTING
设置 GL_LIGHT0
设置光源方向
设置材质漫反射颜色
```

在 ES 2.0 中，需要自己实现光照计算。

典型的顶点漫反射流程是：

1. 将顶点位置变换到裁剪空间；
2. 使用 ModelView 逆转置矩阵变换法线；
3. 将法线与光照方向点乘；
4. 将光照强度传给 Fragment Shader；
5. 用基础颜色乘以光照强度。

```glsl
transNormal = modelViewIT * myNormal;
lightValue = max(dot(transNormal, lightDirection), 0.0);
```

## 为什么法线要使用逆转置矩阵

位置可以直接乘 ModelView 矩阵，但法线不能总是这样做。

如果 Model 矩阵包含非均匀缩放：

```text
x 方向放大 2 倍
y 方向保持不变
```

直接用 ModelView 变换法线会使法线不再垂直于表面。正确做法是使用 ModelView 的逆转置矩阵：

```text
NormalMatrix = transpose(inverse(ModelView))
```

这是从固定功能光照迁移到自定义 Shader 时最重要的数学细节之一。

## 纹理采样迁移

ES 1.x 中只需启用纹理并提交纹理坐标。ES 2.0 中需要显式执行：

1. 将纹理坐标作为 Vertex Attribute；
2. 从 Vertex Shader 传给 Fragment Shader；
3. 将纹理单元编号绑定到 sampler uniform；
4. 在 Fragment Shader 中调用 `texture2D`。

```glsl
varying mediump vec2 uv;
uniform sampler2D sampler2d;

void main()
{
    gl_FragColor = texture2D(sampler2d, uv);
}
```

## 多纹理与材质组合

固定功能管线依靠 `TEXTURE_ENV_MODE`、`GL_ADD`、`GL_MODULATE` 等预定义组合方式。复杂组合往往需要反复试验状态设置。

ES 2.0 中可以直接在 Fragment Shader 中控制：

```glsl
color = mix(textureA, textureB, ratio);
```

这使得以下效果更容易实现：

- 两张纹理按权重混合；
- 随时间变化的材质过渡；
- 基于遮罩的材质切换；
- 自定义颜色叠加和乘法；
- 多层材质与程序化组合。

## 从固定功能到高级效果

可编程管线不仅是迁移成本，也打开了固定管线难以实现的效果：

- Cubemap 反射；
- 法线贴图和凹凸映射；
- 顶点纹理采样；
- Displacement Mapping；
- 后处理、模糊和 Bloom；
- 自定义多纹理混合；
- 更复杂的光照模型。

例如 Cubemap 反射可以在 Vertex Shader 中计算反射方向，再在 Fragment Shader 中使用 `textureCube` 查询环境颜色。

法线贴图则需要额外的切线数据，将光照方向变换到切线空间，再使用纹理中的法线进行逐像素光照。

## 精度限定符

OpenGL ES 2.0 为移动 GPU 提供了精度限定符：

- `highp`：高精度，成本和功耗可能更高；
- `mediump`：中等精度，通常适合位置、方向和一般计算；
- `lowp`：低精度，适合颜色或范围有限的数据。

精度并不是纯粹的代码风格问题，它会影响：

- 数值范围；
- 插值精度；
- 计算稳定性；
- 寄存器和功耗；
- 不同移动 GPU 上的兼容性。

但不能机械地把所有变量都改成 `lowp`。矩阵、深度、长距离位置和高频法线计算可能需要更高精度。

## FBO 与后处理

OpenGL ES 2.0 的 Framebuffer Object 可以把场景渲染到纹理，再用 Fragment Shader 进行后处理：

```text
场景渲染到 FBO
→ 读取颜色纹理
→ 全屏四边形
→ 执行 Blur、Bloom 或颜色空间转换
→ 输出到屏幕
```

这为移动设备上的后处理效果提供了统一基础，但需要注意移动 GPU 的带宽、Render Target 切换和纹理采样成本。

## 现代视角下的迁移边界

本章的具体 API 对现代项目存在时代限制：

- 现代 OpenGL ES 3.x 支持更多纹理、整数和 MRT 功能；
- Vulkan、Metal 和现代 GLES 更强调显式资源绑定；
- 现代引擎通常已经封装了矩阵、材质和 Shader 管理；
- 手机 GPU 架构和精度行为也已发生变化。

但核心迁移原则仍然成立：

```text
固定状态
→ 显式资源
→ 显式 Shader 输入
→ 明确的顶点变换和光照逻辑
→ 明确的 Fragment 输出
```

## 代价与限制

1. 开发者需要自己维护矩阵、光照和材质数据。
2. Shader 资源、uniform 和 attribute 的绑定更复杂。
3. 精度限定符可能造成不同设备上的差异。
4. 移动 GPU 对纹理带宽、分支和寄存器压力较敏感。
5. 旧设备对 Shader 指令、纹理格式和动态分支的支持有限。
6. 直接把固定功能效果机械翻译成 Shader，通常还需要针对移动硬件重新优化。

## 本章结论

从 OpenGL ES 1.x 迁移到 2.0 的本质，是从“配置固定功能状态”转向“自己实现渲染管线”。矩阵、法线、光照、纹理和颜色组合都变成显式的数据与 Shader 逻辑。

这会增加初始开发工作，但换来了对渲染过程的完整控制，也使多纹理、法线贴图、Cubemap、位移和后处理等效果更容易实现。虽然本章 API 属于较早的移动图形时代，但它清楚展示了现代可编程渲染管线的基础思想。
