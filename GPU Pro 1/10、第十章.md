# Virtual Texture Mapping 101（虚拟纹理映射入门）

## 章节内容

本章介绍一种类似操作系统虚拟内存的纹理管理系统：把超大纹理切成许多 Tile/Page，只把当前视点真正需要的部分加载到 GPU 的 Tile Cache 中，其余数据保留在磁盘或主存中。

作者：Matthäus G. Chajdas、Christian Eisenacher、Marc Stamminger、Sylvain Lefebvre。

## 核心问题

现代游戏的纹理数量和分辨率不断增长，但 GPU 显存还要同时容纳几何、后处理、光照和其他临时资源。如果整张大纹理全部上传，会带来：

- 显存不足；
- 初始加载时间过长；
- 大量当前屏幕不可见的数据占用显存；
- 世界切换和摄像机快速移动时的 IO 峰值。

虚拟纹理的目标是让纹理显存需求更多地依赖当前屏幕所需的区域，而不是依赖整个世界纹理的总尺寸。

## 虚拟纹理的三层结构

### Virtual Texture

逻辑上的超大纹理空间。场景材质使用的是它的虚拟 UV，而不是显存中某个固定纹理位置。

### Tile Cache

GPU 中实际存在的一张或多张大纹理，被切分为固定大小的物理 Tile。不同虚拟纹理或不同 MIP 层的 Tile 都可以放入这个缓存。

### Indirection Texture / Page Table

间接纹理记录：

```text
虚拟 Tile → 物理 Tile Cache 中的位置
```

Shader 首先查询 Page Table，再根据返回的物理位置到 Tile Cache 中采样。

## 每帧的基本流程

```text
1. 用特殊 Shader 渲染可见几何
2. 输出当前屏幕需要的 Tile ID 和 MIP 等级
3. CPU 读取反馈，找出尚未缓存的 Tile
4. 从磁盘或系统内存加载 Tile
5. 上传到 GPU Tile Cache
6. 更新 Indirection Texture
7. 正常渲染，并通过 Page Table 重定向纹理采样
```

其中第 1 步直接渲染实际场景几何，因此深度测试自然可以处理遮挡，不只是简单地把视锥体内所有纹理都请求一遍。

## “可见”的准确含义

本章中的可见 Tile 主要是当前屏幕实际覆盖到、并且按屏幕投影尺寸需要某个 MIP 等级的 Tile。

它比“加载相机附近的整张纹理”更精细，但通常仍是屏幕像素级请求的聚合结果，不一定精确到每个最终可见像素。因为一个 Tile 通常覆盖多个像素，所以系统会适当过取一些区域来减少请求数量和管理开销。

还可以扩大一点视场范围进行预取，让摄像机即将看到的区域提前加载，减少转身或快速移动时的低清晰度。

## MIP 和 Tile ID

Tile 请求不仅包含二维位置，还包含 MIP 层级。MIP 选择取决于虚拟 UV 在屏幕上的梯度：

- 屏幕上占用很大的区域，需要更高分辨率 Tile；
- 远处或缩小后的区域，只需要低分辨率 Tile；
- 相机快速移动时，可先加载粗层级，再逐渐替换成细层级。

因此，虚拟纹理不仅是“把大图切成小图”，还同时承担了分页和分辨率管理。

## Page Fault 与遮挡处理

缺失 Tile 可以通过特殊 Shader 生成 Tile ID。由于这个 Pass 使用真实场景几何和深度测试，被遮挡的表面不会产生请求，因此比单纯根据物体列表加载更节省。

为了减少反馈带宽，可以以低于屏幕分辨率的尺寸生成 Tile ID，因为一个 Tile 通常对应多个屏幕像素。也可以使用扩大后的视场角进行预取。

## Tile Cache 管理

当 Tile Cache 满时，需要回收旧 Tile。常见策略包括：

- LRU（最近最少使用）；
- 回收屏幕占用很小的 Tile；
- 回收颜色变化很小的 Tile；
- 用低分辨率祖先 Tile 替换高分辨率 Tile；
- 优先保留当前画面和即将进入画面的区域。

缓存太小会产生 Thrashing：摄像机移动一次就不断换入换出相同区域，导致 IO 和上传开销增加。

## 缺失 Tile 的处理

不能因为 Tile 尚未加载就让画面出现空洞或停顿等待 IO。系统通常让 Page Table 回退到已经存在的父 Tile：

```text
高分辨率 Tile 未到达
        ↓
使用较粗的父级 MIP Tile
        ↓
细 Tile 到达后再替换
```

最粗层级始终保留在 Cache 中，因此任何区域都能得到一个有效的 fallback。为了让画质渐进恢复，加载顺序通常是从粗到细，类似渐进式 JPEG。

## 纹理采样流程

正常渲染时，Shader 先用虚拟 UV 查询 Indirection Texture，得到：

- Tile Cache 中的物理位置；
- 当前实际可用的 MIP 分辨率。

然后计算 UV 在该 Tile 内的偏移，再到 Tile Cache 中采样。由于实际可用的分辨率可能低于理论 MIP 等级，Shader 需要使用 Page Table 返回的真实分辨率，而不能盲目使用原始 MIP 计算结果。

## Tile 边界和过滤

这是虚拟纹理最容易出问题的部分。虚拟纹理中相邻的 Tile 在 Tile Cache 中通常并不相邻，因此硬件过滤器看到的物理纹理坐标可能发生巨大跳变，导致：

- MIP 选择错误；
- 过滤范围过大；
- Tile 接缝变模糊；
- 相邻 Tile 颜色互相渗漏。

解决方法包括：

- 根据原始虚拟 UV 手动计算梯度；
- 按实际 Tile 分辨率缩放梯度；
- 为每个 Tile 添加边界像素；
- 压缩时使用足够宽的边界，避免压缩块跨边缘产生色差；
- 在 Tile Cache 中保留适合硬件过滤的布局。

## 压缩和 IO

Tile Cache 可以使用 GPU 友好的压缩格式来降低显存和上传带宽。磁盘端则可以使用更高压缩率的 JPEG 等格式，再在加载时转码为 GPU 压缩格式。

但如果每个 Tile 都是独立小文件，磁盘 seek 和文件管理成本会很高，因此实际系统通常会把大量 Tile 打包到容器文件中，并维护索引。

## 与普通纹理 Streaming 的区别

普通 Streaming 往往以整张纹理或整级 MIP 为单位加载；虚拟纹理以 Tile 为分页单位：

| 方案 | 加载粒度 | 适合场景 |
| --- | --- | --- |
| 普通纹理 Streaming | 纹理、资源或整级 MIP | 物体数量有限、纹理规模中等 |
| Virtual Texture | 局部 Tile/Page | 超大地形、唯一纹理、开放世界 |

虚拟纹理减少的是纹理数据驻留和加载压力，不会自动减少场景中的三角形、物体数量或 Shader 计算。

## 代价与限制

- 需要 Page Table、Tile Cache 和异步 IO 系统；
- 每帧生成反馈和更新缓存会带来 CPU/GPU 同步成本；
- 摄像机快速转向可能请求大量 Tile，产生 IO 峰值；
- Cache 太小会发生频繁换入换出；
- Tile 边界过滤和压缩容易产生接缝；
- 缺失 Tile 的 fallback 会导致暂时的低分辨率；
- 多张材质纹理需要协调分页，否则颜色、法线和粗糙度可能分辨率不一致。

## 本章结论

虚拟纹理的核心是：

> 把超大纹理划分为 Tile，通过可见性反馈和 MIP 需求，只把当前屏幕需要的局部数据放入 GPU Cache，并用 Page Table 将虚拟 UV 重定向到物理 Tile。

它比普通纹理 Streaming 更细粒度，但也需要额外的分页、缓存、IO、回退和过滤系统。它解决的是“纹理太大、显存放不下”，不是通用的几何或渲染性能优化。
