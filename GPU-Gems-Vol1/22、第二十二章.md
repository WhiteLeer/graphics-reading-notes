# 颜色调整
## 1. 这章解决的问题

前面渲染得到的通常是 HDR、线性空间中的结果。它可能包含远大于 1 的亮度，但显示器和普通 8-bit 颜色缓冲区无法直接表示这么大的范围。因此需要一组“颜色控制”操作，把渲染结果调整成最终可显示、可艺术控制的图像。

这里容易混淆几个概念：

- **Exposure（曝光）**：整体乘一个亮度因子，模拟相机曝光或调整场景亮暗。
- **Tone Mapping（色调映射）**：把 HDR 的大动态范围压缩到显示范围，重点是处理高光、暗部和中间调的关系。
- **Color Grading（调色）**：改变色相、饱和度、对比度、风格和局部颜色关系。
- **Gamma / sRGB 编码**：把线性光转换为适合显示和存储的非线性编码；它不是 Tone Mapping。

一个常见的概念流程是：

```text
线性 HDR
  -> 曝光
  -> Tone Mapping
  -> 调色 / LUT
  -> Gamma 或 sRGB 编码
  -> 显示
```

实际引擎可能根据颜色管理方案调整 Tone Mapping 和调色的先后，但“动态范围压缩”和“显示编码”必须区分。

## 2. 为什么不能直接 Clamp

最简单的做法是：

```hlsl
color = saturate(hdrColor);
```

这会把所有大于 1 的值直接截成 1。这样虽然能输出到 LDR，但高光区域的不同亮度会全部变成同一个白色，云、金属高光、灯光等细节消失，结果通常很生硬。

Tone Mapping 的核心就是使用连续曲线，把较大的 HDR 值压缩到 `[0, 1]`，尽可能保留亮度层次。

## 3. 常见 Tone Mapping 算法

### 3.1 Reinhard

最经典的简单算子：

```text
L_out = L_in / (1 + L_in)
```

特点：

- 实现非常便宜；
- 输出天然落在 `[0, 1)`；
- 高光压缩平滑，不容易突然溢出；
- 但整体容易发灰、对比度偏低，白色也可能不够“白”。

扩展形式会用一个白点控制何时接近白色：

```text
L_out = L_in * (1 + L_in / L_white^2) / (1 + L_in)
```

### 3.2 Filmic / Hable

Filmic 曲线通常模仿电影胶片的响应，常见形状是：

- 暗部有 **toe**，避免黑位过硬；
- 中间有较平滑的近似线性区域；
- 高光有 **shoulder**，逐渐压缩而不是直接变白。

Uncharted 2 中常见的 Hable 曲线可写成：

```text
f(x) = ((x * (A*x + C*B) + D*E) / (x * (A*x + B) + D*F)) - E/F
```

其中 `A~F` 控制曲线的肩部、线性段和黑位。实际使用时还需要用白点或曝光参数归一化，否则曲线输出的范围和亮度会不合适。

它比 Reinhard 更有“电影感”，但参数和颜色管理更复杂，也不等于自动就能得到好看的画面。

### 3.3 ACES

ACES 首先是完整的颜色管理和标准化色彩流程，不应简单等同于某一条公式。实时引擎里常见的“ACES Tonemapping”往往是它的拟合曲线或简化实现。

常见的实时拟合形式类似：

```text
color_out = (color * (2.51 * color + 0.03)) /
            (color * (2.43 * color + 0.59) + 0.14)
```

工程上要注意：这只是某种实时近似，不能代表完整 ACES 流程。ACES 风格通常能较好地压缩高光、保持电影式对比度，但可能改变高饱和颜色，尤其需要关注红色、橙色等区域是否出现偏色或过度去饱和。

### 3.4 AgX

AgX 是较新的视图变换 / Tone Mapping 方案，在 Blender 4.x 等工具中被采用。它不是简单的一行 `x/(1+x)` 曲线，而是结合了颜色空间变换和分段映射，更重视：

- 高光颜色的保留；
- 高饱和颜色在压缩时不突然变白；
- 不同曝光下的稳定性；
- 更自然的中间调和高光过渡。

因此应把 AgX 理解为一套颜色管理视图变换，而不是只换一个标量公式。

### 3.5 Neutral、Lottes、Uchimura 等

还有 Neutral、Lottes、Uchimura 等曲线。它们没有绝对的“最好”，通常是在以下目标之间取舍：

- 高光细节；
- 暗部可见度；
- 中间调对比度；
- 白点是否稳定；
- 高饱和颜色是否变灰或偏色；
- 指令数量和移动平台性能。

选择时应结合实际场景、曝光范围、艺术方向和目标设备，用截图或自动化测试比较，而不是只看名称。

## 4. Tone Mapping 与 Bloom 的顺序

Bloom 通常需要在 Tone Mapping 之前从 HDR 图像提取高亮区域：

```text
HDR 场景颜色
  -> 提取高亮
  -> 降采样与模糊
  -> 加回原 HDR 图像
  -> Tone Mapping
  -> 输出到 LDR
```

如果先 Tone Mapping，再提取高亮，许多原本大于 1 的亮度已经被压进 `[0,1]`，Bloom 的能量和范围会改变，效果往往不稳定。具体引擎也可能提供不同的后处理顺序，但核心原则是：尽量在 HDR 阶段完成依赖真实亮度范围的效果。

## 5. 颜色控制的常见实现

### 5.1 亮度、对比度、饱和度

这些操作通常在全屏后处理 Pass 中完成。亮度可以是加法或乘法；对比度一般围绕某个中灰值缩放；饱和度则把颜色与亮度或灰度值插值：

```text
color_out = lerp(luminance(color), color, saturation)
```

实际实现要注意使用正确的颜色空间。直接在 sRGB 编码值上做物理意义上的亮度运算，结果通常不正确；涉及光强的计算应在线性空间进行。

### 5.2 颜色矩阵

通道之间的线性变换可以写成 3×3 矩阵：

```text
rgb_out = M * rgb_in
```

它适合做色彩空间转换、通道混合和一部分风格调整。若还要加入偏移量，则使用 4×4 矩阵或额外的加法项。

### 5.3 1D LUT 与 3D LUT

- **1D LUT**：每个通道独立映射 `R->R、G->G、B->B`，适合曲线、Levels、Gamma 等操作。
- **3D LUT**：输入的 `R、G、B` 一起决定输出颜色，能够表达通道之间的复杂耦合，适合电影调色和复杂风格变换。

3D LUT 本质上是一张颜色查找表，不是贴图材质意义上的普通纹理；GPU 中通常把它作为 3D Texture 采样，并使用三线性插值。它能把复杂调色从运行时大量计算变成一次查表，但会受 LUT 分辨率、插值误差和额外采样影响。

## 6. 工程上的结论

- Tone Mapping 不是把透明材质变成 Opaque，也不是 Gamma 校正；它是 HDR 到显示范围的动态范围压缩。
- Tone Mapping 无法恢复已经被 Clamp 或低精度缓冲截掉的 HDR 信息，因此应尽量保留 HDR 精度到后处理阶段。
- 算法越复杂不代表画面一定越好；曝光、材质能量、Bloom、调色和显示设备共同决定最终效果。
- 比较不同算子时，要同时看暗部、中间调、高光和高饱和颜色，并在目标平台上测性能。
- 颜色控制通常是后处理全屏 Pass，但很多参数也可以在材质、光照和曝光阶段影响最终结果；不能把所有“颜色问题”都推给 Tone Mapping。
