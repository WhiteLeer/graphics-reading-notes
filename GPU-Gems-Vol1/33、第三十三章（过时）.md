# RenderMan Shader 转为实时 Shader

## 1. 本章的核心问题

本章以《精灵鼠小弟》中的毛发 Shader 为例，讨论如何把生产级 RenderMan Shader 转成 Cg 硬件 Shader。

重点不是逐行翻译语法，而是：

> 离线 Shader 和实时 GPU Shader 的执行模型不同，转换时必须重新安排计算频率、数据流和近似方式。

RenderMan Shader 可以依赖离线渲染器提供的光源遍历、采样和上下文；GPU Shader 则需要明确区分 CPU、Vertex Shader 和 Fragment Shader 的职责，并受限于纹理、寄存器、指令和带宽。

## 2. RenderMan 与实时 Shader 的差异

RenderMan 中可以使用：

- `illuminance` 遍历满足条件的光源；
- 复杂的 ShadeOp；
- 更自由的采样和求值方式；
- 由渲染器提供的着色上下文。

实时 GPU Shader 通常需要：

- 明确光源数量或光源缓冲；
- 明确 Vertex Shader 和 Fragment Shader 的分工；
- 让每个顶点或片元以固定模型执行；
- 适配目标硬件的指令、寄存器和资源限制。

因此不能简单把 RenderMan 代码原封不动搬到 GPU。

## 3. 光源处理

RenderMan 的：

```c
illuminance(P, N, angle)
{
    // 对满足条件的光源执行
}
```

在早期 Cg 中没有直接对应的机制。

### 3.1 固定数量的光源数组

```cg
uniform float3 lightDir[10];
```

然后遍历并累加。缺点是光源数量写死，超过上限需要改 Shader，光源类型变化时也难以扩展。

### 3.2 多 Pass 光源累加

每个 Pass 只绑定一个光源：

```text
Pass 1 -> 光源 A
Pass 2 -> 光源 B
Pass 3 -> 光源 C
```

再把结果加到同一个 Render Target。

优点是 Shader 参数简单，光源数量由应用管理；缺点是每个光源都要重复执行顶点、片元、材质和纹理计算，光源多时性能迅速下降。

现代 Forward+、Tiled、Clustered 和 Deferred Lighting 已经用 GPU 光源列表和空间剔除改善了这个问题。

## 4. Vertex Shader 和 Fragment Shader 的分工

RenderMan 可以用一个 Surface Shader 描述完整材质，但实时 GPU 通常拆成：

```text
Vertex Shader
    -> 处理顶点
    -> 计算并输出插值数据

Fragment Shader
    -> 处理片元
    -> 计算最终颜色
```

毛发例子中，Vertex Shader 可以准备：

- 光照方向 `L`；
- 视线方向 `V`；
- 毛发切线 `T`；
- 法线；
- 发根到发梢的参数。

Fragment Shader 再计算毛发高光、颜色变化和最终亮度。

## 5. 把计算从 Fragment Shader 移到 Vertex Shader

假设场景有：

```text
10,000 个顶点
1,000,000 个片元
```

如果某项计算可以在顶点之间近似插值：

```text
Vertex Shader 计算 -> 10,000 次
Fragment Shader 计算 -> 1,000,000 次
```

因此类似下面的计算：

```hlsl
float tDotL = saturate(dot(tangent, lightDir));
float tDotV = saturate(dot(tangent, viewDir));
```

如果曲线采样足够密、相邻顶点变化平滑，就可以放到 Vertex Shader，再插值给 Fragment Shader。

代价是精度降低。顶点稀疏或曲率变化大时，插值会产生误差，因此需要增加几何采样或保留片元计算。

## 6. 用 LUT 替代复杂数学函数

本章把毛发的 Kajiya-Kay 高光项预先制作成查找表：

```text
输入：dot(T, L)、dot(T, V)
    -> 采样 Kajiya-Kay LUT
    -> 得到高光项
```

运行时把复杂函数变成纹理采样：

```hlsl
float2 uv = float2(dotTL, dotTV);
float2 kajiya = tex2D(kajiyaLUT, uv);
```

这是：

```text
复杂计算
    -> 离线预计算
    -> 运行时查表
```

适合高次幂、复杂曲线、近似 BRDF 和特殊衰减函数，但会受到 LUT 分辨率、插值误差、额外采样和输入范围的限制。

## 7. 向量化

多个相似计算可以组织成向量形式：

```hlsl
float2 powValue = pow(Kajiya, roughness);
```

再使用向量乘法和点积同时处理多个分量。这可以利用 GPU 的 SIMD/SIMT 结构。现代编译器有时会自动完成类似优化，但合理的数据组织仍有助于生成高效代码。

## 8. 条件分支

本章针对当时的 GPU 指出 Fragment Shader 中的 `if/else` 可能无法真正跳过不需要的分支，甚至两个分支都被执行。

现代 GPU 已经支持更复杂的动态分支，但仍需要注意：

- 同一 Warp/Wave 内分支不一致会产生分歧；
- 分支两侧都很复杂时收益有限；
- 随机分支会降低执行效率；
- 编译器可能把简单分支转成条件选择。

因此不能假设写了 `if` 就一定比无分支版本快，必须通过目标 GPU 的 Profile 验证。

## 9. 结果与取舍

本章通过：

- 把计算从片元移到顶点；
- 使用 LUT；
- 重新组织向量计算；
- 简化分支和表达式；
- 减少 Fragment Shader 指令；

将初始 Fragment Shader 从约 104 条指令减少到约 42 条。最终图像与 RenderMan 有一定差异，但毛发的主要高光、颜色变化和视觉特征仍然保留。

对于数量极大的毛发，甚至进一步把完整毛发计算放入 Vertex Shader，以牺牲部分精度换取性能。

## 10. 工程上的转换方法

把离线 Shader 转成实时 Shader 时，应逐项判断：

```text
这项计算应该在哪里做？
每帧、每物体、每顶点还是每片元做？
能不能预计算？
能不能放入 LUT？
能不能用插值替代？
能不能用近似代替？
```

可以概括为：

```text
离线 Shader
    -> 拆分计算频率
    -> 分配到 CPU / Vertex / Fragment
    -> 用 LUT 和近似替代复杂函数
    -> 控制光源和材质组合
    -> 在质量和性能之间取舍
```

## 11. 工程上的结论

- 实时化不是语法翻译，而是重新设计执行位置和计算频率。
- Fragment Shader 中的工作量通常最昂贵，因为片元数量远多于顶点。
- 可以把平滑变化的计算移到 Vertex Shader，再通过插值传递。
- 可以用 LUT 把复杂数学函数转成纹理采样。
- 多光源处理要考虑固定数组、多 Pass、Deferred、Forward+、Tiled 和 Clustered 等方案。
- 现代 GPU 仍然需要在精度、指令、分支、带宽和视觉质量之间取舍。
