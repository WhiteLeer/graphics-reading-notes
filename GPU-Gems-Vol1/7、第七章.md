# 草地渲染

## 我的理解

这一章的核心是：不用真正建模和绘制数百万根完整草叶，而是用少量几何、透明纹理和顶点动画表现大面积草地。

进一步讨论 3A 游戏后，我的理解可以扩展为：草地可以完全由 GPU 程序化生成，也可以使用美术制作的草簇；实际项目通常将两者以及 LOD、剔除、风场和交互混合使用。

## GPU Gems 的基础方案

### 1. 使用草叶纹理

先制作一张包含多根草叶的透明纹理：

```text
草叶颜色 / Alpha
        ↓
映射到少量 Quad
        ↓
用一个 Quad 表现多根草叶
```

如果直接建模每一根草叶，大面积草地的三角形数量会非常高，而且大部分草叶在远处只占据很少的屏幕像素，没有必要保留完整几何细节。

### 2. 使用交叉的 Quad

单独放置一张草叶卡片，从侧面观察很容易变薄甚至消失。因此可以让多个 Quad 互相交叉，形成类似星形的 Grass Object：

```text
       /|
      / | \\
     /  |  \\
```

这样从不同方向观察时，都能看到一定数量的草叶。通常需要关闭背面剔除，使透明草叶从正反两面都可见。

这是一种用二维纹理模拟三维密度的方案，本质上不是把每根草叶都建模出来。

### 3. 批量铺设 Grass Object

Grass Object 可以按照地形、密度图、材质和随机种子铺设到大片区域中。随机化可以作用于：

- 位置；
- 旋转；
- 缩放；
- 纹理翻转；
- 颜色和亮度；
- 动画相位。

随机化的主要作用是隐藏重复，而不是代替几何生成。

## 为什么不直接使用 Geometry Shader？

这里需要区分两个概念：

```text
GPU 程序化生成几何
    ≠
    API 意义上的 Geometry Shader
```

Geometry Shader 确实可以接受一个点或简单图元，然后扩展出草叶几何。但它只是 GPU 生成几何的一种实现方式，面对大量草地时不一定是性能最好的方案。

还可以使用：

- Vertex Shader 根据实例 ID 变形固定 Quad；
- Compute Shader 生成草叶数据；
- Indirect Draw 批量绘制；
- Tessellation；
- Mesh Shader；
- 预先生成基础网格，再由 GPU 程序化调整。

因此，如果“几何着色器”是广义的“GPU 程序化生成几何”，那么可以说草地能够由 GPU 完全程序化生成；如果严格指 Geometry Shader，则不能直接认为所有现代 3A 草地都使用它。

## Shader 如何让草摆动？

关键是只移动草的顶部，底部保持固定在地面上。

```text
草根：位移权重为 0
草尖：位移权重为 1
```

可以利用 UV 的某个分量表示高度权重：

```hlsl
float weight = saturate(vertexUV.y);
float wave = sin(time * speed + worldPosition.x * frequency);
position += windDirection * wave * strength * weight;
```

更自然的风摆通常还会考虑：

- 时间；
- 世界位置；
- 风向；
- 风力；
- 草的高度；
- 多个频率的噪声；
- 每个草对象的随机相位。

如果所有草都只使用同一个 `sin(time)`，整片草会同步摆动，看起来像一块布。加入世界位置和随机相位后，才能形成连续的风浪和局部差异。

## 三种动画组织方式

### 按草簇动画

CPU 为每个草簇计算一个位移向量，再提交对应的 Draw Call。

优点：

- 可以使用复杂的 CPU 风场；
- 同一个簇内部的几何不会互相拉伸。

缺点：

- 簇越多，Draw Call 越多；
- 同一簇中的草同步运动，容易看出分组。

### 按顶点动画

将时间、风向和风力传给 Vertex Shader，每个顶点根据自己的位置计算位移。

优点：

- 可以用很少的 Draw Call 绘制大面积草地；
- 风浪可以在大片草地中连续传播。

缺点：

- 顶部顶点之间的距离可能发生变化，草叶会产生拉伸；
- Shader 中可使用的风场逻辑较复杂时会增加成本；
- 没有额外随机化时，局部运动可能过于一致。

### 按 Grass Object 动画

每个 Grass Object 使用自己的中心位置或随机值计算位移。同一个 Grass Object 内部保持形状稳定，不同对象之间又有不同的运动。

这是一个折中方案：

```text
按簇动画：自然度较低，Draw Call 较多
按顶点动画：Draw Call 少，但容易拉伸
按 Grass Object：Draw Call 少，形状稳定，局部有差异
```

## 3A 游戏中的完整方案

像《对马岛之魂》这样的 3A 游戏，通常不会只使用“预制草簇 + 顶点 Shader”，而会把多个层次结合起来：

```text
近景
    GPU 程序化生成独立草叶
    + 较高几何细节
    + 单独动画和风场

中景
    实例化草叶或草簇
    + 简化几何
    + 批量绘制

远景
    低模、草叶卡片、地表颜色和纹理
    + 更激进的 LOD
```

官方的《对马岛之魂》技术演讲说明，他们在 GPU 上生成大量独立草叶，并让每根草拥有程序化外观和动画，而不是简单复制几个预制草簇。[Procedural Grass in Ghost of Tsushima](https://gdcvault.com/play/1027033/)

但这不代表完全没有美术制作的资产。官方介绍还提到，游戏中的草地和芒草田混合使用了程序生成的三角形草叶，以及手工制作的芒草茎秆和草簇等内容。[PlayStation 官方介绍](https://blog.playstation.com/?p=345372)

因此它更接近：

```text
程序化布局
    + GPU 生成草叶
    + GPU 剔除
    + 实例化 / 间接绘制
    + 顶点或网格动画
    + 多级 LOD
    + 美术制作的特殊植被
    + 交互式位移
```

## GPU 剔除和间接绘制

真正的问题不是“如何把草摆出来”，而是“如何不处理看不见的草”。常见流程是：

```text
候选草叶位置
    ↓
视锥剔除
    ↓
距离剔除 / LOD
    ↓
遮挡或地形区域判断
    ↓
生成间接绘制参数
    ↓
GPU 批量绘制可见草叶
```

如果每根草都由 CPU 单独提交 Draw Call，即使单根草的几何非常简单，也会被提交开销拖慢。因此现代实现一般会把大量草叶组织为实例数据，通过一次或少量 Indirect Draw 批量绘制。

这和前面讨论的 GPU Driven 是同一个方向：

```text
CPU：准备区域、材质、风场和候选数据
GPU：剔除、生成、动画、批量绘制
```

## 风场和交互

大面积草地不能只使用一个全局正弦波，否则会产生整齐的同步运动。更好的方法是叠加多个尺度：

```text
大尺度噪声
    → 整片草地的风浪

中尺度纹理 / 流场
    → 局部风向变化

小尺度随机值
    → 每个草对象的细节差异
```

《对马岛之魂》的公开资料提到，他们使用大尺度滚动噪声和地形上的小尺度纹理共同影响草、树和灌木，使不同植被共享一致的风感；玩家和马匹经过时，再通过粒子系统控制局部草地位移，并使用阻尼波让草逐渐恢复。[PlayStation 官方介绍](https://blog.playstation.com/?p=345372)

## 本章总结

```text
大面积草地
    = 少量或程序化生成的低模几何
    + 草叶纹理 / Alpha
    + GPU 批量生成与绘制
    + 视锥、距离和 LOD 剔除
    + 顶点或网格 Shader 风摆
    + 多尺度风场
    + 近景、中景、远景的不同表示
    + 角色和物体交互
```

最重要的结论是：

> 3A 草地可以不依赖预先制作的大量草簇，而由 GPU 程序化生成草叶；但 Geometry Shader 只是可能的实现手段，不等于整个方案。实际效果来自程序化几何、批量绘制、剔除、LOD、风场、美术资产和交互的组合。
