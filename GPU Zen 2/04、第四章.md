# Rendering Surgery Simulation with Vulkan（使用 Vulkan 渲染手术模拟）

## 章节内容

本章介绍一个手术模拟项目中的 Vulkan 渲染系统，重点不是单个 Shader 技巧，而是高层渲染架构如何影响 Render Pass、可变形网格、资源内存和同步设计。

作者：Nicholas Milef、Di Qi 和 Suvranu De

## 核心思路

手术模拟场景包含器械、组织和其他可变形对象。它们会频繁更新几何和材质数据，因此渲染器必须同时处理：

- 动态几何更新；
- 多个渲染阶段；
- GPU/CPU 资源同步；
- Vulkan 显式内存管理；
- 实时帧率与模拟计算之间的竞争。

渲染系统不是把所有内容放在一个巨大 Pass 中，而是根据模拟和画面需求组织多个阶段，并显式安排资源依赖和布局转换。

## Render Pass 架构

Render Pass 需要描述：

- 哪些颜色和深度附件会被使用；
- 每个附件的加载、清除和保存方式；
- 不同 Subpass 之间的数据依赖；
- 资源何时可以被读写；
- 哪些结果可以在片上或帧内继续复用。

合理的 Pass 设计可以减少不必要的内存读写，但如果把互不相关的阶段强行合并，也会增加同步和资源管理复杂度。因此 Render Pass 结构必须与实际数据流保持一致。

## 可变形网格

手术模拟中的组织会发生形变，渲染器需要频繁更新顶点位置、法线和相关属性。常见处理思路包括：

- 将模拟结果写入 GPU 可访问的动态 Buffer；
- 区分静态拓扑和动态顶点数据；
- 只更新变化的资源范围；
- 通过同步保证模拟写入完成后渲染才能读取；
- 对组织表面、切割区域和器械使用不同的渲染路径。

关键是避免每帧重新创建完整 Vulkan 资源，也避免 CPU 在更新数据时与 GPU 发生不必要的等待。

## 内存管理

Vulkan 不会替应用自动隐藏资源内存细节，因此需要显式管理：

- Buffer 和 Image 的内存分配；
- 内存类型与访问属性；
- 资源子分配和复用；
- staging Buffer 到 GPU-local 内存的传输；
- 动态资源的生命周期；
- 资源销毁与同步。

对于频繁变化的模拟数据，内存策略通常比单个 Shader 优化更重要。需要在 CPU 可写、GPU 可读和传输成本之间做取舍。

## 性能与同步

主要性能风险包括：

- 频繁上传可变形网格；
- CPU 等待 GPU 完成资源使用；
- 过多小型 Command Buffer 或资源切换；
- Render Pass 之间不必要的布局转换；
- 模拟计算和渲染同时争用 GPU。

Vulkan 的显式同步提供了更高控制力，但也要求开发者明确每个资源的读写阶段、访问掩码和布局状态。

## CCT 案例

章节最后通过 CCT 手术模拟案例说明完整系统如何落地，包括可变形组织、手术器械、动态更新和 Vulkan 渲染管线之间的协作。案例重点在于展示架构选择如何影响实际性能和实现复杂度。

## 本章结论

本章的重点是 Vulkan 渲染器的系统设计：对于包含可变形几何和实时模拟的应用，Render Pass 组织、资源生命周期、内存分配和同步策略必须一起设计。Vulkan 的优势是显式控制，但代价是开发者需要自己承担更多正确性和性能管理工作。
