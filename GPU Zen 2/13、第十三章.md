# Writing an Efficient Vulkan Renderer（编写高效的 Vulkan 渲染器）

## 章节内容

本章从通用引擎的角度讨论如何构建高效的 Vulkan 渲染器。重点不是某个具体画面效果，而是 Vulkan 中资源内存、Descriptor、Command Buffer、Pipeline Barrier 和 Render Pass 等底层机制如何共同影响 CPU/GPU 性能。

作者：Arseny Kapoulkine

## 核心思路

Vulkan 把许多原本由驱动隐式完成的工作交给应用程序，因此高效渲染器必须明确管理：

- GPU 内存类型和资源分配；
- Buffer、Image 与 staging 资源的生命周期；
- Descriptor Set 的布局、分配和复用；
- Command Buffer 的录制和提交；
- 资源状态、Pipeline Barrier 和跨队列同步；
- Render Pass 与附件加载/保存行为。

核心原则是减少运行时不必要的分配、状态切换、同步和重复命令，同时让资源布局尽量贴合 GPU 的实际访问模式。

## 内存管理

Vulkan 资源需要从不同 Memory Heap 和 Memory Type 中选择合适的存储位置：

- GPU 本地内存适合高频随机访问的静态资源；
- Host Visible 内存适合 CPU 持续更新的动态 Buffer；
- Staging Buffer 用于把 CPU 数据上传到 GPU 本地资源；
- Tile-based GPU 上，某些不会被保存的 MSAA 或深度附件可以使用 Lazy Allocation；
- 集成显卡的 CPU/GPU 物理内存可能是共享的，策略与独立显卡不同。

资源类型和访问频率比“永远放在显存”更重要。动态 Uniform Buffer 和顶点 Buffer 可以直接使用 Host Visible 内存，但随机访问量大的纹理或 Storage Buffer 通常更适合通过 staging 上传到 Device Local 内存。

## 内存子分配

大型应用不能为每个 Buffer 和 Image 都调用一次 `vkAllocateMemory`。单独分配会受到数量限制，增加驱动开销、对齐浪费和提交成本。

常见做法是：

1. 申请较大的 Vulkan 内存块；
2. 在块内部自行进行子分配；
3. 正确处理资源对齐；
4. 处理 Buffer 与 Image 之间的 `bufferImageGranularity` 约束；
5. 对大型 Render Target 或驱动建议的资源使用 Dedicated Allocation。

持久映射 Host Visible 内存可以减少频繁 Map/Unmap 的成本，但仍需要严格处理 CPU 写入与 GPU 读取之间的生命周期同步。

## Descriptor Set 管理

Descriptor Set 是 Vulkan 向 Shader 提供 Buffer、Image 和 Sampler 的主要方式。它既影响 CPU 更新成本，也影响 GPU 访问方式。

实践中通常需要：

- 根据更新频率拆分 Descriptor Set，例如帧级、材质级和对象级；
- 使用 Descriptor Pool 批量分配，而不是频繁单独释放；
- 在 Pool 耗尽时切换到新的 Pool；
- 根据真实管线统计配置 Pool 大小，避免按最坏情况导致大量浪费；
- 选择 Uniform Buffer、Storage Buffer、动态偏移和不同纹理 Descriptor 类型。

小型、访问模式固定的数据适合 Uniform Buffer；大型数组或动态索引资源更适合 Storage Buffer。Descriptor 的组织方式应服务于资源更新频率和绑定频率，而不是机械地为每个对象创建一套完整集合。

## Command Buffer 与提交

Command Buffer 录制本身也有 CPU 成本。渲染器需要在复用、并行录制和状态排序之间取平衡：

- 静态或低频命令可以缓存；
- 动态场景可以按线程或任务拆分录制；
- 通过排序减少 Pipeline、Descriptor 和 Render Pass 切换；
- 避免为了极少量绘制产生过多小 Command Buffer；
- 使用合适的提交批次，减少 CPU 与驱动交互。

多线程录制并不自动带来收益。如果工作粒度过小、同步过多，线程调度和命令合并成本可能抵消并行收益。

## Pipeline Barrier 与 Render Pass

Vulkan 不会自动推断资源何时从写入变成读取。应用需要明确：

- 资源之前由哪个阶段访问；
- 之后由哪个阶段访问；
- 使用何种访问类型；
- Image 当前处于什么 Layout；
- 是否可以通过 Render Pass Subpass Dependency 复用片上数据。

过少的 Barrier 会产生数据竞争，过多的 Barrier 则会阻塞并行执行。Render Pass 的附件 Load、Clear、Store 和布局转换也会直接影响带宽，特别是在移动端和 Tile-based GPU 上。

## 桌面端与移动端

独立显卡通常更重视 Device Local 内存、PCIe 上传和大带宽资源访问；移动端或集成显卡可能共享物理内存，并且更敏感于 Render Pass、片上缓存和附件保存。

因此不存在完全通用的单一最优策略。渲染器应根据设备类型、资源访问模式和实际 GPU/CPU Profiler 结果选择内存、Descriptor、同步和 Pass 结构。

## 性能与限制

- Vulkan 的显式控制不会自动保证更高性能；
- 错误的内存类型选择会导致 PCIe 访问或 GPU 缓存效率下降；
- 频繁分配和释放 Descriptor/Memory 会带来驱动开销；
- 过度使用 Barrier 会破坏 GPU 并行；
- 过细的 Command Buffer 拆分会增加 CPU 录制和提交成本；
- 复杂的跨平台抽象可能掩盖不同 GPU 架构的最佳策略。

## 本章结论

高效 Vulkan 渲染器的关键不是单独优化某一个 API 调用，而是建立一套与资源生命周期、访问模式和帧内数据流一致的管理体系：大块内存子分配、合理的 Descriptor 分层、可复用的命令录制、精确的 Barrier，以及针对设备架构调整的 Render Pass。

Vulkan 提供的是控制权，而不是自动优化。最终性能仍需要通过实际设备上的 CPU/GPU 测量来验证。
