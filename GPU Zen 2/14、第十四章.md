# glTF—Runtime 3D Asset Delivery（glTF：运行时 3D 资产交付）

## 章节内容

本章介绍 Khronos Group 的 glTF，以及它如何作为面向实时渲染的 3D 资产交付格式。glTF 不试图替代所有 DCC 交换格式，而是提供一种结构明确、容易解析、接近运行时数据布局的资产描述方式。

作者：Marco Hutter

## 核心定位

glTF 解决的是资产从内容生产工具到运行时程序之间的交付问题。它可以描述：

- 场景和节点层级；
- Mesh、顶点属性和索引；
- 材质和纹理；
- 骨骼蒙皮；
- Morph Target；
- 动画；
- 摄像机和扩展对象。

它不是为了保证 Blender、Maya、3ds Max、Unity 和 Unreal 内部 Transform 数值完全相同，而是通过统一的语义、单位和数据结构减少解释差异。

## glTF 与 FBX 的关系

FBX 仍然适合 DCC 之间交换复杂制作数据。glTF 更适合把已经整理好的资产交给游戏、Web、模型查看器或自研渲染器。

因此实际项目可以继续使用 FBX 作为制作和交换格式，再在资产处理阶段导出到 glTF 或引擎专用格式。若已有稳定的 FBX 管线，glTF 并不是必须替换它的理由。

## 文件组织

glTF 通常有两种交付形式：

- **`.gltf`**：JSON 描述文件，引用独立的 `.bin` 和 PNG/JPG 纹理；
- **`.glb`**：将 JSON、二进制 Buffer 和纹理打包到一个二进制文件中，方便传输和部署。

JSON 部分描述场景结构、资源引用、材质参数和 Buffer 的解释方式。二进制数据中存储顶点、索引、动画关键帧、骨骼权重等内容，纹理可以作为外部文件，也可以嵌入二进制资产。

## Buffer 与 Accessor

glTF 使用 Buffer、BufferView 和 Accessor 描述二进制数据：

- Buffer 是底层二进制存储；
- BufferView 描述其中一段连续范围；
- Accessor 描述这段数据应当如何解释，例如元素数量、向量维度、数据类型和步长。

例如同一个二进制文件中可以同时存放位置、法线和索引，Accessor 会告诉运行时哪些字节是三维浮点位置，哪些字节是三十二位索引。这样的布局通常可以直接上传到 GPU Buffer，减少额外转换。

## 坐标、单位和变换

核心规范约定：

- 右手坐标系；
- Y 轴向上；
- 资产正面沿正 Z 方向；
- 长度和距离以米为基本单位；
- 旋转可以使用四元数表达。

这些约定减少了不同查看器和运行时之间的歧义，但目标软件仍可能在导入时转换到自己的坐标系。例如 Unreal 通常需要进行轴向和厘米单位转换，Unity 也可能根据导入策略调整坐标和根节点。

## Mesh、蒙皮与动画

Mesh 可以是点、线或三角形，也可以使用索引。核心顶点属性包括：

- Position；
- Normal；
- Tangent；
- Texture Coordinate；
- Vertex Color；
- Joint Indices；
- Joint Weights。

Morph Target 通过保存相对基础网格的差异来表达变形；骨骼蒙皮则通过节点层级、关节索引和权重影响顶点位置。动画由关键帧、Sampler 和 Channel 组成，可以驱动节点变换或 Morph Target 权重，并支持阶梯、线性和三次样条插值。

## PBR 材质

glTF 核心材质使用 Metallic-Roughness PBR 模型，常见属性包括：

- Base Color；
- Metallic；
- Roughness；
- Normal；
- Occlusion；
- Emissive；
- Alpha 和透明模式。

此外可以通过扩展支持 Specular-Glossiness 等其他材质模型。PBR 被纳入核心规范的目的，是让不同运行时对材质参数有更一致的解释，而不是保证不同引擎的最终光照完全一致。

## 运行时价值

glTF 的数据布局和语义比较接近实时渲染器：

- 资源引用关系明确；
- Buffer 可以直接映射到 GPU 数据；
- 纹理格式和 Sampler 信息明确；
- 支持骨骼、Morph 和动画；
- `.glb` 方便单文件传输；
- JSON 与二进制数据分离，适合流式加载和缓存。

它降低的是“解析和解释资产”的复杂度，而不是消除所有平台转换。运行时仍可能需要纹理压缩、Shader 变体生成、坐标转换和引擎专用资源构建。

## 代价与限制

- glTF 主要描述运行时资产，不包含完整 DCC 编辑历史和修改器系统；
- 不同引擎对扩展、材质、动画和坐标的支持可能不同；
- glTF 本身不保证所有软件的导入结果完全一致；
- PBR 参数统一不等于光照、后处理和色彩管理完全一致；
- 大型复杂场景的协作和非破坏编辑能力不如 USD；
- 游戏最终通常仍会把 glTF 转换成自己的运行时格式。

## 本章结论

glTF 的核心价值不是“替代 FBX”，而是提供一个开放、轻量、面向实时渲染的共同交付协议。FBX 可以继续承担 DCC 制作和交换，glTF 则适合把整理后的 Mesh、材质、骨骼和动画交给 Web、引擎或自研运行时。

它通过统一语义和数据布局减少跨软件差异，但不能替开发者处理单位、轴向、材质模型和引擎导入策略。
