# GPU 流程控制惯用法

## 章节内容

本章讨论 GPU 上的 `if`、`for`、`while` 和其他流程控制方式。早期 GPU 的片元处理器本质上是 SIMD 结构，分支和循环必须谨慎使用；本章介绍如何根据硬件能力选择动态分支、静态展开、谓词计算、深度测试和遮挡查询等实现方式。

### GPU 分支的基本限制

高层 Shader 语言虽然允许写 C 风格的流程控制，但它们不一定对应 CPU 上的分支执行。早期硬件常常会执行两个分支，再使用条件结果选择最终值；如果一个执行组内的片元走向不同分支，就会产生线程闲置。

因此，分支条件在空间上越一致，效率通常越高。若整个物体或一大片区域都走同一分支，动态分支可能很有效；若相邻片元频繁分歧，则可能比无分支代码更慢。

### 条件计算与谓词

对于简单条件，可以把分支改写为 `lerp`、`step`、`smoothstep`、乘法和加法，让所有线程执行同一条路径，再用权重选择结果。这适合两个分支都很短的情况；如果分支一侧计算非常昂贵，强行同时计算两侧反而会浪费大量 ALU。

### 循环

固定次数循环可以由编译器展开，以换取更少的分支控制；但展开会增加指令和寄存器压力。动态次数循环可以减少无效计算，但早期硬件对动态循环的支持有限，且同一执行组内不同线程退出时间不同会降低效率。

通常应把循环上限控制在较小范围，尽量让线程在相近的迭代次数结束，并把不随线程变化的循环内容提取到外部。

### 利用深度测试和遮挡查询

某些需要“筛选元素”的算法可以借助 GPU 固定功能完成。例如先把满足条件的元素写入深度缓冲，再用深度测试让后续片元被剔除；遮挡查询可以统计通过深度测试的片元数量。

这种做法可以把部分条件判断转移到光栅化和深度单元，但需要额外 PASS、状态切换和同步。它不是所有分支的通用替代品，只适合条件能够表达为空间覆盖或深度关系的任务。

### 顶点程序与片元程序

顶点处理器和片元处理器的控制流能力并不完全相同。顶点数量通常较少，顶点阶段更适合做较复杂的分支；片元数量可能非常大，因此片元分支要更加关注分歧、过度计算和早期剔除。

### 总结

GPU 流程控制的目标不是彻底消灭 `if`，而是让分支具有空间一致性，避免昂贵分支的分歧，并在合适时利用固定功能的深度、模板和遮挡机制。实际性能需要结合分支成本、线程分歧、循环次数、寄存器占用和测试结果判断。

## 讨论与补充

### 1. GPU 中循环的执行方式

循环和分支的本质类似：同一个 Warp/Wave 中的线程通常共享指令流。

如果所有线程执行固定次数的循环，执行效率通常较好：

```hlsl
for (int i = 0; i < 4; i++)
{
    DoWork();
}
```

此时整个线程组都会执行相同的四次循环，没有明显的线程分歧。

如果循环次数由每个线程自己的数据决定，就可能出现不同线程执行不同次数的情况：

```hlsl
for (int i = 0; i < count; i++)
{
    DoWork();
}
```

例如同一 Warp 中某个线程需要循环 2 次，其他线程需要循环 4 次，硬件通常要把循环执行到最长的 4 次：

```text
第 1、2 次：所有线程执行
第 3、4 次：前一个线程已经结束，处于闲置状态
```

已经完成循环的线程会被屏蔽，但不会自动切换去执行其他无关任务。

`break` 和 `continue` 也可能造成类似分歧。如果同一 Warp 中部分线程退出循环，其他线程继续执行，整个 Warp 仍需要维持循环控制流程，只是已经退出的线程不再参与计算。

固定次数的小循环可能被编译器展开成重复的指令，从而减少循环计数和跳转；但展开会增加指令数量和寄存器占用，过度展开可能降低同时驻留的 Warp 数量。因此循环展开需要根据循环规模、Shader 复杂度和实际性能测试决定。

总结来说：

> 循环次数在 Warp 内一致时通常效率较好；循环次数不一致时，硬件往往执行到最长循环次数，提前结束的线程会闲置。固定循环可以被展开，但会增加指令和寄存器压力。
