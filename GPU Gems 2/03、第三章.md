# 几何实例化

## 章节内容

本章介绍几何实例化的基本概念和多种实现方式。核心目标是：当场景中存在大量使用相同或相近网格的物体时，不必让 CPU 为每个物体单独准备和提交绘制批次，而是复用同一份几何数据，只改变每个实例的变换、颜色、动画或 LOD 等属性，从而降低 CPU、API 调用和总线传输开销。

### 1. 为什么需要几何实例化

植被、草、石块、建筑部件、粒子以及其他场景杂物通常会重复使用相同的网格，但每个实例仍需要拥有不同的位置、旋转、缩放和少量外观变化。如果为每个实例单独提交一次绘制，就会产生大量批次，CPU 需要反复设置渲染状态、绑定资源并调用绘制接口。

几何实例化将“相同的几何结构”和“每个实例不同的属性”分离，使 GPU 能够在一次批处理中绘制许多份几何。书中将一个实例化批次抽象为一组共享的几何数据、一组实例属性以及对应的渲染和纹理上下文。

### 2. 基本数据结构

#### 2.1 Geometry Packet

Geometry Packet 是模型本身的几何数据，通常包括：

- 顶点位置；
- 顶点索引；
- 纹理坐标；
- 法线和切线；
- 骨骼权重等蒙皮数据；
- 顶点颜色等逐顶点属性；
- 用于剔除的包围球。

它描述的是模型空间中的一份共享网格，不包含某个实例在世界中的具体位置。

#### 2.2 Instance Attributes

Instance Attributes 是每个实例独有的数据，通常包括：

- 模型到世界空间的变换矩阵；
- 实例颜色或其他外观参数；
- 动画或蒙皮状态；
- LOD 级别等实例级选择信息。

顶点着色器可以使用这些属性，将同一份模型空间几何变换到不同的世界位置，或者为不同实例产生不同的颜色和动画效果。

#### 2.3 Geometry Instance、Render Context 与 Texture Context

一个 Geometry Instance 可以看作 Geometry Packet 与 Instance Attributes 的组合。

Render Context 保存实例绘制时所需的渲染状态，例如着色器、混合状态、深度状态和光栅化状态。Texture Context 保存当前绘制所使用的纹理及其采样相关设置。

多个 Geometry Instance 在共享几何、渲染状态和纹理上下文的条件下，可以组成一个 Geometry Batch。一个 Geometry Batch 最终可以对应一次 `DrawIndexedPrimitive` 调用。

### 3. 批次排序与渲染阶段

为了减少管线状态和纹理切换，渲染器通常先按照 Render Context 对批次排序，再按照 Texture Context 对批次排序。这样可以让使用相同着色器、渲染状态和纹理的几何尽可能连续绘制。

更新实例属性和绘制实例可以分成两个阶段。把更新阶段与渲染阶段分开，有利于同一批几何被多个渲染过程复用，例如主视图、阴影贴图、水面反射和水面折射等。更新阶段也可以根据需要执行动画、LOD 或实例位置变化。

### 4. 静态批处理

静态批处理会在初始化或加载阶段，把每个实例的顶点变换到世界空间，然后将所有实例的顶点和索引复制到一组较大的静态顶点缓冲区和索引缓冲区中。

优点：

- 运行时不需要为每个实例重新变换顶点；
- 实现简单，旧硬件也可以支持；
- 对完全静止的物体通常具有较好的运行时性能。

缺点：

- 每个实例都需要一份变换后的顶点数据，显存占用较大；
- 实例移动后需要重新构建或更新批次；
- 不适合运行时动画和蒙皮；
- 不容易在同一批数据中灵活地进行实例级 LOD；
- 大批次可能导致剔除粒度变粗。

### 5. 动态批处理

动态批处理在每帧将实例数据变换到世界空间，并把结果流式写入动态顶点缓冲区和索引缓冲区，然后进行绘制。它可以处理位置变化、动画和蒙皮，因此比静态批处理灵活。

但动态批处理需要 CPU 每帧执行顶点变换、复制几何数据并向 GPU 上传，可能产生较高的 CPU 计算、内存带宽和总线传输开销。频繁锁定和丢弃动态缓冲区也会增加管理成本，因此通常是几种方案中运行时开销较高的一种。

### 6. 顶点常量实例化

顶点常量实例化只在 GPU 内保存一份共享几何，然后把每个实例的变换矩阵、颜色等属性放入顶点常量。顶点着色器根据当前实例编号读取相应常量，并完成实例变换。

这种方式不需要复制多份顶点数据，CPU 和显存带宽开销较低，适合支持顶点着色器的硬件。但顶点常量数量有限，因此一个批次能容纳的实例数量受到限制。例如，一个实例使用五个常量寄存器，而硬件最多提供 256 个常量寄存器时，一次批次理论上只能放入约 40 个实例，实际还要扣除着色器本身使用的常量。

该方案通常不适合复杂蒙皮，因为骨骼矩阵也会快速消耗常量空间；实例数量过多时，还需要拆成多个批次。

### 7. Geometry Instancing API

硬件几何实例化 API 将共享几何和实例数据放在不同的数据流中：

- 一个数据流保存模型的顶点和索引；
- 另一个数据流保存每个实例的变换、颜色等实例属性。

GPU 会在一次绘制调用中虚拟地复制并处理多份几何。顶点着色器可以通过实例编号读取当前实例的数据，使许多相同网格在不同位置、以不同参数绘制。

相较顶点常量实例化，实例数据不再受到顶点常量寄存器数量的严格限制；相较静态批处理，也不需要为每个实例复制一整份顶点数据。它能够显著减少 CPU 绘制调用、几何复制以及总线传输，适合树木、植被、粒子和其他具有大量相同几何的对象。

这种方式的限制是：同一个批次中的实例必须共享同一个 Geometry Packet。不同网格通常需要拆成不同批次；不同材质和纹理也可能需要按照渲染上下文拆分。复杂蒙皮不是该方案最直接的使用场景，不过可以通过骨骼纹理等方式把动画数据提供给顶点着色器。

### 8. 方案选择

本章没有给出适用于所有场景的唯一方案，而是根据对象的运动性、数量、几何共享程度和硬件能力进行选择：

- 室内大量静止且重复的物体，可以使用静态批处理；
- 需要动画或蒙皮的对象，可以使用动态批处理；
- 植被、树木、粒子等需要大量重复绘制且实例属性经常变化的对象，适合使用硬件几何实例化；
- 实际渲染器可以将这些实现封装在统一的 `GeometryBatch` 抽象之后，根据对象类型选择具体方案。

## 讨论与补充

### 1. 批次排序不等于合批

批次排序和合批相关，但不是同一个概念：

- **合批**：把多个物体合并或组织成一个批次，目标是减少 Draw Call 或减少每次绘制需要处理的内容；
- **批次排序**：批次已经存在后，重新安排绘制顺序，让使用相同 Shader、材质、纹理和管线状态的批次连续绘制，以减少状态切换。

例如，批次 A 和 C 使用相同的 Shader 与纹理，批次 B 使用另一套资源：

```text
原顺序：A → B → C
调整后：A → C → B
```

调整顺序不会自动把 A 和 C 合并成一个批次，只是让它们连续绘制，使状态切换更少。透明物体还需要遵守正确的深度顺序，因此不能任意排序。

### 2. Unity 中几种批处理方式的区别

Unity 的静态合批、动态合批和 SRP Batcher 都是为了降低 CPU 侧的渲染开销，但优化对象不同：

| 方式 | 主要减少的开销 | 是否合并几何 |
| --- | --- | --- |
| 静态合批 | 运行时顶点变换和部分状态切换 | 是 |
| 动态合批 | 将小型动态网格临时组织成批次 | 是，通常逐帧进行 |
| SRP Batcher | 每个 Draw Call 前的材质和管线状态准备 | 否 |

静态合批适合不会独立移动的物体。Unity 会在加载阶段或构建阶段将实例变换到世界空间，并组织到较大的顶点和索引缓冲区中。它可能增加内存占用，而且大批次会使剔除粒度变粗。

动态合批适合小型、会移动的物体，但需要 CPU 每帧变换和复制顶点数据。在现代硬件上，这些 CPU 工作有时可能比直接提交 Draw Call 更昂贵，因此不能默认认为动态合批一定更快。

SRP Batcher 不会把多个网格合并成一个网格，也通常不会减少 Draw Call 数量。它要求物体使用相同的 Shader Variant，通过复用和持续保留材质相关的常量缓冲区，减少每个 Draw Call 前的 CPU 设置工作。

### 3. 它们与 GPU Instancing 的关系

GPU Instancing 是一份共享网格配合多份实例数据，尽量用一次绘制调用绘制多个相同 Geometry Packet。它和 SRP Batcher 解决的问题不同：

```text
GPU Instancing → 尽量减少 Draw Call 数量
SRP Batcher    → 让仍然存在的 Draw Call 更便宜
```

静态合批、动态合批、GPU Instancing 和 SRP Batcher 可以在同一项目中并存，但某个具体物体最终采用哪种方式取决于其是否静止、网格和材质是否兼容、Shader Variant 是否一致，以及 Unity 当前的批处理选择规则。
