# 分段缓冲

## 章节内容

本章介绍分段缓冲（Segment Buffering）。它针对大量静态实例导致批次数量过多的问题，将空间位置相近、材质和几何条件相容的多个实例自动组织到一个更大的顶点/索引缓冲区中，同时保留每个原始实例在大缓冲区中的边界信息。渲染时只提交可见实例对应的连续片段，从而在减少批次的同时保留较好的剔除能力和非重复的场景外观。

### 1. 问题：实例化之后批次仍然过多

实例化可以避免为每个物体制作独立模型，但如果场景中有大量实例，每个实例仍然对应一个批次，就可能被 Draw Call 数量和渲染状态切换限制。

例如，一个场景中摆放了大量使用相同材质的椅子、杂物或建筑部件。即使它们共享同一个模型，每个实例仍可能需要单独设置变换、光照贴图或顶点流。频繁的状态变化会增加驱动程序和 CPU 的开销。

直接由美术把多个模型合并成新模型可以减少实例数，但会增加定制资产的工作量，也容易让场景产生重复感，并且不利于单独剔除其中某个物体。

### 2. 分段缓冲的核心思路

分段缓冲在加载阶段自动完成类似的组织：

1. 收集某个模型的实例列表；
2. 按实例的空间位置重新排序，使空间相近的实例在一维数组中也尽量相邻；
3. 将这些实例的几何拼接到一个较大的顶点缓冲区和索引缓冲区；
4. 记录每个原始实例在大缓冲区中对应的顶点和索引范围，这些记录称为 Segment；
5. 渲染时根据可见实例得到需要绘制的 Segment 列表，并合并其中连续的 Segment。

最终结果类似于自动生成了多个“超实例”（über-instance），但它仍然可以跳过视锥体外的原始实例。

### 3. 空间排序

空间排序是分段缓冲能保持剔除效率的关键。书中提出使用空间数据结构组织实例位置，例如：

- 三维 K-d tree；
- Octree；
- 其他能够把空间邻近对象排列到一起的数据结构。

具体做法是先根据实例位置建立树，然后进行深度优先遍历。遍历到叶节点时，将叶节点中的实例加入新的有序列表。这样，空间上相近的实例通常会在大缓冲区中相邻。

分段缓冲和实例有序列表通常只需要在载入新的实例列表时生成一次，而不是每帧重建。

### 4. 构建大顶点和索引缓冲区

按照空间排序后的实例列表，逐个处理实例：

- 将实例的顶点变换到世界空间；
- 把变换后的顶点追加到统一的顶点缓冲区；
- 将对应索引追加到统一的索引缓冲区；
- 保存该实例在大缓冲区中的起始位置和结束位置。

由于这些实例是静态的，大缓冲区通常只在加载阶段创建。每个 Segment 都知道自己对应的顶点和索引范围，因此后续可以只提交某些 Segment。

### 5. 渲染时合并可见片段

每次渲染时，先像普通实例一样确定哪些物体可见。例如，位于相机视锥体外的实例可以直接从可见列表中删除。

然后将可见实例转换为大缓冲区中的 Segment 范围。如果相邻实例对应的 Segment 在大缓冲区中也是连续的，就可以把它们合并成一段更大的绘制范围。最终生成的 Draw 列表只包含可见并且经过合并的缓冲区片段。

理想情况下，输出结果与逐个绘制原始实例完全一致，只是减少了批次数量。

### 6. 光照贴图与纹理图集

分段缓冲要求相邻实例之间不能频繁发生无法合并的渲染状态变化。如果每个实例都有独立的光照贴图，那么绘制实例之间就必须切换纹理，简单拼接会失去批处理收益。

解决方式之一是自动生成纹理图集：

- 将多个实例的光照贴图放入同一张更大的纹理；
- 调整每个实例的纹理坐标，使其指向图集中的独立区域；
- 因为每个实例在大顶点缓冲区中有独立的顶点区间，所以可以直接修改对应顶点的纹理坐标，不会影响其他实例。

这样，原本需要在实例之间切换的纹理可以统一为一张纹理，从而使分段缓冲能够用于带光照贴图的场景。

## 讨论与补充

### 1. Unity 静态合批与手动合并网格不是一回事

“合得太少优化不明显，合得太多剔除粒度过粗”的担心，主要针对在 DCC 或运行时直接使用 `Mesh.CombineMeshes` 把多个物体变成一个大网格的情况。这样一旦其中一部分可见，整个合并网格可能都需要绘制。

Unity 的静态合批会把几何数据放入内部的合并缓冲区，但原来的 GameObject 仍然存在，因此仍可以对原始物体单独做剔除。它不是简单地把整个场景变成一个不可分割的大物体。

可以把两者区分为：

```text
手动合并网格：
多个物体 → 一个网格 → 可能牺牲物体级剔除

Unity 静态合批：
多个物体 → 共享合并后的几何存储
          → 保留原始 Renderer 的独立剔除
```

### 2. 静态合批的适用范围

静态合批更适合小范围、不会独立移动、材质相容的物体，例如室内房间中的墙、柱子和装饰物，或者同一建筑区域内的大量静态小物件。

它不适合被频繁移动的物体，也不适合需要独立 LOD、运行时替换或大量流式加载的对象。大型开放世界、密集森林等场景通常还需要结合 GPU Instancing、HLOD、分块加载或 GPU Driven 等方案。

静态合批会增加几何数据的内存占用，而且不同材质、不同渲染状态仍然会限制合批效果。因此是否启用不能只看 Inspector 中的 Static 标记，还应通过 Profiler、Frame Debugger 或 RenderDoc 检查实际的 CPU 和 GPU 收益。
