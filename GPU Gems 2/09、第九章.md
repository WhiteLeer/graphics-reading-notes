# 延迟着色

## 章节内容

本章以《S.T.A.L.K.E.R.》为例，回顾一个完全基于延迟着色和全动态光照的渲染器。延迟着色把场景几何绘制和光照计算拆开：第一阶段只把位置、法线、材质等属性写入 G-Buffer，之后以屏幕空间的光照 Pass 读取这些属性并计算光照。这样可以避免前向渲染中对每个物体、每个光源反复执行相同的顶点和材质工作，并降低大量动态光照带来的 CPU 批次压力。

本章不是延迟渲染的通用教程，而是一次针对高端 GPU、全动态光照和动态阴影目标的工程复盘，重点讨论延迟渲染的收益、限制和优化方法。

### 1. 延迟着色的基本流程

前向渲染通常在绘制几何体时直接完成材质和光照计算；延迟着色则分成两个主要阶段：

```text
场景几何 Pass
    → 写入 G-Buffer：位置、法线、反照率、光泽度、材质 ID 等

光照 Pass
    → 读取 G-Buffer
    → 计算点光源、聚光灯、方向光和阴影
    → 累加最终光照
```

几何阶段不需要针对每个光源重复计算完整材质。光照阶段可以使用全屏四边形、光源体积或其他屏幕空间几何，只处理当前光源实际影响的像素。

### 2. 为什么 S.T.A.L.K.E.R. 选择延迟着色

书中选择延迟着色主要有几个原因：

- CPU 受大量动态光源和渲染批次限制；
- 顶点处理能力也是瓶颈；
- 场景有较多动态光照和阴影；
- 前向渲染会反复执行顶点变换、各向异性纹理过滤、视差映射、法线贴图解码和细节纹理采样；
- 延迟渲染可以让光照成本更接近光源影响的屏幕区域，而不是物体与光源组合的数量。

在大量动态光源的复杂场景中，即使原来的前向着色器更简单，最终前向渲染器仍可能比延迟渲染器更慢。

### 3. 延迟着色的常见误解

#### 3.1 延迟着色一定更慢

延迟着色的光照计算全部在像素级进行，但光照 Pixel Shader 并不一定比前向版本复杂很多。额外成本主要来自：

- 读取 G-Buffer；
- 解码 G-Buffer 中压缩的数据；
- 生成和写入多个渲染目标；
- 额外的带宽和填充率压力。

最终性能取决于数据集、Overdraw、光源数量、屏幕分辨率和 CPU/顶点处理是否已经成为瓶颈。

#### 3.2 延迟着色不适合方向光

如果只有少量无阴影方向光，延迟光照的优势可能不明显；但对于带阴影的太阳光，即使只有一个方向光，也可以通过屏幕空间遮挡和模板优化减少复杂阴影计算，因此仍然可能受益。

### 4. G-Buffer 与材质系统

延迟渲染的限制之一是几何阶段必须把材质信息编码进有限数量的渲染目标。书中使用 DirectX 9 的 MRT，在多个 Render Target 中保存位置、法线、反照率、光泽度以及额外的材质和物体 ID。

多出的通道被用于控制光照函数。光照 Shader 读取材质 ID，再根据 ID 选择对应的光照参数或查找表。这样，材质属性可以影响光照 Shader，而不是像前向渲染那样为每个材质和光照组合生成大量 Shader 变体。

这种方法可以支持多种光源类型和特殊光源，例如：

- 点光源；
- 聚光灯；
- 方向光；
- 包裹式半球光；
- 体积雾光源。

本质上，材质系统从“材质 Shader 受光源影响”转变为“光源 Shader 根据材质属性变化”。

### 5. 延迟渲染的主要性能瓶颈

本章将瓶颈分为三个部分：

1. G-Buffer 创建；
2. 光照计算；
3. 后处理和 G-Buffer 解码。

在 S.T.A.L.K.E.R. 中，实时阴影生成是重要瓶颈，有些场景中甚至是最大的单项开销。因此优化目标包括：

- 只处理真正影响屏幕图像的光源；
- 尽量把不需要阴影的光源转成无阴影光源；
- 简化光照 Shader；
- 优化 G-Buffer 和后处理，但不牺牲目标画质。

由于 G-Buffer 和后处理的成本相对稳定，而玩家可以在同一位置放置任意数量的火把，使动态光照成本变得不可预测，书中倾向于优先保证 G-Buffer 和后处理质量，再严格控制光照数量和光照 Shader。

### 6. 光源剔除与受影响像素剔除

延迟光照的重要优化是：

```text
只绘制影响最终图像的光源
    ↓
对每个光源只处理受其影响的像素
```

S.T.A.L.K.E.R. 使用了多级光源剔除：

1. 使用 Sector-Portal 结构进行粗粒度剔除；
2. 使用类似 Hierarchical Z-Buffer 的 CPU 遮挡剔除；
3. 使用 DirectX 9 Occlusion Query 删除完全被遮挡的光源；
4. 使用 Stencil Mask 标记每个光源真正影响的屏幕像素。

在典型室内场景中，前面的剔除可以减少约 30% 到 50% 的光源。结合模板标记后，可以显著减少光照 Shader 的实际执行范围。

### 7. 光源和阴影的工程取舍

书中要求艺术和技术共同决定每个光源的特性：

- 是否真的需要投射阴影；
- 是否需要投影纹理；
- 是否需要半透明物体投射阴影；
- 是否需要高光反射；
- 光源是否移动。

许多光源只是用来模拟全局光照的外观，并不一定需要阴影或高光。对于不移动的光源，可以预计算静态遮挡物的潜在可见集合，减少阴影生成时需要测试的投影物体。

### 8. 太阳光优化

书中的太阳光使用一张较大的阴影贴图，并采用类似 Perspective Shadow Map 的投影，让更多分辨率集中在观察者附近。

太阳阴影通常需要较高的过滤成本，因此需要尽量减少需要复杂光照的像素：

- 天空盒不需要进行太阳表面光照；
- 背向太阳的像素通常不需要复杂的太阳光计算；
- Ambient Occlusion 为零的像素可以排除，因为太阳光无法到达这些区域。

书中先用较简单的 Shader 判断这些条件，再写入 Stencil Mask。后续复杂太阳光 Pass 只在模板允许的像素上执行。

### 9. G-Buffer 格式与带宽

G-Buffer 格式会直接影响读取带宽和解码成本。更大的每像素格式可以保存更多精度，但读取成本和显存带宽也会增加。例如 64 位纹素通常比 32 位纹素读取成本更高，128 位格式则更明显。

书中指出，最小格式不一定最快。某些情况下，较宽但更容易直接解码的 G-Buffer，虽然浪费带宽，却可能比紧凑编码的格式更快，因为它减少了复杂的解包和重建计算。

### 10. 点光源的全向阴影

延迟渲染中，全向点光源阴影主要有三种实现：

- 使用立方体阴影贴图保存光源到遮挡物的距离；
- 将立方体的六个面展开到一张 2D 纹理中，再使用小型立方体纹理进行重索引；
- 把点光源拆成六个聚光灯分别渲染。

书中最终选择把点光源当作六个聚光灯处理，因为延迟渲染可以避免前向渲染中反复变换大量几何的高成本，并且这种方案更方便进行过滤和纹理打包。每个聚光灯边缘需要预留比过滤核更大的边界，避免视锥体边缘的过滤错误。

### 11. 透明物体

延迟渲染的 G-Buffer 通常只保存每个像素最前面的表面属性，因此天然不适合普通 Alpha Blending 和多层透明表面。

S.T.A.L.K.E.R. 的处理方式是：

```text
不透明物体 → 延迟渲染
透明物体   → 前向渲染
```

透明物体使用带光照但不带阴影的前向路径。这是一个工程上的混合方案，而不是试图让透明表面强行适配单层 G-Buffer。

### 12. 逐像素位移和实验性方案

本章还讨论了若干实验或辅助方案：

- 使用虚拟位置修正改善视差贴图在阴影边缘附近的表现，并缓解部分阴影偏移问题；
- 将 Ambient Occlusion 存在未使用的顶点分量中，而不是为所有对象制作独立 AO 光照贴图；
- 尝试通过多层 G-Buffer 实现 Elevation Map，但发现需要大量层才能隐藏层间伪影，并带来巨大的填充和着色成本，因此放弃；
- 尝试使用动态生成的间接光源近似全局光照，但结果和性能仍不适合作为实际游戏方案。

### 13. 结论

延迟着色并不适合所有游戏，但对于大量动态光源、动态阴影、CPU Draw Call 压力较高且 Overdraw 适中的场景，它可以显著降低几何处理、重复材质计算和 CPU 管理成本。

它的代价主要是：

- G-Buffer 的显存带宽和写入成本；
- 对透明材质、抗锯齿和部分复杂材质模型的限制；
- 光照阶段可能随着光源数量失控。

S.T.A.L.K.E.R. 的经验说明，延迟渲染的效果取决于完整的工程配套：G-Buffer 设计、光源剔除、阴影策略、模板遮罩、材质系统和后处理必须一起设计。

## 讨论与补充

### 1. MRT 与 G-Buffer 的关系

MRT 是 **Multiple Render Targets，多重渲染目标**。它允许一个片元着色器在一次绘制中，同时向多张 Render Texture 写入不同输出：

```text
SV_Target0 → Albedo
SV_Target1 → Normal
SV_Target2 → Position / Depth
SV_Target3 → Material ID / Roughness
```

延迟渲染通常使用 MRT 一次生成 G-Buffer，但 MRT 和 G-Buffer 不是同一个概念：

```text
MRT：一次 Pass 同时写入多张 Render Target 的机制
G-Buffer：延迟渲染中保存位置、法线、材质等属性的纹理集合
```

MRT 可以减少为了分别生成颜色、法线和材质数据而重复绘制场景的次数，但代价是同时写入多张纹理，增加显存带宽、Render Target 占用和 G-Buffer 格式设计成本。
