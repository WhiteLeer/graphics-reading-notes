# 硬件遮挡查询

## 章节内容

本章介绍如何有效使用硬件遮挡查询（Hardware Occlusion Query）进行遮挡剔除。遮挡查询允许应用询问：如果绘制某个物体，有多少片元能够通过深度测试。通过先测试一个物体或空间层级节点是否可见，就可以跳过完全被其他物体遮挡的复杂几何，从而减少顶点处理、光栅化、像素着色和 Draw Call。

本章重点解决两个问题：遮挡查询本身会增加额外绘制开销，以及查询结果通常不能立即返回，CPU 如果等待结果会造成流水线停顿。解决方案是利用空间连贯性和时间连贯性，使用层级结构和上一帧的可见性结果来安排本帧的查询与绘制。

### 1. 硬件遮挡查询的基本机制

一次典型的遮挡查询过程如下：

1. 开始一个 Occlusion Query；
2. 关闭颜色写入和深度写入，只保留必要的深度测试状态；
3. 绘制待测试物体的简单保守近似，通常是包围盒；
4. 结束 Occlusion Query；
5. 查询 GPU 统计到的片元数量；
6. 如果通过深度测试的片元数量大于阈值，则绘制物体的完整几何。

这里的近似体必须覆盖原始物体在屏幕空间中的全部可能区域，否则可能出现包围盒不可见、但真实物体仍有部分可见的错误。包围盒越简单，测试成本越低，但过于松散的包围盒会降低剔除收益。

遮挡查询统计的是通过深度测试的片元数量，而不是简单判断包围盒是否进入视锥体。因此它可以处理被其他实际几何遮挡的情况。

### 2. 为什么朴素方案会很慢

最直接的做法是按照从前到后的顺序，对场景中的每个物体分别执行：

```text
发起查询
等待结果
如果可见则绘制物体
```

这种方案有两个主要问题：

- 每个物体都额外增加一次查询绘制；
- CPU 必须等待 GPU 返回结果，可能导致 CPU 停顿和 GPU 空闲。

在城市漫游场景中，可能只有几百个物体可见，但场景中有成千上万个物体。如果对所有物体逐个查询，查询本身的开销可能超过直接绘制这些简单物体的开销。

### 3. 使用空间层级减少查询数量

本章使用空间层级将邻近物体组织到一起，例如：

- K-d tree；
- BSP tree；
- 八叉树；
- 其他包围体层级结构。

树的内部节点代表一组物体，叶节点代表较小的物体集合或实际几何。遍历时先测试内部节点：

```text
测试父节点
    ├─ 完全被遮挡 → 跳过整个子树
    └─ 可见        → 继续测试子节点
```

如果一个内部节点包含几百个物体，那么一次查询被遮挡后，就可以跳过这几百个物体对应的查询和绘制。层级结构因此把一次查询的收益扩大到一个空间区域。

节点通常按照从前到后的顺序处理，使前方的遮挡物尽早写入深度缓冲，从而提高后续遮挡查询的有效性。

### 4. 分层 Stop-and-Wait 方法的问题

即使使用层级结构，如果每测试一个节点都立即等待查询结果，CPU 仍然会频繁停顿。其流程大致是：

1. 查询当前节点；
2. 等待结果；
3. 节点可见则继续访问子节点；
4. 节点不可见则跳过整个子树。

这种方法虽然减少了测试对象数量，但没有解决 GPU 查询结果的高延迟问题。对于层级很深的场景，CPU 可能在每一层都等待。

### 5. 相干层级遮挡剔除

本章的核心算法利用了两种连贯性：

#### 5.1 时间连贯性

实时场景中，相机和物体通常不会在一帧内发生巨大变化。因此，上一帧可见的节点大概率在本帧仍然可见，上一帧被遮挡的节点也可能继续被遮挡。

算法使用上一帧的可见性结果作为本帧的初始猜测，避免在每次查询后立即等待。上一帧可见的节点可以先直接绘制，同时在合适的位置发起新的查询；查询结果返回后，再用于后续节点的判断。

#### 5.2 空间连贯性

空间上相邻的物体通常具有相近的可见性。算法通过层级结构将它们组织在一起，并优先测试可能包含大量被遮挡物体的节点。

这样可以把查询结果等待期间填充为有用的绘制工作，并避免测试大多数不必要的内部节点。查询数量主要与可见区域附近的节点数量相关，而不是与整个场景的物体总数或层级深度成正比。

### 6. 哪些场景适合遮挡查询

硬件遮挡查询最适合：

- 场景规模很大；
- 每帧只有一小部分区域可见；
- 存在建筑、墙壁或其他大型遮挡物；
- 被遮挡的节点包含大量几何、Draw Call 或像素工作。

典型例子是城市街道或室内区域的步行视角。通过跳过整栋建筑、街区或房间，可以获得明显收益。

如果场景几乎没有遮挡，例如从高空俯视城市或在开阔平原中飞行，遮挡查询很难剔除大量物体，反而会增加额外查询开销。这种情况下应该关闭或切换掉遮挡查询。

### 7. 进一步优化

本章还讨论了几种优化：

- 对上一帧已经可见的叶节点，直接使用真实几何发起查询，避免额外绘制包围盒；
- 先执行 Z-Only Pass，建立深度缓冲并获得可见性分类，再执行完整颜色 Pass；
- 将可见像素阈值设置为大于零，忽略只露出极少像素的物体，以换取性能；
- 假定物体在连续若干帧内保持可见，减少查询次数，但代价是可能多绘制一些物体。

这些优化都会在准确性、查询数量、额外几何绘制和可能的过度绘制之间进行取舍。

## 讨论与补充

### 1. 遮挡剔除可以关闭，也可以由自定义系统接管

遮挡剔除是一个可选的可见性优化阶段，并不是保证画面正确所必需的阶段。关闭后，距离、Layer、视锥体等其他剔除仍然可以继续执行；只是原本完全被遮挡的物体可能仍会提交 Draw，之后再由 GPU 的深度测试淘汰其大部分片元。

整体结构可以是：

```text
关闭内置遮挡剔除
    ↓
自定义视锥体、距离、HZB 或 GPU Driven 可见性判断
    ↓
只提交自定义列表中的物体
```

在 Unity 中，可以关闭相机的内置遮挡剔除；如果要完全接管主场景的可见性流程，通常需要自定义 SRP、GPU Driven 渲染框架或更底层的批处理接口。普通 RendererFeature 通常只是追加一个 Render Pass，并不会自动替换主渲染的全部剔除流程。

在 Unreal 中，也可以关闭硬件 Occlusion Query，改用 HZB、预计算可见性或自定义可见性系统。自定义方案还需要同时处理视锥体、距离、LOD、阴影和反射等额外视图的可见性。
