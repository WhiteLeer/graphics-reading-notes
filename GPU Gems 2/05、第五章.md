# 多流顶点数据与资源管理

## 章节内容

本章讨论复杂场景中的资源管理和多流顶点数据。一个网格的每个顶点可能包含位置、法线、切线、多个纹理坐标、骨骼权重等大量属性，但不同渲染 Pass 并不一定需要全部属性。书中的方案将顶点数据拆分为多个用途明确的 Vertex Stream，再根据当前 Pass 组合所需的数据，并由资源管理器将通用网格数据转换为适合当前硬件的格式，从而减少内存、总线传输和 GPU 输入带宽。

### 1. 问题：顶点数据并非每个 Pass 都需要

现代场景需要复杂网格、多种材质和多个渲染 Pass，例如主渲染、阴影、反射、折射和深度预处理。一个完整顶点可能同时包含：

- 位置；
- 法线；
- 顶点颜色；
- 切线；
- 多组纹理坐标；
- 骨骼权重和骨骼影响；
- 实例化数据。

但不同 Pass 的需求不同。例如纯 Z-Prepass 可能只需要位置，普通静态渲染可能需要位置和纹理坐标，带蒙皮的主渲染则还需要动画数据。如果所有 Pass 都绑定完整顶点结构，就会传输和读取大量当前并不需要的数据。

### 2. 四类 Vertex Stream

书中将顶点数据拆分为四类：

- **G：Geometry Stream**：位置、法线和顶点颜色；
- **T：Texture Stream**：纹理坐标，以及切线空间法线贴图所需的切线等数据；
- **A：Animation Stream**：骨骼权重、骨骼影响等动画数据；
- **I：Instancing Stream**：硬件实例化所需的实例数据。

根据当前渲染任务选择不同组合：

```text
静态网格              G 或 G + T
带动画网格            G + A 或 G + T + A
实例化网格            G + I 或 G + T + I
实例化且带动画        G + A + I 或 G + T + A + I
纯 Z-Pass             G
```

这样可以让渲染器只绑定当前 Pass 真正需要的 Vertex Stream。

### 3. DirectX 中的多流绑定

DirectX 8 引入了将多个 Vertex Buffer 绑定到不同 Stream 的机制。每个 Stream 是一个连续的组件数组，GPU 可以从多个顶点缓冲区读取同一个顶点所需的不同属性。

在 DirectX 9 中，主要通过以下步骤使用多流：

1. 创建描述顶点布局的 Vertex Declaration；
2. 使用 `SetVertexDeclaration()` 设置顶点声明；
3. 使用 `SetStreamSource()` 将不同 Vertex Buffer 绑定到对应的 Stream；
4. 调用 `DrawIndexedPrimitive()` 等绘制接口。

例如，Stream 0 可以保存位置、法线和颜色，Stream 1 保存多组纹理坐标。顶点声明负责说明每个属性位于哪个 Stream、具有何种类型以及在 Stream 中的偏移。

多流数量也不是越多越好。硬件支持的最大 Stream 数量有限，绑定过多 Stream 也会产生一定开销，因此书中的实现通常只使用一到四个 Stream。

### 4. 资源管理器

Gothic III 引擎将网格、纹理、动画、声音等数据统一封装为资源对象，并通过文件名或 GUID 访问。资源管理器负责：

- 按需加载资源；
- 通过引用计数让多个物体复用同一份网格；
- 管理资源在内存中的生命周期；
- 将与图形 API 无关的通用数据转换为硬件所需的数据格式；
- 根据当前硬件和渲染需求生成合适的顶点流。

网格资源本身不直接依赖 DirectX 或 OpenGL，而是保存位置数组、法线数组、颜色数组、纹理坐标数组、权重数组和索引数组等通用数据。这样同一套资源系统可以在不同图形 API 或不同硬件配置下生成不同的 GPU 数据布局。

### 5. Vertexprocessor：从通用数据生成硬件数据

渲染器在真正绘制前，根据网格资源中的顶点格式和当前需求，将通用顶点数组拆分到 G、T、A、I 等硬件 Vertex Stream 中。

典型过程是：

1. 请求网格资源；如果资源尚未载入则加载，否则增加引用计数；
2. 判断网格包含哪些顶点属性；
3. 根据当前渲染 Pass 选择需要的属性；
4. 将通用顶点数组复制或转换到特定的 Vertex Buffer；
5. 创建匹配的 Vertex Declaration 和 Index Buffer；
6. 将生成后的硬件格式用于实际绘制。

如果某些低端硬件或低质量模式关闭了某些效果，那么对应的纹理坐标、切线或其他顶点属性就不必生成和上传。

### 6. 各类数据的处理

Geometry Stream 通常保存位置、法线和颜色，并可以设计为固定大小的顶点格式，以便缓存和读取。

Texture Stream 根据网格实际拥有的纹理坐标数量生成可变布局，也可以把切线编码到其中一个坐标槽位中。如果使用光照贴图，每个实例通常需要独立的光照贴图 UV，因为 UV 与实例的世界位置有关，这会限制实例化并增加每个实例的内存开销。

Animation Stream 保存硬件蒙皮需要的骨骼权重和影响索引。不同模型需要的权重数量可能不同，因此可以只为实际需要的数量分配数据，而不是使用固定的最大数量。

Index Buffer 根据顶点数量选择 16 位或 32 位索引。顶点数量不超过 65,535 时可以使用 16 位索引，否则需要 32 位索引。使用能满足需求的最小索引类型可以降低内存占用。

### 7. 不同 Pass 选择不同 Stream

书中给出的一个例子是使用 G Stream 单独执行 Z-Pass。因为 Z-Pass 只需要几何位置等基础数据，所以可以不绑定纹理和动画相关的 Stream，以便快速完成深度写入和遮挡查询。

普通渲染则根据是否需要纹理、动画和实例化，组合相应的 Stream。各个 Stream 是否启用由当前视图和当前渲染任务决定，而不是所有 Pass 都固定使用完整顶点结构。

## 讨论与补充

### 1. ShaderPass、顶点属性与 Vertex Stream 的关系

ShaderPass 会声明自己需要的顶点属性，例如 `POSITION`、`NORMAL` 和 `TEXCOORD0`，但它通常不会直接在 Shader 代码中选择底层 Vertex Buffer。

实际流程更接近：

```text
ShaderPass 声明需要哪些顶点属性
    ↓
渲染器检查 Mesh Layout
    ↓
创建或选择 Vertex Declaration / Input Layout
    ↓
在 Draw 前绑定对应 Vertex Stream
    ↓
执行 Draw
```

例如：

```text
DepthPass：   绑定 G Stream
OpaquePass：  绑定 G + T Stream
SkinningPass：绑定 G + T + A Stream
```

因此，ShaderPass 是“声明需要什么”，渲染器是“决定这些属性来自哪个 Stream”，Draw 指令则使用当前已经绑定的顶点流执行绘制。普通 Unity ShaderLab 通常只能声明顶点属性，不能在 Pass 内直接重组底层 Stream；这种能力更多由引擎底层的 Mesh Layout、Vertex Factory 或自定义渲染器提供。
